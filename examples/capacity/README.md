# 多会话容量验证

这个 example 用同一套默认对话装配，验证单个 Node 进程在多会话同时运行时的正确性、时延、内存与持久化成本。它直接调用 `Runner`；“200 会话”表示 200 份独立内容、结构和运行器，不表示已经验证 200 个浏览器用户，也不以 HTTP 200 作为成功依据。

经真实 Web HTTP、独立负载发生器及 1/2/4 个服务进程的扩展实验见 [HTTP 多进程容量](./server/README.md)。它复用公开 Web 宿主，保持固定会话归属，单独记录容量曲线；本页下面的旧数字仍是直接调用 Runner 的结果。

模型端使用独立子进程中的本地 HTTP/SSE 模拟服务，客户端使用真正的 `ChatCompletionsProvider`。没有调用 DeepSeek 或其他真实模型，不读取 `.env`、API Key 或现有对话数据库。验证覆盖真实的模型协议解析、流式转交、交互等待、消息接纳和可选机制，但不评价模型智能、记忆质量或供应商并发额度。

## 使用

在仓库根目录执行，Node 与 pnpm 版本沿用根 `package.json`。

```sh
pnpm build

# 小规模回归：2、4 会话，以及全部装配组合和扰动场景。
node examples/capacity/run.mjs --smoke --out .capix/capacity-smoke-01

# 默认完整计划：10、50、100、200 会话，最后两组持续负载各 60 秒。
node examples/capacity/run.mjs --out .capix/capacity-200-01

# 自定义阶梯、持续时间和每秒提交数；其余场景仍照常执行。
node examples/capacity/run.mjs \
  --users 10,50,100,200 --duration 60 --rate 20 \
  --out .capix/capacity-custom-01
```

`--out` 必须是尚不存在的新目录，避免覆盖结果或复用旧数据库。`--users` 是严格递增的会话数列表，最高 500；持续负载总提交数受配置上限约束。模拟模型参数固定在 [plan.mjs](./plan.mjs)，本工具没有真实模型模式。

每个场景在新的 worker 进程中运行，场景之间串行；每个 worker 拥有自己的模拟上游进程。worker 未交付结果（如 OOM、超时或被终止）时停止后续负载；完整返回但未通过断言的场景保留失败结果，继续其余独立场景。任一失败均使套件非零退出。不要同时运行多个容量套件或单元测试后再将结果用于直接比较。

输出目录包含：

```text
environment.json                    # 机器、Node、实验配置和全部计划
summary.json                        # 已执行场景的汇总
report.md                           # 便于阅读的表格与解释范围
memory-burst-200/
  config.json
  result.json                       # 汇总、逐提交和逐模型请求指标
  worker.log
sqlite-burst-200/
  ...
  session-0.sqlite                  # 每会话独立实验库
  session-1.sqlite
```

根目录 `.capix/` 已被 Git 忽略。原始报告、数据库和分析产物留在本机，不作为源码提交；需要共享结论时应另写带配置与边界的摘要。

## 负载与装配

每个会话预置约 2 KiB 历史和一条私有记忆，View 纳入它们。提交携带会话、序号及请求标记；回答由标记和填充正文组成，用于核对最终回答与流式预览没有丢失或串入其他请求。

每个成功提交执行默认材料对话链：追加用户消息、纳入 View、准备材料、流式回答交互、接纳助手消息、记忆提案交互与维护。模拟记忆提案返回合法的 `{"changes":[]}`。回答目标时长 1000 ms、20 个片段、正文约 2 KiB；记忆提案目标时长 100 ms。这些是上游目标值，实际耗时另行记录。

四种 profile 使用相同业务结构：

| profile      | 内容及交互持久化     | CP   | 主动记录                   |
| ------------ | -------------------- | ---- | -------------------------- |
| `memory`     | 进程内               | 关闭 | 安装控制器，保持 idle      |
| `sqlite`     | 每会话一个 SQLite 库 | 关闭 | idle                       |
| `checkpoint` | 同上                 | 开启 | idle                       |
| `recording`  | 同上                 | 开启 | 开始采集并保留真实调用记录 |

各会话共享同一个模型 Provider，内容、View、结构、Runner、Interactions 和数据库分别持有。这个实验没有把本来不会共享的对话实体当作共享资源，也没有验证多会话竞争同一个 SQLite 写入者。CP 对照包含固定效果凭据、实体写入及镜像保存的变化，不能将差额全部解释成序列化成本。

默认计划有 10 个场景：

| 形态     | 提交方式                                                        | 要验证的内容                                                       |
| -------- | --------------------------------------------------------------- | ------------------------------------------------------------------ |
| `burst`  | 每个会话同时提交一次，整批结束后再做第二批                      | 真实重叠执行、规模增长、四种 profile 的差异                        |
| `steady` | 在最多 200 个会话中轮转，按固定计划每秒提交 20 次，持续 60 秒   | 调度延迟、接纳与拒绝、持续增长；不等待上一次完成后才安排下一次     |
| `churn`  | 同时提交一批；20% 在首个增量后取消调用，另 20% 解除一个显示订阅 | 局部取消与外部发送分离，解除消费不取消业务，退出后没有遗留在途活动 |

`steady` 中 busy 原样统计为拒绝，不排队或重试。`churn` 保留独立的测量订阅，以便显示订阅解除后仍能验证完整结果；它不是慢浏览器或传输背压测试。

## 测量与通过条件

| 指标                 | 口径                                                                                                       |
| -------------------- | ---------------------------------------------------------------------------------------------------------- |
| 提交、占用、上游并发 | 分别统计尚未返回的 `run`、真实 `entry.acquired/released`、模型客户端在途与上游实际收到的请求；不能互相替代 |
| 首增量、完成         | 从实际调用 `runner.run` 开始；另存计划到达时间、实际开始延迟和计划到完成时延                               |
| 吞吐                 | 成功提交数除以包含收尾的调用时间窗口；业务返回成功仍需通过独立正确性断言                                   |
| 外部收尾             | 本地调用结束后，继续等待每个 Interactions 的 `settled()` 并核对残留活动                                    |
| CPU、事件循环        | worker 的进程 CPU、事件循环利用率与延迟；单核完全占用记作 100%，并非整机 CPU 百分比                        |
| 内存                 | 50 ms 采样的 RSS/heap 峰值、进程 maxRSS、结束值及关闭后显式 GC 值；采样可能遗漏瞬时峰值                    |
| 模型传输             | 序列化请求字节、正文增量字节、请求耗时与失败数；上游独立统计 HTTP/SSE 字节和实际时序                       |
| 存储                 | 关闭后文件尺寸、表行数、CP 编码大小与原始 JSON 大小；不是累计磁盘写入流量                                  |
| 冷装配               | 单独测量建立会话、种子内容、资源、Runner 与可选数据库的成本，不混入提交耗时                                |

通过条件除了回答文本和预览一致，还包括：没有观测/输出消费者被隔离的故障、模型请求数正确且没有失败、上游实际收到并完成对应请求、消息与 View 数量正确、记录完整、退出后没有残留调用或外部发送。持久化 profile 关闭后重新加载内容并与内存状态对照，不执行恢复旧调用。

默认服务允许记忆提案失败后保留已接纳回答。因此 `run` 全部成功并不足以判定实验通过：只要出现模型请求失败，容量验证仍然失败。这样避免把可选业务分支降级掩盖成正常负载表现。

结果解释还需保留几个限制：上游与 worker 仍共享同一台机器；不能用客户端耗时直接减去预设模型延时作为精确框架成本；正文、交互反馈、CP 和记录有合法留存，短时内存曲线不能证明无泄漏。60 秒只是短样本；目前未覆盖公开服务 HTTP、认证、网络断连、多进程负载均衡、长期资源耗尽或供应商限流。

## 首次容量验证暴露的问题

2026-11-05，首次完整阶梯在 100 会话时 heap 峰值约 1987.5 MiB，200 会话时触及默认堆上限并退出。请求及正文数据量远小于这一分配规模，关闭后 GC 又显著回落，不能简单归因为正文或 CP 留存。

根因是每个 `InvocationChildren` 为接纳回调创建独立的 `AsyncLocalStorage`，而这些实例持续启用。在本次使用的 Node 22.23.2 中，新异步资源会遍历全部已启用 ALS，并为每个实例附加自己的 Symbol 属性，即使该实例在当前异步链中没有 store。历史调用越多，后续 Promise、计时器和网络资源的传播成本越高；这与 CPU 分析及 OOM 中对象属性字典扩容的表现一致。

修复在调用包内完成：机制共用一个 ALS，每个父调用持有独立 owner，每次接纳建立带子调用身份和 active 状态的局部帧；嵌套帧保留父链。查询只匹配本 owner 最近的帧，过期匹配不能回退借用更早接纳。业务的并发隔离、祖先接纳可见性和迟到回调拒绝语义保持不变，没有提高堆上限或削减测试负载。

### 第一次修复后结果：部分通过

以下只记录首次 ALS 修复后的那次运行，来源为本机 [capacity-200-fixed-20261105/report.md](../../.capix/capacity-200-fixed-20261105/report.md) 与各场景 `result.json`。环境为 Apple M3 Max、16 个逻辑核、64 GiB 内存、Node 22.23.2。原始目录不随 Git 分发；后续结果应另行注明实验目录和配置，不覆盖这次失败事实。

| 场景                 | 成功提交／计划提交 | 模型失败 | 完成 p95 ms | 首增量 p95 ms | heap 采样峰值 MiB | 判定                                   |
| -------------------- | ------------------ | -------- | ----------- | ------------- | ----------------- | -------------------------------------- |
| memory，10 会话      | 20/20              | 0        | 1180.5      | 97.2          | 35.4              | 通过                                   |
| memory，50 会话      | 100/100            | 0        | 1277.2      | 136.2         | 72.2              | 通过                                   |
| memory，100 会话     | 200/200            | 0        | 1367.4      | 187.3         | 159.7             | 通过                                   |
| memory，200 会话     | 400/400            | 0        | 1592.8      | 297.6         | 312.4             | 通过                                   |
| sqlite，200 会话     | 400/400            | 0        | 1751.7      | 351.8         | 325.9             | 通过                                   |
| checkpoint，200 会话 | 400/400            | 198      | 6875.7      | 1803.3        | 237.3             | **不通过，含降级，不作为正常容量结果** |

前五个场景均核对了对应的真实上游并发，200 会话场景确实达到 200 个在途上游请求；SQLite 组的 200 个库全部重载核对通过。

CP 场景虽然返回了 400 个回答，但 800 次模型客户端调用中有 198 次记忆请求以 `NETWORK` 失败，上游实际只收到并完成 602 次请求。默认维护策略接收了这些记忆提案失败，所以入口成功数不能证明完整链路正常。其耗时、存储和内存数据描述的是包含降级的失败运行，不能直接用于与前五组比较正常吞吐。

该次计划在 CP 场景后停止，共执行 6/10 个场景。recording、两组 steady 和 churn 在这次完整计划中尚未执行；不能声称四种 profile 或 60 秒持续负载全部通过。后续修复、复测结论与下一步另行补充。

### 完整复测：9/10 场景通过

同日完整复测保留在本机 [capacity-complete-20261105/report.md](../../.capix/capacity-complete-20261105/report.md)。配置与首次修后实验一致；完整交付但未通过的场景不再阻断其余独立场景。套件如实以非零状态结束，未提高堆限额、延长上游连接超时、关闭 CP 或加入请求重试。

| 负载                                     | 回答成功／提交              | 模型失败 | 完成 p95 | 事件循环 p99 | 结论                             |
| ---------------------------------------- | --------------------------- | -------- | -------- | ------------ | -------------------------------- |
| 200 会话突发，内存                       | 400/400                     | 0        | 1.514 s  | 92 ms        | 通过                             |
| 200 会话突发，SQLite                     | 400/400                     | 0        | 1.738 s  | 156 ms       | 通过，200 库重载一致             |
| 200 会话突发，SQLite + CP                | 400/400                     | 196      | 6.866 s  | 2500 ms      | **不通过，记忆请求发生降级**     |
| 200 会话突发，SQLite + CP + 记录         | 400/400                     | 0        | 9.474 s  | 2718 ms      | 正确性通过，阻塞和时延明显       |
| 200 会话轮转，20 次/s，60 s，内存        | 1200/1200                   | 0        | 1.119 s  | 17 ms        | 通过，峰值占用 28 个调用         |
| 200 会话轮转，20 次/s，60 s，SQLite + CP | 1200/1200                   | 0        | 1.468 s  | 101 ms       | 通过，峰值占用 42 个调用         |
| 200 会话扰动：取消 40、解除显示订阅 40   | 160/200，另 40 次按预期取消 | 0        | 1.485 s  | 25 ms        | 通过，独立交互均完成且无残留活动 |

10/50/100 会话的内存阶梯也全部通过。200 会话内存突发的 heap 采样峰值约 312.7 MiB、关闭后约 27.0 MiB，先前的 GB 级放大已消除。所有持久化组各 200 个库均重载核对通过；这不替代 CP 续接恢复测试。

CP 突发的失败在两次定向复现中也出现。离线 fetch 诊断确认底层为 `ECONNRESET`、signal 未取消，失败发生在模型请求到达上游之前。它与本地同步 CP 批次和长事件循环停顿共现；两种单连接阻塞探针未复现，因此尚不能断言是某一种 keep-alive 复用竞态。开启记录的更慢场景反而没有网络失败，也说明连接时序不能仅按总耗时判断。最终 196 次失败与首次 198 次略有差异，原始结果均保留。

持续 CP 组的进程 CPU 已达单核约 95.9%，所以“这一分钟完成 20 次/s”不等于已经有充分的增长余量。该组生成 50,400 份 CP 镜像，累计原始 JSON 约 930.4 MiB，编码后的镜像正文约 63.5 MiB，200 个库总计约 164.8 MiB；这些是保存的累计状态与文件大小，不是峰值内存或系统磁盘写入计数。

下一步应先分析 CP 的构建、复制/校验、压缩、SQLite 提交分别占用多少同步时间，并进一步定位上述连接故障。再根据成本决定优化位置；不能仅把整体写入改成后台任务而改变已接纳、持久提交与恢复依据的顺序。这轮没有修改这些契约，也没有建立多用户 HTTP 服务或调度平台。

### 后续 CP 调查

上述结果是第一次完整容量验证的历史记录。后续双端探针已确认那次复现的 198 个网络失败均复用了上游已经超时关闭的连接；内存 CP 对照也证明主要同步成本不全来自磁盘。完整成本分解、连接时序、诊断命令及候选优化边界见 [CP 容量问题调查](../../docs/checkpoint-capacity-investigation.md)。`diagnostics/` 只由显式 preload 或分析命令启用，普通容量套件不加载它们。
