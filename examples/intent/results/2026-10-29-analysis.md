# 意图识别实测：消息、记忆与 Skill

本次验证了现有实体 → View → 资源 → 决策 Node → 候选 Node 的完整路径。**25 次请求中 24 次符合预先设定的期望，1 次因缺少必要材料被契约拒绝。** 这是人工合成样本的一次对照，不能解释为通用意图识别准确率。

## 实验条件

- 时间：2026-10-29 01:19（Asia/Shanghai）；请求与返回的模型均为 `deepseek-flash`。
- `thinking=disabled`、`temperature=0`、输出上限 700 tokens；不重试、不改写模型结果。
- 14 个固定案例、25 个不同的模型请求，8 个候选，13 次实际候选子调用覆盖全部 8 个候选。
- 同一案例切换当前输入、消息、记忆、Skill 或完整材料。消息来自 Transcript；手工记忆通过 Memories 正式落实并引用来源消息；Skill 是示例的静态来源；三者通过 View 的成员选择确定可见范围。
- 模型只看到 `query/catalog/material`。case ID、条件名和期望答案只在评估侧，开跑前固定；未根据结果修改提示词或期望。
- 原始记录：[2026-10-29-deepseek.jsonl](2026-10-29-deepseek.jsonl)。每行保存材料、模型原始决定、验证结果、真实子调用计划、用量和延迟；首行保存实验参数、计划及 prompt/catalog 哈希，末行保存汇总。

## 关键对照

| 场景                 | 没有对应依据                                   | 提供依据之后                           |
| -------------------- | ---------------------------------------------- | -------------------------------------- |
| “照刚才那样处理”英文 | 澄清                                           | 消息说明刚才在翻译 → `translate`       |
| “按我的惯例处理”     | 无材料或只有无关近期消息均澄清                 | 记忆定义惯例 → `translate`             |
| 查询译文偏好         | 无材料或只有近期寒暄均澄清                     | 偏好记忆 → `recall_memory`             |
| 点名“简报”           | 澄清                                           | Skill 正文说明多步处理 → `apply_skill` |
| 总结刚才的决定       | **错误地选择 `summarize_history`，被契约拒绝** | 消息完整 → `summarize_history`         |
| 查找刚才的发布日期   | 澄清                                           | 对应消息 → `recall_history`            |

补充边界也符合本次期望：当前明确要求“只润色英文”时，旧翻译偏好没有覆盖它；只有饮食记忆时不会虚构译文偏好；只有“校对”Skill 时不会假装有“简报”；正文摘要、明确记住偏好、范围外的订票请求分别选择 `summarize_text`、`remember`、`unsupported`。

| 条件     | 数量 | 符合期望 | 被契约拒绝 |
| -------- | ---: | -------: | ---------: |
| 当前输入 |   12 |       11 |          1 |
| 加消息   |    5 |        5 |          0 |
| 加记忆   |    3 |        3 |          0 |
| 加 Skill |    1 |        1 |          0 |
| 全部来源 |    4 |        4 |          0 |

各行用的案例不同，不能把这些比例当作不同材料方案的排名。全程 Provider 错误与 Runtime 错误均为 0。Provider 报告输入 14,125 tokens、输出 1,313 tokens、合计 15,438 tokens；本地累计调用时间约 23.5 秒。测量不包含构建时间，不是性能基准。

## 值得分析的失败

输入是“请总结一下我们刚才讨论的决定。”，材料为空。模型输出合法 JSON，选择 `summarize_history`，简短理由中甚至明确提到材料为空，却认为目录支持这个操作就可以选择。

这里可以分清三件事：

1. **意图分类**：用户想总结历史，分类本身合理。
2. **执行资格**：本次没有历史材料，不能进入这个候选。
3. **推进策略**：示例约定材料不足先澄清，模型没有执行这条规则。

因此这不是“消息实体丢失历史”，也不是传输或格式解析失败。是模型没有同时满足意图与资格要求；本例的 `missing-material` 检查阻止了候选调用，但**没有自动转成澄清**，报告仍如实显示 contract-error。下一步若要改善体验，可在服务策略中把明确的缺材料原因转成澄清；暂时没有证据支持新增复杂的内核意图层或递归预检流程。

## 对当前架构的判断

现有资源与结构已经能承载这个实验，无需为意图识别修改内核。Provider 提供文本完成；模型解释当前输入与材料；目录描述候选；业务契约限制可接受决定；Group 按真实成员执行。消息、记忆和 Skill 的价值是提供不同来源的依据，它们本身没有新增“识别算法”。

目前最需要保持清楚的是：**选哪个能力、是否已有必要材料、如何形成执行输入是不同的问题。** 本实验只验证前两者的一小部分，候选都只返回动作计划。`apply_skill` 没有真实执行 Skill，`remember` 没有把新偏好写回，也没有验证自动提取记忆、检索、多轮澄清、文件副作用或 CP。

证据引用检查只能保证 ref 存在。比如“只润色”的正确选择仍引用了被当前要求覆盖的旧翻译记忆；它可能表示“考虑过这份材料”，不能直接解释成“该记忆证明了决定”。当前没有区分支持、冲突与排除关系，不应据此推导更强的审计保证。

本次材料少、意图边界由目录明确描述；没有比较其他模型、提示词或候选顺序，也没有多次采样。后续更有价值的小验证是扩充真实歧义和相互冲突的材料，并单独观察分类、资格与澄清，暂时不扩大框架实现。
