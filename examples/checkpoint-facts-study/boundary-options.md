# 第二轮：交付边界、数据形态与候选不变量

状态：2026-11-06。新增 11 项小场景，与第一轮合计 21 项；生产实现和现行契约未修改。

```sh
node --test examples/checkpoint-facts-study/scenarios.test.mjs examples/checkpoint-facts-study/boundaries.test.mjs
```

本轮从“复制时机”继续推进到两个不同问题：**业务消费哪一种内容，以及这份内容何时取得所有权、何时正式成立。** 用真实 Runner、接纳、资源访问验证部分接缝，其余仍是独立可执行伪代码，不冒充完整恢复矩阵。

## 1. 一个不可兼得的组合

下面四项不能同时保证：

1. 任意 JS 原对象的身份保持不变。
2. 原对象及既有别名仍可以修改。
3. 所有消费者读到的交付内容始终固定。
4. 不再遍历检测旧正文。

因此需要改变交付契约，不能靠缓存或类型断言同时保留四项。`Readonly<T>` 不消除别名，也不会移除 Date/Map 的修改方法。

## 2. 三种可能的业务消费形态

| 候选                   | 什么是正式依据                                  | 业务读取方式                             | 收益                                   | 代价/边界                                                     |
| ---------------------- | ----------------------------------------------- | ---------------------------------------- | -------------------------------------- | ------------------------------------------------------------- |
| 固定值交付             | 交付内容本身固定                                | work.input、返回、facts 使用同一逻辑内容 | 心智最直接；适合跨调用共享、记录和恢复 | 未知值隔离会改变引用身份；不能无条件支持任意 JS 对象          |
| 固定依据与工作副本分开 | 固定表示 S 是唯一依据                           | 作者另取可变草稿 T                       | 可继续使用 Date、可变类等工作形态      | 草稿不能仍冒充固定 input/facts；取得副本可能重复付出 O(大小)  |
| 显式固定/借用          | fixed 是内容，borrowed 是受生命周期约束的活能力 | 类型和访问方式分别表达                   | 给需要传递活能力的业务留空间           | 增加作者概念；借用没有历史内容保证，CP 不得靠 ID 自动恢复能力 |

当前优先探索第一种，并允许业务显式创建局部草稿。第二种不应被透明藏进同一个 `Work<Input>` 类型；第三种暂作挑战候选，不急于给每个节点增加模式开关。资源体系已经承接很多活能力，应先证明有哪些实际场景必须通过 IO 传递它们。

“固定值”不等于“全仓强制 JSON”。本实验只实现普通 JSON 数据作为受限样本；生产是否支持更多标量、二进制、集合或可信不可变类尚未决定。类型必须诚实：Date 转成 epoch/ISO 后，就不能继续宣称它仍是 Date。

### 富对象反例与可行形态

- `Object.freeze(new Date(...))` 仍可 `setUTCFullYear`；冻结 Map 仍可 set。
- `structuredClone` 不保留自定义类的原型方法，不能无声替换 `T`。
- 一个自行持有私有时间数值、只提供读取方法的 Instant 类可以设计为不可变；但冻结一个方法读取外部 Date 的 wrapper 并不能固定内容。
- 固定 `{epochMs}`，再由业务创建 `new Date(epochMs)` 作为草稿是可行的；草稿变化不改写事实，但草稿不能被称为固定输入。

这是类型实现/访问语义的区别，不是检查 `Object.isFrozen` 能解决的问题。

## 3. 固定候选与正式成立是两个时刻

第一轮“在返回时固定”还不够精确。真实执行包含等待和可能失败的关闭阶段。

```text
内核取得正文候选值
  → 固定候选内容
  → 原有输出封口、等待接纳、Work 关闭、输出检查
  → 等待子退出、完成观察、资源关闭、必要的 CP.finish
  → 对父层正式交付 returned
```

固定候选不提前宣称成功。关闭或必要保存失败时，候选内容可以仍然稳定，但正式交付必须是失败。也不能直到所有等待结束才复制：原对象可能已经在等待期间改变。

本轮 `deliverySketch` 对照证明：等待前固定保留收到的值；等待后固定会纳入等待期间的别名变化；关闭失败不能产生成功交付。它不改变/验证整套 Invocation 的取消和观察排序。

### 输入也有候选与建立的区别

```text
公开入口接收输入
  → 固定输入候选
  → 宿主检查、资源捕获、范围解算
  → 安装调用身份与输入依据
```

当前根入口在 `scope.prepare` 前还有 Runner requested/acquired 观察以及 calls.begin 的宿主回调。如果要承诺“进入即固定”，不能只在 Context 构造或 prepare 前补一次复制；必须明确公开入口的固定边界。纯 busy/cancel 检查可以在固定前完成，不能让已取得调用的阶段使用不同内容。

本轮真实 Runner 对照：宿主 capture 读出 first.txt 后修改调用方原别名，现行执行会读到 second.txt。两者甚至是同一个对象。宿主先隔离输入再 `runner.run` 后，capture/执行都得到 first.txt。**这验证候选的放置方向，不代表内核已经安装此策略，也没有覆盖所有入口观察回调。**

### `return` 的词法位置不是可承诺的通用边界

```js
function produce() {
  queueMicrotask(() => {
    raw.value = 2;
  });
  return raw; // 此行时还是 1。
}
const received = await produce(); // 此时可以已经是 2。
```

同步和异步 producer 经本实验的 await 接收路径都能复现。候选承诺应是：**内核取得值后，在再次调用作者代码或让出前固定。** 同步快路径可以另选时机，但不能解决异步 producer 内部所有别名问题。

作者确实需要更早含义时，可以先产生可信固定值再返回；本轮也验证这会保留 1。不能声称内核能追溯捕获任意函数内部 return 表达式那一瞬间。

### 接纳成立前后的失败分别处理

```text
调用接纳回调（可能已落实实体效果）
  → 取得并固定接纳候选
  → 只读契约检查
  → 安装 accepted/handled
  → 发布观察
```

固定/检查失败不能撤销回调已经产生的实体效果，也不能自动再调用 failed 或重做接纳。安装接纳后观察失败，不能把既有接纳改回未成立。需要规范化时，应有明确的数据转换，不把修改藏在只读 check 中。

本轮进入真实 `relation.accept`，回调先增加 effects 计数，再由 check 拒绝超出纯数据范围的 Date：effects 保持 1，子 returned 成功，父 reception 失败。它只验证接纳控制边界，不是数据库事务或持久回执不确定的验证。

## 4. 候选不变量

| 规则                   | 可检查的含义                                                     | 当前证据/未决内容                                    |
| ---------------------- | ---------------------------------------------------------------- | ---------------------------------------------------- |
| 输入依据一致           | 资源捕获、范围解算和执行消费同一固定内容                         | 真实 Runner 宿主前置隔离验证；内核边界待定           |
| 已取得内容不被别名改写 | 后续修改原对象不改变候选/正式内容                                | 第一轮与本轮等待窗口反例                             |
| 内容固定不等于成功     | 失败的关闭/检查不能形成成功交付                                  | 时序模型通过；真实机制迁移未做                       |
| 逻辑归属独立于内容共享 | 多次调用可共享相同内容，每次仍有自己的身份、顺序、归属           | 保留现有规则；不能用内容 digest 合并两个调用         |
| 接纳不改写返回         | 父层转换产生自己的值，不修改孩子的交付                           | 第一轮 O1/A1 隔离验证                                |
| 推进只产生下一版本     | 新状态不得修改之前保存的 state/refs                              | 第一轮 CP1/CP2 对照；不等于更新成本已增量化          |
| CP 开关不改变数据形态  | 固定/借用不能由是否安装 CP 隐式切换                              | 候选纯数据路径通过；允许 CP 引入真实持久失败         |
| 持久表示按契约区分     | 同一固定值使用不同 codec，不能复用错误表示                       | 本轮两个确定性 codec 反例；跨进程身份/同版本漂移另论 |
| 恢复保留数据含义       | 解码结果在契约规定的数据含义上与正式交付等价                     | 第一轮 trim 反例；尚未制定通用等价性契约             |
| 能力访问仍受窗口约束   | 固定 locator/读取结果不赋予访问权限，不复活旧端点                | 真实资源窗口关闭后拒绝访问                           |
| 固定性证据有明确权威   | 不信任任意 frozen、品牌断言或业务 `isFixed()`                    | 本地证据已演示；跨包签发和共享尚未设计               |
| 固定、保存、可恢复分开 | 有固定值不代表已落盘；有编号不代表正文可读；有正文不代表允许恢复 | 第一轮缺正文/失败反例；完整宿主恢复未迁移            |

普通业务错误与受保护故障的归属保持独立。稳定失败诊断不能替换原 Error 的传播身份；正文候选失败、关闭合成失败与对父最终失败也不是同一个时刻。

## 5. 哪些计算可以复用，哪些仍需发生

```text
新交付内容：隔离/固定一次
新消费契约：检查它实际要求的内容
首次持久化：按对应固定 codec 形成表示
同事实同 codec 再保存：复用既有表示
新进程读回：重新核验持久材料、契约和关系
```

至少按“固定内容 + 准确编码契约”区分表示，不能只按对象身份缓存。例如一个 codec 编码为数字 7，另一个编码为字符串 "7"。本轮仅验证复用键需要区分契约；没有证明任意有状态 codec 可缓存，也没有统一跨进程的契约身份。

未知对象首次固定仍有与大小相关的成本。可信固定内容继续传递可以复用，但信任必须由实际持有内容的实现建立；contracts 放一个类型不构成运行期证明。不同事实可以共享正文，但各自的父子身份及接纳归属不能共享冒充。

旧 refs、完整业务 state、完整 Frame 序列化以及集合成员数组仍可能是 O(历史)。本轮没有通过新格式消除它们，不能用“固定值”宣称长任务成本已经解决。

## 6. 本轮结果与下一道设计门槛

`boundaries.test.mjs` 的 11 项检查全部通过：

- 真实 Runner 前置输入固定对照。
- 等待前/后固定、关闭失败不交付成功。
- await 取得值的时机与 producer 提前固定。
- 真实接纳检查失败保留既有效果。
- Date/Map/类反例、显式工作草稿、可信不可变类型与活视图对照。
- 真实资源端点关闭后拒绝访问。
- 编码表示按契约区分。

建议继续围绕第一种消费形态收敛：**业务正式读取固定值，局部可变计算显式产生草稿，活能力通过资源窗口访问。** 不立即增加统一借用模式、不规定全仓只能 JSON、不创建新的事实平台。

下一步需要确定的不是 Frame v6，而是一个最小值交付契约：默认支持哪些值，未知值如何取得所有权，可信实体值如何跨包复用，业务检查与规范化如何分开。再把它放进输入、返回和接纳三处真实边界，以相同输入/结果覆盖正常、失败、取消和恢复。现行原引用契约在此之前不改。
