# 多主题长对话验证

这是新对话装配服务的持续使用实验：**54 次用户提交**，支持只运行前 **24 / 36 / 54** 次。一条提交包含正常回答及回答后的记忆维护，最多分别产生 **48 / 72 / 108** 次模型请求。“次数”仅是样本顺序，不给内核增加轮次实体。

完整人工材料见 [scenario.md](scenario.md)，可执行数据见 [scenario.mjs](scenario.mjs)。多个虚构主题交错推进，覆盖事实更正、计划撤销、同名对象、局部偏好与全局偏好、假设与承诺、长间隔回访、缺失依据和跨主题综合。内容不依赖实时搜索，也不要求服务真的订票、发消息或读写外部文件。

## 使用

先构建，再在**全新目录**运行；数据库、报告都与日常对话分开：

```sh
pnpm build
node examples/long-conversation/run.mjs --turns 54 --out .capix/studies/long-offline-01
```

默认使用固定 ModelProvider 替身。回答是明确的占位文本，记忆提案按人工脚本创建和更新，用来验证真实实体、资源、结构、交互、记录与 CP 的完整增长链路。**离线通过不能解释为模型通过了 54 题**，其输入规模与耗时也不能代替真实模型数据。

实际模型运行必须显式 `--live`：

```sh
node --env-file=.env examples/long-conversation/run.mjs --live --turns 24 --out .capix/studies/long-live-24-01
# 从空白对话完整运行 54 次，使用另一个新目录：
node --env-file=.env examples/long-conversation/run.mjs --live --turns 54 --out .capix/studies/long-live-54-01
```

凭据仅由宿主环境提供（`DEEPSEEK_API_KEY`、可选 `DEEPSEEK_MODEL`）；脚本本身不读取 `.env`。保持服务当前的模型请求配置，正文流式、提取非流式；每个请求最多等待 45 秒，不重试。Provider 故障或正式调用失败后停止，不在失败后继续消耗后续样本；已被业务接收的提案校验异常仍记录为 handled，并允许后续提交推进。

已有目录会被拒绝，不复用日常数据库或覆盖结果。24 次和 54 次命令各自独立起跑；没有隐含的“从上次报告接着发”，也不自动重发未知请求。所有结果文件权限为 0600，目录为 0700；报告只含人工材料和实际业务输出，不保存请求头或凭据。

## 装配与测量边界

复用 `@capix/conversation-service/assembly` 的默认材料 Scene、资源登记、内容载入与独立 Interactions，启用 SQLite CP 和模型交互持久化，并安装普通记录预设。没有替换默认 View 成员策略、记忆提取范围或恢复资格。

模型只接收 `turn.input` 经服务形成的正式请求。`expectations` 是评估材料；`memoryUpdates` 只用于离线替身。两者都不会作为额外提示注入真实请求。真实模型提取出的记忆自然参与后续回答；只凭最终回答正确不能区分它使用了消息还是记忆，当前默认 View 同时保留两者，本实验不声称完成了记忆消融对照。

每次提交记录：

- 回答与提取分别的 ModelRequest JSON 字节、prompt 文本字节、来源项数量、返回 usage；live 额外记录实际 HTTP 请求正文大小。字节不是 token，HTTP 正文不是含头部和压缩的全量网络传输。
- 首片段、请求完成和本次调用耗时；预览字节、提案 accepted/handled、正式消息与记忆变化。
- 成功保存的 CP image 数量、原 JSON 总字节/最大值及持久端口耗时；`finish` 的交付值另计。压缩之后仍保留这个口径，不把序列化材料变小等同于构造与校验计算消失。
- DB/WAL/SHM 当时文件大小、当前装配 RecordBook 大小。记录在重新装配后重新开始；测量本身的快照与报告耗时单独记录。运行耗时包含同步 CP 计量和请求日志开销，不用来宣称无插桩性能。

第 24、36、54 次完成后，关闭宿主并只读统计原 CP JSON、实际存储正文、最大 image 和数据库页占用。测量兼容 v2 原文存储与 v3 压缩存储：`images.bytes/maxBytes`、`heads.deliveryBytes/maxDeliveryBytes` 保留原 JSON 口径；`images.storedBytes/maxStoredBytes`、`heads.storedDeliveryBytes/maxStoredDeliveryBytes` 统计实际 TEXT 内容，包含压缩 Base64 与 envelope。v3 原大小来自检查过编码、字段和范围的 `jsonBytes` 元数据，测量不解压认证载荷，完整性校验仍由服务存储读取负责。`checkpoints.originalBytesSource` 标明原大小来源。

这些统计都不是 SQLite 累计物理写入量；存储正文不含索引、页开销，压缩迁移释放的页也可能仍留在 DB 文件中。继续阶段重新载入全部正式内容，比较包括固定凭据在内的完整状态，并确认重载没有发送模型请求。**这验证正常重载；真实进程中断与 CP 续接由已有恢复专项测试负责。** 本实验不改变 CP image 保留策略。

## Token 消耗口径

live 模式使用提供者实际返回的 `usage.promptTokens/completionTokens`，按回答和记忆提取分别累计，报告合计 input/output/total 及记忆维护占已报告 token 的比例；同时标明 usage 覆盖请求数。包含失败、输出截断和提案被跳过的尝试，未返回 usage 的请求标为未知，不能当作零消耗。此处不按缓存或输入/输出单价折算金额，也不从 JSON 字节估算 token。

提供者的可选 `promptCacheHitTokens/promptCacheMissTokens` 原样保留到事件和交互反馈；报告只对同时提供两项的请求汇总，列出覆盖数和覆盖部分的命中率。单侧报告仍保留原始值，不补齐另一项。旧实验缺少计数保持未知，不能从历史文本重复推断实际命中。缓存不减少原始 token 数，此处也不估算账单。

“完成提交”只是运行交付，不是“正确解决任务”。若要比较每个成功任务的消耗，需先固定任务集、模型与配置，确定语义成功标准，把失败尝试也计入总消耗，再与同模型同任务的基线比较；本实验尚未建立该对照，不把全部模型 token 归为内核额外开销。当前完整历史会反复进入回答和提取请求，累计 token 也不是独立信息量；记忆策略和模型执行能力需分别评估。

## 结果

每个运行目录包含：

| 文件                         | 用途                                                        |
| ---------------------------- | ----------------------------------------------------------- |
| `conversation.sqlite`        | 这次实验的正式内容、完整交互及 CP                           |
| `scenario.json`              | 本次准确人工场景；summary 同时保存场景 SHA-256 与 Node 版本 |
| `events.jsonl`               | 每次真实请求/反馈、提交指标、记忆快照、检查点统计           |
| `content-24.json` 等         | 检查点完整正式内容及固定凭据                                |
| `summary.json` / `report.md` | 完成状态及可比较的增长指标                                  |
| `review.md`                  | 原题、实际回答、来源编号与人工评估依据                      |

人工评估逐题标记通过 / 部分 / 失败 / 无法判断；重点看纠正是否覆盖旧事实、假设是否被当成决定、同名是否串线、缺依据是否编造。再结合每次正式记忆快照，分析是提取错误、材料不充分还是回答误用。不会仅以关键词命中或模型自评宣称正确率。

24/36/54 的数字只是阶段性样本，不足以证明框架普遍性能；先依据报告找增长来源，再决定是否需要可替换的 View/提取策略或持久层优化。
