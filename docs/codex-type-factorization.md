## 1. 本轮先回答什么

前一版从“当前规则已经成立”出发，讨论怎样用更少的重复类型表达它们。这一前提需要撤回。用户这次提出的议题更早一层：**这些规则解释的是哪些真实区别，它们的划分和归属是否合适？**

例如，当前只有 E 带 entry。可以据此描述源码，也可以据此设计兼容的类型；但不能据此证明入口接纳本质上只属于 E。反过来，把 entry 移走后类型更简单，也不能证明新的职责划分更正确。

本轮采用以下推导次序：

```text
真实场景与需要区分的事实
  → 当前实现及当时选择的理由
  → 候选维度、取值与相互约束
  → 能解释的场景、反例与替代划分
  → 经讨论暂定的规则和职责
  → 类型表达及无法静态证明的部分
  → 对照实现，判断保留、修正或暂缓
```

“维度”在这里是帮助解释问题的分析工具，不预设它们彼此正交、能够任意组合，或者每个维度都需要一个模块。也不先认定九个分组足以覆盖整个 Agent 框架。目标是形成足以判断当前疑点的模型，不要求先穷尽所有未来能力。

## 2. 证据与结论的层次

| 层次         | 本文如何使用                                                            | 不能替代什么                                 |
| ------------ | ----------------------------------------------------------------------- | -------------------------------------------- |
| 当前事实     | 源码、真实时序、类型复现、测试与测量；标明基线和限制                    | 不能仅凭“已经这样实现”证明应该如此           |
| 历史选择     | 说明当时解决的问题、取舍和兼容成本；例如 REOA 层级、阶段 Work、有限恢复 | 不能自动成为本轮的前提                       |
| 候选基石     | 暂用来解释现象的维度与规则，列出支持场景、反例和替代方式                | 不能把候选的禁止项直接变成验收失败项         |
| 本轮暂定结论 | 经场景和反例比较，记录采用理由、适用范围、剩余不确定性                  | 不能声称已获类型或运行验证；两者仍需后续证明 |

首个讨论议题的概念结论已写入 §12；其范围以外仍按候选处理。像“子返回不等于父接纳”“实体不由 R 统一拥有”这类已有大量场景支持的区分，可以作为较强的候选基石；仍需说明它解释了什么，不能只引用现行约定作为理由。概念收敛不替代类型、迁移与运行验证。

需要分别记下两件事：**希望继续保证的行为**，以及**当前承载这个行为的对象组织方式**。保留行为未必要求保留原归属；改变归属也不证明行为自动保持。若讨论得出行为本身应调整，应明确受影响场景及代价，而不是隐藏在“类型优化”中。

| G07 时序与外部协作       | Interaction 独立保存请求／反馈；局部等待超时、取消请求、实际终止并不等价                 | 外部交互与内部调用如何关联而不锁成同一生命周期？这一差异是否能解释 C/S 跟随及外部 A，哪些仅是相似而非同一契约？        |
| G08 事实、观测与交付解释 | 生产者事实、可选观测、记录载体、服务投影、网络反馈、UI 具有不同失效边界                  | 各出口负责保证什么？必要捕获与可选观察是否划分准确？“事实”是否被用来泛称所有返回值或存储数据？                         |
| G09 留存、续接与同步     | 内容恢复、交互反馈读取、CP 有限续接、客户端 follow 是不同承诺                            | 应按保存对象、继续位置、权威来源还是时间范围划分？哪些区分不可省略，哪些只是实现形式？                                 |

分组间也有待检验的关系。例如：

- 当前子能力种类受 level 约束，因此不能先称能力与位置完全正交；是否保留这项约束，要有场景理由。
- 阶段、轮次与恢复活动来源描述不同问题；把它们放进一个枚举，可能隐藏组合约束，但拆开也不意味着每种组合都合法。
- 资源的寿命限制与调用的阶段动作都限制使用，但不因此自动成为同一个“权限系统”。
- 调用交付、父层接纳和 C/S 反馈不能仅因都称为“返回”就合并；独立实体与跨提交交互也不必都找到一个 REOA 所有者。

一个候选维度值得保留，需要能说明它改变了什么判断：同一其他条件下，改变它会导致什么行为差异、允许／拒绝条件或验证责任。若它没有独立解释力，只是字段换名，应并回更合适的概念。相互依赖本身不否定维度，但依赖要显式表达。

## 5. 首个样本：entry 是类型特化，还是职责划分尚未解释清楚

### 5.1 当前真实链路

源码定位：`server/runtime/src/structure/execution.ts`、`definition/entry.ts`、`definition/invocation.ts`、`invocation/builders/execution.ts`；服务样本：`services/observer/src/conversation/execution.ts` 与 `conversation/binding/source.ts`。

以下描述当前行为，不是新设计：

```text
R 调用已经活动
  → BoundExecution.create 收到入口输入
  → binding 建立入口资源窗口（挂接已有 R 调用）
  → E 声明的 entry.accept
  → accepted 同步回调（若安装）
  → 未取消时 entry.admit（若声明）
  → 关闭入口资源窗口
  → 检查父调用仍可活动
  → binding.capture 固定 E 使用的资源
  → ExecutionInvocationBuilder 创建 E Context／Invocation
  → started 建立回调与后续调用进展
  → E 正常执行
```

Observer 的 `entry.accept` 不只改写输入类型：它通过 `acceptConversationRequest` 校验并正式追加用户消息；`entry.admit` 准备原文分段。`ConversationCallSource` 提供入口资源、配置与捕获来源，capture 固定原文范围等依据，started 关联真实 R/E 身份。同步建立回调与被动进展订阅有不同失败语义。

入口失败时 E 可能尚不存在；入口资源和事件目前依附已有 R。输入正式追加后发生取消，消息仍保留，后续 admit／E 创建可被阻止。E 恢复路径跳过 accept／admit，使用保存的输入再 capture。这些是新解释需要逐项审视的事实边界，不能在重排对象时无声改变。

没有 entry 时，当前实现将输入直接视作内部 Input。这里仍需核对 EntryInput 与 Input 的静态约束是否足够；实现中的强转本身不证明两者可以不同而仍安全运行。

### 5.2 当前存在两种不同的“入口”

| 对比         | E 的 entry                                                     | InvocationEntry／defineChildEntry                                |
| ------------ | -------------------------------------------------------------- | ---------------------------------------------------------------- |
| 当前作用     | 接纳入口输入，可使用入口资源并执行 admit；capture 另由绑定承担 | 为已声明子能力提供另一种输入契约，将输入转换为目标所需的入口输入 |
| 处理依据     | 入口输入与专门供应的资源                                       | 输入、父层只读事实（round／continuation／children）、key         |
| 生命周期处理 | BoundExecution 安排独立资源窗口和 E 建立前的顺序               | 转换自身不声明独立的资源／admit／capture 窗口                    |
| 可否串联     | 接收转换后的 E 入口输入，再得到 E 内部 Input                   | 可以指向 E，先转换，再进入 E 的 entry 流程                       |

这使输入路径可能是：

```text
替代输入 → InvocationEntry → E 的 EntryInput → E.entry → 内部 Input
```

相似的函数签名不足以证明应该合并；名称不同也不足以证明必须分开。讨论要判断它们共同承担什么、额外承担什么，而不是先统一名字或类型。

### 5.3 为什么它影响类型讨论

当前 EntryInput 出现在公共 InvocationDefinition 的签名见证中，用于区分入口输入与内部 Input；E 的 EntryInput／EntryResources 还沿 Definition、Binding、Bound 和 source 契约传播。ExecutionInvocationBuilder 已只接收接纳后的 Input，没有继续携带 EntryInput。

因此，类型需要追踪的关联不只由 I/O 决定，还与“在哪里完成输入建立”有关。应检查关联是否止于正确边界，而不先把 EntryInput 从所有公共类型删除，或为求统一把它推广给全部层级。当前传播路径是证据，尚不足以证明它是编译热点。

### 5.4 最初比较的三种解释（讨论历史）

以下保留最初的问题与取舍。P02 现已选择职责拆分方向，具体边界见 §12；本表不再表示三种方案同时待选。

| 候选解释                                       | 需要成立的理由                                                             | 最应挑战的反例或代价                                                              |
| ---------------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 保留 E 专属进入边界                            | E 的职责确实包含一种其他层不承担的任务建立；接纳与资源窗口组合具有稳定意义 | 非对话 E 是否仍需要？O 的输入准备与此有何本质区别？不能只以当前层级定义自证       |
| 将进入边界理解为调用构造能力，按位置或装配安装 | 相同生命周期问题会在多个位置真实出现，且能共用事实归属、失败和资源窗口规则 | 是否给所有调用引入无实际需要的阶段？进入前还没有目标 Context 时谁负责？           |
| 将输入适配、宿主接纳政策和内核运行建立分开     | 当前 entry 混合了不同决策责任，拆分能保持事实且减少特例                    | 是否把原有正确顺序推给每个业务作者自行保证？是否让 R 或宿主重新承担更多隐式业务？ |

当时先比较职责和可保证的行为，再决定是否需要新对象；本轮结论仍不设计通用 EntryManager 或入口平台。

| S04  | 两种不同入口输入到同一内部 Input；另一个 E 完全不需要入口副作用 | 什么可以共享，什么属于目标或宿主；无 entry 的类型条件是什么？                 |
| S05  | O 在调用子层前需要输入适配或准备资源                            | 与 E entry 是同一机制、部分相同还是只名称相似？差异来自位置还是职责？         |
| S06  | 已保存 E 输入后恢复，原消息已经落实                             | 如何避免重演正式接纳，同时重建必要运行资源？是否依赖 E 专属性？               |
| S07  | 同声明同 key 多次调用；并行两个子调用后逐一接纳                 | 身份、顺序、返回和接纳如何区分；会不会把多关系压成 latest？                   |
| S08  | 异常处理阶段读取旧交付，接纳成功结果，另行启动或恢复子工作      | 历史知识、接纳动作和行动资格各需要哪些依据？                                  |
| S09  | 外部反馈已到但本次等待已结束；新 A 读取同一交互                 | 交互、调用与反馈保存为什么需要不同寿命？                                      |
| S10  | 子成功返回，父尚未接纳；父接纳过程中实体已落实，后续通知失败    | 哪些是既成事实、哪些未完成；观测和 CP 分别解释、保存什么？                    |
| S11  | 无 Recorder 运行；增量预览后正式结果不同；客户端反馈断开        | 运行、观察、内容落实及传输各自的承诺是否仍能解释？                            |
| S12  | 非对话任务：读取多个文件，组合子能力处理，再合并写出            | 不借用消息／记忆／QA 语义，候选规则是否仍成立；允许哪些位置组合需要明确论证？ |

优先走 S01–S06，暴露 entry 的归属与寿命问题，再用 S07–S12 检查候选解释是否误把当前对话形状当成通用结构。对于未实现的变体，只做伪代码或契约推演，不默认建立新能力。

### 8.2 当前阶段规则作为讨论样本

目前 run 省略 uses 代表全部注册子声明；exceptions／resume 省略 uses 代表无新子调用能力，显式空数组为空集。类型上限、实际注册对象身份和阶段资格是不同检查。

refs 可以保存 resume uses 之外的历史关系。facts 不要求启动资格；open(ref) 签发当前阶段句柄，不只是纯读；合法窗口内的 accept 可以落实实体而不启动子工作。真正启动／恢复有 uses 检查。CP 已保存成功交付的读取与普通活 Invocation 再次 run 也不等价。

这些区别值得保留在场景推演中。若提出合并，需说明谁接替相应保证；不能因新 API 更短而略过。同时，它们不是不能挑战的最终阶段划分。

## 9. 何时才值得进入实施

P02 已完成概念收敛，但本轮仍停留在文档与讨论，不启动类型迁移、目录调整或批量接口改写。原批次 0–3 不再是待执行计划；P02 的具体实施门槛见 §12.11。

进入下一轮实施前，至少需要针对选定范围形成以下材料：

1. **明确问题。** 是行为错误、职责含混、类型表达不一致，还是实测成本问题；避免把所有不规则都当成重构理由。
2. **暂定的维度与规则。** 说明当前选择中保留什么、修正什么、哪些仍待定，以及后者是否影响本次改动。
3. **一条完整解释链。** 至少走通 entry 的建立／失败／取消／恢复，以及一条子返回→父接纳→实体落实链；不能只画成功对象图。
4. **反例与替代比较。** 含非对话样本、没有可选能力的路径及多子关系；说明为何不采用另一种归属，而不只展示选定写法可以工作。
5. **实现与验证边界。** 类型证明止于哪里，运行期谁负责；哪些行为和格式保持，哪些需要显式调整；再制定小范围实施顺序。

不要求先回答所有未来问题。若最终只有局部类型缺口需要修正，就只做局部修正；若现有归属能给出充分解释，可以保留现状。讨论结果也可能是暂缓，而不是必然启动一次架构改造。

前置准备时提出的交叉审查问题如下，保留用于回查；P02 本轮审查入口已更新为 §12.12：

- 哪些“维度”仍只是现有对象或文件的另一个名字？是否漏掉了能解释 entry 特化的区分？
- 哪些规则正在用当前实现、AGENTS 或既有方案循环证明自己？
- entry 三种解释分别在哪个场景更自然，在哪个失败路径需要额外特例？
- 候选模型是否把作者的业务决定与内核的机制保证区分清楚，又是否把实际需要的业务能力删掉了？
- 哪些问题已可局部下结论，哪些必须等待更早的议题；现有工程证据对这些判断究竟有多强？

类型伪代码、模块位置和性能比较排在这些问题之后。当前没有必要仅为了完成原类型整理计划继续推进实现。

## 10. 保留的工程证据：职责、依赖与编译成本

本节保留 2026-10-18 已收集的工程证据，对应候选 F09。它帮助发现当前划分的成本和接缝，不证明任何一个维度或职责归属已经成立。下列调整方向均待前置讨论，不构成本轮实施清单；本次文档修订未重新运行编译测量。

### 10.1 分开判断三种成本

| 成本                 | 需要检查什么                                                    | 不能据此直接得出的结论                                     |
| -------------------- | --------------------------------------------------------------- | ---------------------------------------------------------- |
| 职责与阅读成本       | 一个规则是否放在其所属能力；消费者是否为局部事实理解整个实现    | 文件少、类型少就更清楚                                     |
| 模块加载与声明可达面 | import/export 链、公开入口、源码与 d.ts、type-only 与运行值依赖 | 多次导入同文件就会多次完整编译；类型环就是运行期循环初始化 |
| 类型推导与关系检查   | 条件分发、递归泛型、交叉/映射、具体声明树的传播、结构可赋值比较 | 移动文件就减少实例化；任何 Pick 或类型环都是性能热点       |

同一 TypeScript Program 中模块会被复用，不按 import 次数逐次完整检查。`import type` 消除了相应运行值依赖，但保留类型解析需求。当前 runtime 的 tsconfig 包含全部 src，单纯移动文件或改成局部导入，不会自动减少这个项目的源码检查范围。消费者项目则还受公开 d.ts 可达面和实际实例化影响。

因此，目录放置不合理可以是真实的职责问题；只有它进一步造成不必要的类型关联、展开或公开依赖时，才构成需要测量的编译成本问题。

### 10.2 已核实的依赖与候选调整

下表右栏沿用前一版的局部改善设想，其中“保留”指以当前行为为目标时的约束，不使相应机制免于前置讨论。若概念结论改变了行为，应先修订该栏，不能绕过讨论照表实施。

| 能力/职责                      | 已核实的现状                                                                                                                      | 待检验的方向                                                                                                             |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 声明层级与资源推导             | 通用 ChildLevel / ChildrenOf / ResourceRequests / ResourcesOf 在 definition/checkpoint.ts，普通工厂必须从 CP 文件取得这些类型     | 先判断通用层级/资源推导与 CP 的关系，再确定归属；不预先承诺提速                                                          |
| 子声明与阶段 Work              | ChildDefinition 包含完整 E/O/A；各类通过 InvocationDefinition 的 run/checkpoint 回到 Work，再通过 ChildCalls 回到 ChildDefinition | 核对必要 I/O、位置、身份关联，以及已有签名提取是否仍适合；避免仅为局部提取而无理由地展开完整树                           |
| CP 保存端口与恢复声明          | Work 依赖 AuthorCheckpointWriter；同一 CP 声明文件中的 point.resume 又依赖 ResumeWork                                             | 分清 writer/owner/slot 等消费端契约与完整 point/resume 声明；仅在实际依赖变窄时拆分，不以文件分拆数验收                  |

| 观测安装与单次观测             | observation/invocation.ts 以 ObservationInstallation 作为匹配键，而该类型来自同时执行装配的 binding/observation.ts                | 核对是否只需已有安装契约；如抽出契约，应继续保持安装对象身份及父子观察关联，不新增观测管理实体                           |
| 编排 helper 与绑定收集         | Sequence.requests 借用 binding/resources.ts 的 collectDefinitionRequirements；该收集器同时有观测供给和 CP 阶段语义                | 先厘清 requests 的实际承诺和使用者；纯声明分析可归声明侧，供给匹配仍归 binding。不能复制一份收集逻辑或顺手改变收集范围   |
| 资源、异常、输出、变化及其辅助 | 已有 ResourceOffer、exception/contract、output/contract、changes 等能力归属，跨 REOA 复用                                         | 按每个 helper 的实际操作审查，不因为某层调用它就迁入该层；不存在问题的现有窄契约保持                                     |

| 根公开出口                     | index.ts 还再导出 construction/recording/content；内部未发现反向从自身包入口或根 index 导入                                       | 公开可达面作为观测项，不因导出多就拆包、移除现有出口或判定编译慢                                                         |

其中声明类型的真实回链可以概括为：

```text
ChildDefinition（完整 E/O/A）
  → InvocationDefinition
  → run / checkpoint
  → ExecuteWork / ResumeWork
  → ChildCalls<Allowed>
  → ChildDefinition

Work → AuthorCheckpointWriter
Point.resume → ResumeWork
```

这些回链承载现有语义，不能仅凭有环就认定错误。若确认保留当前关联，ChildReference<D>、CP slot 与 owner 不能仅为减少依赖而擦成 unknown，工厂端的精确资源和 uses 也不能被统一宽类型替代；若关联本身需要调整，应单独论证。

此前静态扫描覆盖 runtime 的 172 个源文件：存在包含 8 个声明模块的依赖环，以及更大的调用/资源/观测/CP 相互引用组；在当时对相对静态 import/export 和 import type 表达式的扫描范围内，未发现运行值导入环。该结果只说明模块边，不证明检查器实际展开路径，也不覆盖动态加载。无需以“依赖图必须无环”为验收目标。

### 10.3 已有边界及其解释成本

另外有三个需要纳入具体审查的落点：

- `binding/access.ts` 的 InvocationAccess 只约束基础 InvocationContext，却在实现中强转取得 resources 和 signal。这暴露了声明端口与实际使用的差异；若职责不变，可考虑准确表达所需本层资源 Context 或窄契约，不要求为此把完整具体 Context 类型传遍所有 helper，也不声称此项单独提速。
- `Sequence.requests` 当前只向收集器传入 run/exceptions，与 Binder 包含 CP 及启用观测供给的正式集合并非同一语义，当前实际消费者仅在测试中。先确定其作为局部摘要的必要性或是否应移除该便利入口，不把它迁到别处就视为解决，更不能顺手补齐字段而改变其公开含义。
- `combineFaults` 位于 observation/error.ts，却供 invocation、changes 和 memory 共同使用；这是检查它是否属于通用错误职责的理由。归属调整仍需核对实际语义，不是已经测得的编译优化。

BoundChildren 和 InvocationWorkBinding 已在异构接线处保存统一契约；完整业务声明树并未作为一个泛型参数沿全部 InvocationBuilder 传递。InvocationCycleWork 也已经提供调用周期所需的窄操作端口。

因此不把所有 Builder、Binder 和 helper 一律再包装。检查每个位置时，先回答：

1. 它需要实际对象、业务 I/O 关联，还是只需要 level、身份、codec 或事实字段？
2. 它是否持有自身不变量，还是只组合已有正式操作？
3. 泛型关联在这里是否仍有消费者？能否在既有异构边界局部收敛，同时保持作者与子调用边界的准确性？
4. helper 的归属依据是否是它执行的职责，而不是恰好调用它的对象？

这里的候选原则是依赖与实际操作相称：若确实只读 codec，是否需要完整 Invocation；若只按签名提取 I/O，是否需要展开声明树。反过来，已确认需要关联的子调用输入/输出、阶段 uses、CP slot/owner 等，不能在类型简化中失去证明能力。

### 11.2 entry 的候选解释：三个维度叠加，一条顺序不变量（候选解释）

Observer 的 entry 链路（§5.1）实际叠加了三个不同维度的工作：

| 维度           | 当前承担者                                              | 输入／输出性质                            | 是否依赖对话业务 |
| -------------- | ------------------------------------------------------- | ----------------------------------------- | ---------------- |
| ① 输入适配     | `entry.accept` 的类型转换部分；`InvocationEntry`        | token → token，纯函数                     | 否               |
| ② 宿主接纳政策 | `acceptConversationRequest` 正式追加消息；`entry.admit` | 产生带凭据的实体效果（Transcript append） | 是               |
| ③ 运行范围固定 | `binding.capture`                                       | 内核构造：固定资源来源与原文范围          | 否               |

三者唯一共享的是**顺序不变量**：① → accepted → ②（未取消时）→ ③ → 建立 Context。顺序由 `BoundExecution` 保证。

**E 专属性的来源。** 维度 ② 的特殊之处不是“追加消息”，而是“在自身 Context 尚不存在时、在父活动之下产生正式效果，且失败归属于父”。这个边界只出现在 R 的直接子上——因为位置规则规定 R 的子只能是 E。O 的输入准备（S05）没有这个问题：O 的父 Context 已存在，O 可以在父 execute 内先准备再 `create`。所以 **entry 只在 E 是 G01 位置规则的推论，不是 E 的本质**；若位置规则改变，entry 的归属随之改变。这回答了 §5.4 第一列的“不能只以当前层级定义自证”。

**两种“入口”的关系。** `InvocationEntry/defineChildEntry` 只承担维度 ①；E entry 承担 ①＋②，③ 由绑定承担。它们不该合并（②③ 是另外两个维度），但共享的 ① 值得单独命名，使“输入适配”在两处是同一个概念而非两个相似签名。

**三种解释的对照：**

| §5.4 解释                      | 更自然的场景                                        | 需要特例的失败路径                                                                                   | 对照 S12 的预期                                                 |
| ------------------------------ | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 保留 E 专属进入边界            | S01、S06（恢复跳过 ①②、只做 ③）                     | S05 要解释为何 O 不需要；非对话 E 若无实体效果，② 为空但仍要走入口资源窗口                           | S12 的 E 会有一个只做类型转换的 entry，窗口与回调成为空转       |
| 进入边界为按位置安装的构造能力 | S04（两种入口输入到同一 Input）                     | 进入前没有目标 Context 时谁持有资源窗口——仍需一个“父活动下的窗口”，等于把 E 的机制泛化给未出现的位置 | 没有新增场景要求它；S12 不需要                                  |
| 拆分 ①②③                       | S02、S03（失败与取消的归属按维度落到不同对象）、S12 | 顺序不变量不再由一个对象持有，须由绑定显式编排，否则每个业务作者要自己保证顺序                       | S12 的 E 只声明 ①，② 缺省，③ 照常；最接近“没有可选能力时的路径” |

**暂定判断**：解释 3 最贴合维度，但只有在**绑定侧继续持有顺序不变量**（而非交给作者）时才可行；解释 1 是解释 3 在“② 由宿主对话政策填充”时的特例。S12 应优先建成 fixture，它是区分 1 与 3 的判据。本节不主张立即改动 `BoundExecution`。

## 12. 首个议题结果：拆开 entry，明确 R/E、内容与受理边界

### 12.1 收敛范围与结论

本节记录用户与 Codex 在 §11 之后的讨论结果，供 Fable 交叉审查。这里的“第一个议题”指首先展开的 **P02**，不是已经完成 P01 对全部 REOA 位置的重新论证。结论是概念与职责方向，尚未通过迁移实现、类型用例和运行回归证明。

**R/E 保持普通的调用输入与执行关系；内容变化进入内容实体与活跃视图机制；对外接纳进入受理机制。E entry 不再作为 E 的固有组成。** 原 entry 承担的行为分别归位，后续若发现剩余职责，需要给出独立场景证明，不能仅为兼容旧形状重新保留 entry。

| 对象／职责   | 本轮确定的边界                                                                                                         |
| ------------ | ---------------------------------------------------------------------------------------------------------------------- |
| R/E 调用     | 各有正常 Input/Output。R 可以在自己的声明处理函数中准备 E 的参数，选择、调用并接纳 E；一个 R 可以调用多个 E。          |
| R 的特殊之处 | 根调用的宿主入口、占用与控制，不是天然拥有消息、记忆或上下文维护。普通输入处理并非 E 专有能力。                        |
| 对外受理     | 根据真实事实作出外部承诺，可关联多个 E 的建立与结果。通过绑定及生命周期出口取得依据，不让每个 E 的构造器承担对外宣称。 |
| 内容实体     | 消息、记忆等独立存在，正式落实有自身契约；E 尚未建立不抹去已成立内容。                                                 |
| 活跃视图     | 明确发布当前参与后续理解的材料。业务决定保留、过滤和维护策略；框架保证依据、版本及安装／读取边界。                     |
| 容量维护     | 容量变化可以触发声明的处理能力。实际业务维护统一按 O 运行，作者可以提供简单函数、组合声明或兼容的现有 O。              |
| 绑定         | 检查并固定资源、声明、阶段资格及出口接线。业务顺序由运行声明或组合预设表达，不转移为 Binder 的隐式业务。               |

消息、记忆、活跃视图可以是框架提供的内容能力与预设，但不成为每一个 REOA 任务的强制依赖，也不把它们的所有权移到 R。当前内容包边界不因这一结论立即调整。

### 12.3 显化的维度与联合约束

这里的“上下文材料”指提供给模型的对话信息，不是 Invocation 的 Context。下表用于区分责任，不要求每行新增类、接口或目录。

| 维度           | 需要区分的取值／事实                               | 规则与责任                                                                                     |
| -------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 调用位置与输入 | R/E/O/A 的普通输入、父层构造的子输入               | 所属声明决定 Input；父层构造合法值，内核检查调用位置、登记身份与行动资格。                     |
| 内容落实       | 未提交、已正式落实、提交结果未知                   | 实体是权威来源。随后发生的维护／调用／通知失败，不能把已落实解释成未发生；未知也不能猜作成功。 |
| 活跃成员与版本 | 当前发布的成员、固定旧版本、更新尚未安装           | 视图机制表达哪些材料生效，调用读取有明确版本；既有源消息仍可存在于活跃集合之外。               |
| 容量评估       | 指定约束下未超限／超限                             | 相对于视图版本和容量约束评估，不是整个系统的健康状态，也不等于供应商保证接受。                 |
| 维护策略与执行 | 未配置、待处理、执行中、已结束／失败               | 策略决定删什么、保留什么或是否调用模型；实际执行由正常 O 承担，位置与阶段不能由 hook 绕过。    |
| 对外承诺       | 请求被跟踪、内容已接纳、相关调用已建立、运行已结束 | 受理机制解释真实事实并形成服务契约；这些事实不自动等价，也不必须压成一个状态。                 |
| 通知交付       | 事实成立、投影已处理、反馈已送达                   | 事实生产、服务解释和连接交付各有失败边界；反馈失败不重做业务。                                 |

由此保留以下联合不变量：

1. **先占用，再产生本次运行的内容副作用。** Observer 的忙碌拒绝不能先追加请求消息；占用失败不是内容已接纳。
2. **R 处理内容不等于 R 拥有内容。** 声明按资源申请使用实体，BoundRuntime 不理解 Transcript、Submission 或 HTTP。
3. **正式落实与对外接纳分别有依据。** 服务可以在内容落实或目标调用建立等明确条件下宣称相应承诺，但不得用回调被执行、跟踪项创建或连接成功替代这些事实。
4. **活跃视图的完整性相对于已发布版本。** 消费方取得这一版本应有的材料，不偷偷再做一次语义筛选；并非保证全部历史永远参与，也不替业务规定必须保留的成员。
5. **视图有效、视图新鲜与容量合适分别判断。** 当前合法发布的视图仍可超限。若内容变化应进入视图而同步失败，不能把旧版本伪称为最新；旧版本是否仍可用于某次处理须有明确依据。
6. **更新不能悄悄覆盖较新的视图。** 维护决定基于哪个版本，应在安装时核对；冲突如何失败或由业务重新决策可后续确定，不默认自动重跑模型。
7. **已固定请求不随活跃视图变化。** 当前请求使用的材料与配置一经固定，后续写入、过滤或维护不追溯改写它。
8. **维护失败不能回滚既成内容。** 声明异常、机制错误、取消和通知故障继续按各自契约处理；不得凭一个通用 throw 推断所有此前效果都未发生。

### 12.4 主链路：普通 R 输入到普通 E 输入

主案不增加 `tryOccupy() → occupied.run()` 一类新入口。服务先做无内容副作用的协议解码；现有 `R.run` 取得占用并建立 R；R 的普通处理函数通过内容资源处理输入，然后构造 E 的普通 Input。

```text
外部请求
  → 服务协议校验／解码：形成领域输入，尚未追加消息
  → R.run：取得占用、创建本次 R Context／Invocation
  → R.execute：正式处理输入内容，取得真实落实结果／视图变化依据
  → R 构造 E Input，正常 create／run／accept
  → E 按业务需要执行维护、生成、后处理等声明能力
  → R 可以继续选择其他 E，最终交付本次结果

实体落实与调用建立／结束事实
  → 绑定的受理／服务投影
  → 对外接纳与后续反馈
```

职责伪代码如下。函数名和字段名仅用于推演；省略了具体 requires、uses、异常、输出及 checkpoint 声明，不表示这些资格由内核自动放宽。

```ts
// 服务：跟踪请求不等于已经接纳，decode 不产生内容副作用。
const input = decodeConversationRequest(request);
const tracking = submissions.begin(submissionId);
const feedback = bindSubmissionFacts(tracking);
return runtime.run(input, { signal, progress: feedback });

// R 定义的普通 execute：不是 BoundRuntime 的内置业务。
async function execute(work) {
  const received = await work.resources.content.appendInput(work.input.messages);
  const child = work.children.create(answerExecution, {
    message: received.message,
    instruction: work.input.instruction,
    viewChange: received.viewChange,
  });

  await child.run();
  return child.accept();
}
```

`received` 必须有正式实体操作的依据；它不是从当前集合长度、通知是否成功或最后一条内容反推的结果。示例将正式消息与视图变化作为 E 输入，是这个对话声明的选择，不是通用 E 输入字段。

如果一个请求需要多个 E，R 可以把同一个已落实输入用于多个子调用，不需要每创建一个 E 都追加一次。受理机制分别关联这些调用的真实身份；“首个建立即受理”还是“全部必要调用建立后才受理”属于该服务的承诺，不能由内核默认猜测。

若未来宿主明确需要在 R 创建之前就正式保存外部请求，应单独定义宿主受理和运行准入的交接。这是可能的新需求，不是本轮为维持旧 entry 形状预建的机制。当前主案没有这个要求。

### 12.5 活跃视图：框架保证什么，策略决定什么

消息、记忆及其他对话信息可在任意合法阶段写入。内容接入必须说明相应写入怎样影响活跃视图：哪些内容进入、哪些退出、何时完成安装，以及怎样暴露容量评估与待处理变化。不能只在“创建下一次 E”时隐式改变后续理解范围。

框架负责可明确读取和核对的活跃材料版本，以及对写入／视图变化的处理接缝。策略可以是简单过滤，也可以是带模型调用的后处理；业务决定过滤哪些消息、记忆，是否摘要、是否产生替代内容。这里不另建一个通用的“是否需要更多信息”决策体系。

概念契约可以先写成：

```ts
interface ActiveViewSnapshot<Item> {
  readonly viewId: string;
  readonly revision: number;
  readonly items: readonly Item[];
}

interface ViewAssessment {
  readonly viewId: string;
  readonly revision: number;
  readonly constraintId: string;
  readonly status: 'within' | 'exceeded';
}

// 相同材料可在不同模型／预算约束下有不同评估。
const assessment = evaluate(snapshot, configuredConstraint);
```

`readonly` 只是类型示意，不能代替运行时的快照和值边界。版本怎样关联源实体修订、内容与视图是否共用事务、视图保存还是可重建，均需在实施前证明，当前没有承诺一个全系统原子快照。

容量规则分三处看：

- **内容变化后评估与维护**：是否留出余量、何时退出哪些材料，由策略决定；任何写入时机都能形成可处理的变化依据。
- **实际模型请求构造**：按目标模型契约序列化，算入任务指令、Schema、工具定义等实际材料。活跃视图没有承诺这些额外输入必然装得下。
- **真正超限时**：如实交付失败或进入明确声明的维护流程。不能通过未声明截断、跳过长消息或悄悄丢记忆来伪装满足容量。

因此，视图提供“系统当前明确发布的基础”，不保证信息永不退出、不保证未来输入不会溢出，也不把维护结果正确性等同于模型一定能理解。

### 12.6 容量 hook 与 REOA：统一 O，保持合法调用归属

实际触发的业务维护统一为 O，是本轮选择的执行语义；作者可以提交一个简单函数、组合声明或兼容的现有 O。简单函数可成为无子层的 O，不强制额外包一层 A；现有 O 可直接使用，不再包一个空 O。未配置维护能力时保留可观察的容量事实，不制造空调用。

```ts
// 作者写一个过滤策略；装配预设将其建立为维护 O。
onOverflow: ({ view, capacity }) => filterActiveItems(view, capacity);

// 作者也可以提供正常的组合声明。
onOverflow: defineViewMaintenance({
  children: [prepareRequest, requestModel, acceptDecision],
  run: maintenanceWork,
});

// 兼容输入／输出、资源和阶段契约的现有 O 可以直接装配。
onOverflow: existingMaintenanceOperation;
```

这里的“可以组合”指装配时生成并解算声明树。运行中仍在已声明的能力内选择，不引入动态注册新能力、替换正在工作的绑定或新的调度平台。

**触发位置不等于调用父层。** hook 不能让正在写入的 A 越级调用 O，也不能让一个资源回调暗中取得祖先 Work。最小合法组合是：

```text
O 写入并处理变化
  → A 正式写入内容，返回落实依据／视图变化
  → 父 O 接纳 A
  → 父 O 调用声明的维护 O
      → 可调用已声明的准备／模型／接纳能力
  → 父 O 接纳维护决定，通过正式端点安装视图更新
  → 返回
```

也可以让 E 在某个 O 返回并被接纳后处理变化。R 直接追加输入时可把变化依据交给随后正常建立的 E，由该 E 在合法边界调用维护 O；**R 不能为了 hook 直接调用 O**。若要求维护完成后才能建立后续目标 E，应在 R 的声明组合中明确选择一个提供该处理的 E，而不是让绑定跨层代调；本轮不强制新增这种前置 E。

组合伪代码：

```ts
// 位于有权调用下列 A/O 的父 O 中；资源、uses 已由声明给出。
const write = work.children.create(writeContent, input);
await write.run();
const committed = await write.accept();

if (committed.viewChange.needsHandling) {
  const maintenance = work.children.create(maintainView, committed.viewChange);
  await maintenance.run();
  const decision = await maintenance.accept();
  await work.resources.activeView.apply(decision); // 核对决定依据的版本
}

return committed;
```

这个写法表达两种不同的确认：父子调用的接纳，以及视图实体对变更决定的正式落实。视图落实失败时，维护 O 已返回的决定仍可存在，不应伪称它没有被交付。

组合预设应帮助作者建立正确的父层、resources／uses 和处理边界，作者不必接触 Invocation 或手工搜索祖先。helper 只使用当前 Work 的正式端口。机制必须避免以下情形：

- 父层正在等 A；A 在资源 hook 中反过来等待父层运行维护 O，形成等待环。
- 维护 O 写入内容后，再自动触发自己，无限递归处理超限。
- 声明未注册或阶段没有资格，却借 hook 开始新调用。
- 普通视图映射、容量计算也被强行提升为独立 O。统一 O 只约束实际业务维护，不替普通辅助函数制造调用身份。

如果“写入并完成维护”必须作为一个整体操作交付，公开的是包含这些步骤的 O；单个写入 A 不暗中承担父层编排。未处理的变化如何合并、哪个边界负责接走，必须在组合实现中明确验证，不能靠一个回调签名宣称已解决。

### 12.7 资源固定与维护完成的接缝

移除 entry 不等于移除资源 capture。配置、消息范围、记忆或活跃材料的固定时机，应由资源访问与该调用的声明决定，不能让所有调用都改为读取“最新全局对象”。

尤其需要验证以下链路：E 已建立 → E 调用维护 O → 新视图安装 → 构造模型请求。如果 E 在建立时已固定旧材料，后续维护不会让这个快照自动变新。需要在正确阶段正式取得维护后的版本，再将其固定为该请求依据；不能靠替换 E 的隐式资源来源修复。

本轮确定“应从明确版本取得本次依据”的规则，尚未确定全部端点形状。后续要证明这项读取如何与现有 binding/access capture、阶段 Work 及 CP 保存依据协作。该证明未完成前，不能声称只删除 `ExecutionEntry` 就完成了迁移。

### 12.8 受理、失败与恢复的场景推演

下表是本轮概念推演，不是已通过的自动化测试。

| 场景                                       | 按本轮边界应如何解释                                                                                                 |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| S01：正常请求                              | 协议解码后正常运行 R，实体正式接纳输入，R 构造 E 参数，E 执行；受理根据明确条件发布承诺。                            |
| 忙碌拒绝／R 建立失败                       | 尚未进入 R 的内容操作，不追加输入。跟踪请求存在不代表受理成立。                                                      |
| S02：内容已落实，维护／capture／E 建立失败 | 保留真实内容事实及 R 的失败；E 未建立则无 E 调用。服务按事实说明后续未完成，不伪造 E，也不把输入重新视为可安全重发。 |
| S03：内容已落实，随后取消                  | 内容保留；正常控制检查阻止后续不应启动的调用。取消请求与实际停止分别表达。                                           |
| S04/S05：不同入口数据、其他层的输入准备    | 由服务解码、父层普通逻辑或明确的输入适配完成；目标声明只规定自己的 Input。无需为每层新增 entry 窗口。                |
| S13：一个 R 创建两个 E                     | 可共享同一正式输入，分别建立与接纳；第二个失败不抹去第一个的建立／交付事实。对外承诺的聚合规则由服务声明。           |
| S12：非对话文件任务                        | 普通 R 输入到 E/O/A；不需要 Transcript、Memories、活跃视图或对话受理字段。                                           |
| 任意合法阶段写入导致超限                   | 形成带依据的变化，在明确的合法父层边界运行维护 O；没有处理器仍保留超限事实，不隐式截断。                             |
| 维护完成前视图已被另一合法更新改变         | 安装时识别版本冲突，不静默覆盖；不自动重跑模型来掩盖冲突。                                                           |
| E 已固定输入／请求，随后视图改变           | 保持原调用依据；新版本只影响明确选择它的后续处理。                                                                   |
| 通知／反馈链路失败                         | 不否定已落实内容或已建立调用，不触发业务重做；服务另行表达投影／连接状态。                                           |
| S06：已保存点续接                          | 按固定输入、关系和实体依据继续，不重演输入追加、已落实视图决定或已固定外部请求；依据不足仍拒绝续接。                 |

R 新增普通内容处理，会改变恢复链中“哪些输入已经正式落实”的位置。现有 Transcript `applyFixed` 使用父子接纳依据，**不能假定它未经调整即可用于 R 自身的输入追加**。若该位置需要可恢复落实，必须明确其固定操作依据、凭据与 CP 位置；或将效果安排到已有契约能够证明的组合位置。该项属于实施门槛，不在本节引入新的通用证据体系。

CP 也不因维护函数被包装成 O 就能恢复任意函数内部位置。仍只恢复声明的点、固定子关系和可确认实体效果；旧 CP 声明位置／输入含义改变须考虑版本，不自动迁移历史 image。

### 12.9 对类型组成的影响

本轮撤回的是“E 必须由 InvocationCore + children + WithEntry 组成”的前提，不是已经证明四个类型可以任意合并。后续可以从下面的组成式出发：

```text
R = 普通调用契约<I, O> + runtime 位置 + 声明的 E children
E = 普通调用契约<I, O> + execution 位置 + 声明的 O children
O = 普通调用契约<I, O> + operation 位置 + 声明的 O/A children
A = 普通调用契约<I, O> + attempt 位置
```

E Input 由本身的业务契约规定，父层参数须与之关联；不再默认让 EntryInput／EntryResources 随全部 InvocationDefinition 传播。普通调用是否仍需要某种显式输入适配接口，可以另行评估 `InvocationEntry/defineChildEntry` 的真实用途，不能仅因名称相近一并删除。

资源、异常、观测、增量、checkpoint、各阶段 uses 与行动句柄的关联没有因此消失。公开定义、阶段 Work 和异构绑定之间何处结束泛型展开，还需后续用通过／拒绝用例证明；不能用一个宽 `unknown` 或断言掩盖新 I/O 和资源关系。

类型接缝至少要能表达：

- 父层实际传入值符合目标普通 Input；非对话任务不被强加消息类型。
- 维护定义的输入与容量／视图依据、输出与正式视图变更契约关联。
- 简单函数与现有 O 的装配都得到同一种受约束的 O；不丢失注册身份和合法父层。
- 普通阶段、维护阶段及恢复阶段分别取得自身的资源与 uses，不通过 hook 取得额外资格。
- 受理只消费正式声明的事实出口，不要求业务处理函数接收 Submission 或协议状态机。

“为什么要按这些维度表达”在本议题已有答案；“怎样写出可推导且不累加展开的类型”仍未完成。本文不据此宣称编译性能已经改善。

### 12.10 本议题闭合了什么，没有扩展到什么

## 14. P02 最小闭环的实施结果

本节记录 2026-10-18 的实际落地，区分于前面的讨论和实施前审查。它只完成 P02 的当前服务闭环，**没有实施 F01–F09 的整体类型因式分解，也没有重新裁定其余维度议题**。

### 14.1 原来 E entry 的职责如何归位

| 原职责                 | 当前归属与行为                                                                  | 仍然保留的边界                                                           |
| ---------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 服务输入校验与正式接纳 | Observer R 的普通 execute 申请 Transcript append，取得正式 message/messageIndex | 这是服务声明业务，不成为通用 R 内核必备行为                              |
| 输入已接纳的对外反馈   | 正式追加点产生 input 进展；Submission 解释该事实                                | 不依赖 E 已建立、记录存在或 accepted 绑定回调                            |
| E 输入构造             | R 用普通输入创建 E                                                              | 内核四层都具有普通 I/O，移除 E 的 EntryInput/EntryResources 和专属 entry |
| 模型配置与原文定位     | ConversationCallSource 在创建 E 时 capture                                      | 定位不作为材料选择，不从当前集合长度猜本次输入                           |
| 活跃范围维护           | 可选 maintainContext O，执行注入函数或普通 O 策略                               | 不是 Binder 动作，不递归触发，不默认保留/丢弃具体内容                    |
| 固定工作材料           | prepareContext O 在维护后 capture                                               | 下游沿用同一份消息/记忆值，不回读旧范围作为模型输入                      |
| 默认容量行为           | 每个实际请求装载完整固定材料后 checkCapacity                                    | 超限失败，不隐式分段、截取历史前缀或运行选择模型                         |

`InvocationEntry` / `defineChildEntry` 仍保留为显式子调用输入适配；它们不是 E 的专属入口。本次没有夹带 P04 的进一步改造。

```text
R 普通调用
  → 正式追加输入，发布真实 input 事实
  → create E({ message, messageIndex, fileTask? })
      → 固定配置与定位，建立 E
      → prepareContext O
          → 可选 before-request 维护 O
          → 固定 ActiveContentSnapshot
      → 决策与能力推进
      → 回答落实、记忆收尾
      → 可选 after-content 维护 O
  → R 接纳 E 的真实交付
```

输入已接纳而 E 尚未建立时，保留正式消息与 R 的失败事实；没有 E 调用便不补造 E 记录。正常取消、占用与失败释放仍由现有调用机制处理。当前 Observer 仍组合单 E，内核没有恢复为 R 与 E 一一对应的结构特化。

### 14.2 活跃视图的最小落点

ActiveContent 位于服务 conversation/content，由 ConversationContent 持有；它是已有内容上的可持久索引，没有独立 UID 或关闭生命周期。它保存消息索引与记忆 ID，不持有新的一套正文实体，不用记录解释当前业务材料。

成员可以非连续、有明确顺序；退出不删除正式内容，不要求生成替代内容。新消息和新记忆默认纳入，已有记忆更新不自动重新纳入已退出成员。capture 返回不可变消息/记忆值，复合依据为 `transcriptId + memoriesId + indexRevision + transcriptRevision + memorySequence`，因此成员不变的记忆更新也会被正确区分。

read/manage 是正式资源，端点按 access 时机执行 capture/apply。SQLite 升为 v6，源追加或新建与其活跃成员在同一事务提交；显式 apply 按完整依据检查冲突后保存。旧库以当前消息段和全部已有记忆初始化，不自动唤回归档段。

默认 prepareContext 输出 material、context 和用于既有观测形状的 selection 索引。理解接收固定 history；回答/文档接收固定 context；记忆提取接收原固定材料加本轮 QA/已接纳操作结果。原文 fixedRange 仅用于定位/核验；材料计数通过资源核对真实消息后落实，不用 CP 解码对象的内存身份代表消息身份。

这形成“索引当前成员 → 捕获单次值 → 下游消费”的清楚边界，不建立第二套内容管理平台。契约及装配样例见 [活跃材料与维护](active-content.md)。

### 14.3 维护能力接回 REOA

配置 maintenance 时，维护本身是普通 O。函数策略可直接处理快照；需要模型或其他能力的策略是其子 O，再按既有规则组合 O/A 和资源。P02 初版用 maintenanceResources 显式透传额外资源；本轮 §15 已移除该补丁，由子树 supply 解算向下供应，各声明只申请自己所用。所有资源仍必须在绑定侧真实供应。

当前只落实 before-request 和 after-content 两个服务边界，各调用一次。策略自己产生内容变化不会再次调度维护；写入之后若需提出索引决定，必须取得新 basis，旧决定不能覆盖新源内容。未配置时不创建空维护调用。维护失败保持正常错误语义；后处理失败保留已经成立的回答。

这不是任何阶段写入都自动触发的 hook 平台，也不保证后处理一定预留足够容量。单条输入或任意完整请求仍可能超限；真实请求构造明确失败。

### 14.4 CP 与未扩大的恢复承诺

本轮改变声明的输入与子结构后，Observer R/E 的 checkpoint 契约版本为 **3/4**，旧版本明确拒绝，不保留旧 entry/selection 状态的兼容壳。Frame 仍为 v2；内容数据库的 v6 是另一个版本维度。

准备 completed、E preparationAccepted 和已返回准备交付保存原材料。恢复核对原消息、记忆版本及固定落实凭据，不通过当前活跃索引重建原输入。R 续接准确 E，不再次执行原输入追加；R 追加后尚无首份 CP 的窗口仍未承诺恢复。

维护预设提供 waiting（子策略有 CP 时）、accepted 和 completed 局部点，准备预设可等待并接纳真实维护子调用。**当前宿主仍拒绝自定义维护恢复**，即使该策略 O 有 CP；还缺完整的宿主配置/实现版本关联，不能把局部预设验证当成全部链路的恢复承诺。

ActiveContent.apply 尚无固定效果凭据。索引已落实但 completed 未保存时，旧 accepted 点面对变化后的 basis 必须拒绝；目标成员相同也不证明是原操作。completed 续接复用已保存结果，不再应用索引。这是明示限制，没有用自动重试或重新运行策略掩盖。

## 15. P03/P04 窄闭环：结构、调用、能力与 Work

本节记录 P02 之后对资源供给及调用控制的实施收敛，不启动 F01–F09 的全量类型迁移。公开定义仍是 REOA 四个命名层；没有引入通用能力平台。

```text
REOA 定义 → Binder 解算 → Bound 可复用结构
                              │ 每次调用
                       Invocation ↔ Context
                         │         本层事实、固定输入与构造归属
                         ├─ Control：启动与活动窗口关闭
                         ├─ Children/Relation：调用、返回、接纳及在途活动
                         ├─ 资源/CP/输出/观测：各自固定契约与生命周期
                         └─ Access → 当前阶段 Work → 业务处理
```

### 15.1 本次显化的维度

| 维度                   | 规则                                                         | 被拒绝的近邻                                          |
| ---------------------- | ------------------------------------------------------------ | ----------------------------------------------------- |
| 层级位置               | R→E、E→O、O→O/A，A 为叶                                      | 为供给管道改变合法子层                                |
| 内部供给与本层使用     | supply 汇集已声明子树所需 offer；requires 决定本层 Work 端点 | 父仅因透传就取得子资源、观测专供满足业务申请          |
| 固定构造条件与活动控制 | 创建固定来源/收窄/构造归属/控制信号；真实启动验证直接父      | 每次父状态变化重新解算子供给或查祖先 Context          |
| Context 与 Control     | Context 保存语义状态；Control 门控本次活动，不复制业务状态机 | 把资源实体、关系表或外部交互归 Control 所有           |
| 阶段资格与已启动活动   | Work/句柄受阶段约束；已启动子拥有自己的窗口                  | 用旧 Work 继续派发，或把父阶段变化当作子取消          |
| 返回与接纳             | 子交付和父接纳分开；收尾只等待，不替业务接受结果             | 将 pending 关系一律视为在途、自动接纳或自动重发       |
| 调用与外部交互         | 调用发起/等待读取；Interaction 独立保存发送与反馈            | 调用取消自动 abort 外部发送，或把晚到反馈用于复活旧 A |

R→E 独立来源仍是当前实现的明确非均匀点，不把这轮供给汇集宣称为全部层级的来源统一。Context 仍持有本层 ResourceBindings；子构造只读取固定供给捕获，不使用父 Work 的视图，也不依赖祖先活动性。

### 15.2 小闭环的行为增量

1. 父层不再为透传子资源展开 child.requires。维护 O 的 through/maintenanceResources 删除；E 仅申请自己使用的资源。收窄可以作用于纯透传供给，父和兄弟不变。
2. 恢复点有独立资源与动作窗口；离开 resume 后永久关闭。正常 run.execute→run.accept 仍共享本轮正常资源端点，已取得的普通数据值不失效。
3. 阶段退出先等待已开始的接纳回调，终态交付前等待已启动子调用真实收尾。不自动接纳、不等未启动子，不隐式停止兄弟。
4. 调用取消停止本地等待，独立 Provider timeout 管理外部发送；晚到反馈仍可保存，新 A 可按 ID 读取。环境关闭仍要求独立交互已结束；宿主可先显式等待 settled()，进程强制退出不保证反馈保存。
5. 观测依据实际发生资源访问的调用解释配置。E 自己不读模型配置时，不为了旧 UI 投影重新扩大 E 申请；子树存在多个或冲突供给时明确展示非唯一状态。

新增收尾等待是显式行为增量，不宣称只是文件重排。子声明异常晚到时只交付；业务原样传播仍按原父、阶段、轮次认证。已确定的本层退出失败不能被收尾期间另一份声明异常诊断覆盖，技术错误仍然优先且不能由 catch 清除。

### 15.3 仍保留的界限

- 不引入 Work.control、公开 stop/wait、选择性停止兄弟、跨阶段失败凭据再签发；有真实场景后单独确定契约。
- 不持久化 Control 或任意 Promise，不扩大 Frame v2、checkpoint 可保存点、未知外部反馈的恢复承诺。
- 固定调用入口不等于禁止实时资源读取或业务修改实体；实时/快照语义由各资源契约解释。
- 非协作执行体若永不退出，本轮收尾也会等待；不能通过提前释放 R 占用宣称已结束。
- 不增加模型并发限额，接纳 ready 不保证模型成功或无外部在途工作；需要真实容量治理时另定策略。

验证落点包括资源纯透传/收窄/缺失供给，父子阶段变化与真实收尾，失败传播与错误优先，恢复端点撤销，取消后的晚到持久反馈、新提交、独立交互在途时的合法 CP 恢复，以及无模型的服务/客户端完整回归。具体结果随本轮工程检查报告。

## 16. 候选收敛与契约类型小闭环

本节记录 2026-10-19 的实施，目标是让现有作者类型和建立边界准确表达既有规则，不启动完整类型因式分解。

### 16.1 候选去留

| 候选                                           | 本轮决定                                                                                     |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 资源供给、本层申请与访问窗口分离               | §15 已实施，保持原规则                                                                       |
| 资源来源策略与层级解耦                         | 保留候选；独立捕获与共享捕获语义不同，本轮不新增 E 继承或 O/A 独立来源模式                   |
| 同一声明按装配位置配置业务资源分支             | 撤销内核候选；用户注册多个 O/A、选择能力及复用处理逻辑属于最佳实践，不新增声明变体或身份体系 |
| 必要调用建立与被动进展/输出                    | 保持不同失败语义，修复同步回调缺口；不重写 RuntimeCallSource 或新增 CallWiring               |
| 层级上限、注册集合与阶段资格                   | 补齐 Work、基础声明及恢复点的类型上限，保持身份与窗口运行期核验                              |
| ContextView 合并、完整声明因式分解、元数据归属 | 暂缓，不作为本轮前置                                                                         |

### 16.2 类型与职责落点

- `definition/level.ts` 保存现行 R→E、E→O、O→O/A、A 叶子规则；ChildLevel 与 Binder 从同一表取得约束。这是固定位置规则，不是可扩展层级注册表。
- `definition/children.ts` 提供 ChildrenOf；Work 的默认 Allowed 及显式参数均受所属层级约束，基础 run/exceptions 和 checkpoint point 同样遵守。工厂继续根据真实 children/uses 推导更窄的行动集合。
- `ResourceRequests / ResourcesOf` 移至 `resource/offer.ts`，根公开名称不变；普通工厂不再向 CP 文件借用资源和层级推导。
- 工厂和 point 的 handler 参数使用 NoInfer 固定资源推导方向：requires 声明决定资源类型，helper 参数不得反向补出未申请的资源。返回类型和显式 requires 继续完整推导。
- Observer 中为流式输出显式填写的宽 ChildDefinition 参数改用对应 ChildrenOf，业务流程和声明树不变。

历史 refs、facts 与 open 不受当前 uses 集合收窄。创建与恢复动作的类型限制不代表运行期可以省去注册身份、归属和阶段检查。具名类和未携带具体集合的 helper 只证明层级上限；同形声明身份、Sequence 内的异构组合仍由既有运行检查兜住，本轮不宣称整个编排已被静态证明。

### 16.3 同步建立契约

InvocationStarted 从 void 收紧为 undefined，调用入口同步拒绝其他返回值，失败归 setup 且不执行工作、不发布 started 事实。意外 Promise 的迟到拒绝会被消费；不等待 Promise、不提供登记事务或副作用回滚。Observer 先执行必要 CP 登记，再透传宿主回调返回值，防止包装层掩盖异步误用。

新 E 建立执行登记，旧 E 恢复不重复；恢复活动中新建 E 仍执行登记。同一调用进入第二轮不再次登记。这些区分沿用原机制，不按 recovering 一律跳过。

### 16.4 验证范围

作者契约用公开出口验证具名类、工厂、裸 Work 和 helper；正例覆盖各层合法子调用、输入适配、各阶段资源、无申请 helper、恢复点与无 uses 的历史接纳。独立编译失败用例覆盖非法层级、显式扩大 Allowed、空 uses 启动、未申请或类型不符的 helper 资源，不用断言或 suppress 掩盖错误。

调用和服务回归覆盖正常同步登记、抛错、非 undefined 返回、异步迟到拒绝、局部继续、旧 E 恢复、新 E 在恢复活动中建立，以及服务包装失败后下一请求仍可执行。运行机制不改变 CP Frame、协议、资源来源策略或被动消费者隔离语义。

清理各包生成产物后运行 `pnpm check`，构建、类型检查、1508 项测试及全仓格式检查通过；使用现有确定性替身与本地恢复回归，没有调用真实模型。不依据本次类型归属调整宣称编译性能提升。

## 17. 声明元信息、能力契约与候选目录的设计闭环

本节是职责与迁移范围的收敛，源码核对基线为 `e07a217`。用户确认：能否执行、是否满足被选择的前提由强约束兑现；元信息辅助理解。下面的 `meta/source` 是统一的讨论词汇，不是新增公共 API；不增加通用 Catalog 实体、条件引擎或新的 A 类族。

### 17.1 三个判断及其责任

| 判断                     | 依据与责任                                                               | 不意味着什么                              |
| ------------------------ | ------------------------------------------------------------------------ | ----------------------------------------- |
| 当前是否允许提出这个选择 | 父流程的选择契约与已接纳事实；产生候选后，在提案接纳时复核               | 不保证实际调用一定成功，也不取代阶段 uses |
| 真实调用及操作是否成立   | 内核检查注册、位置与活动窗口；能力检查业务输入；资源兑现范围及实体不变量 | 不能根据元信息、模型承诺或预检成功而跳过  |
| 合法候选中哪个更适合目标 | 函数或模型决策策略；使用用户目标、已接纳进展、能力说明与参数含义         | 不因选择更合理而扩大合法范围              |

声明可以同时携带正式契约和可理解的说明，但二者不互相代替。例如“不会覆盖已有文件”可出现在说明中，真正保证它的是文件端点；“先有回答才能保存”属于当前父流程，不必成为通用文件能力的输入前提。条件的文字说明可以辅助选择，不能成为另一份独立执行规则。

正式契约继续由已有的 I/O、requires、uses、raises、output、checkpoint 等各自表达，不复制进元信息。TypeScript 输入类型不是模型可消费的 Schema；目录参数仍需明确的运行期校验与可序列化描述。父流程的 State 类型停留在本流程目录适配处，不进入通用子声明的泛型。

### 17.2 名称、身份与描述分开解释

| 项                                | 作用域与用途                                                   | 必须保留的区别                                         |
| --------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------ |
| 声明元信息 name / label / summary | 能力的符号说明、短标题及用途说明；可供进展、观测和目录投影使用 | 不因同名而成为同一声明，不从名称证明输出形状或权限     |
| catalog 的 name                   | 本目录中显式登记的选择键，关联真实 use、参数及输入适配         | 这是有意建立的选择契约；不是扫描声明元信息匹配同名对象 |
| 子调用 key / ref / contextId      | 关系说明、认证引用与单次身份，各沿既有机制使用                 | catalog 键不是子调用身份，key 也不是恢复身份证明       |
| CP key/version、点、直接子关联    | 已声明的保存与续接契约                                         | 不从源码路径或展示名称自动推导兼容性                   |
| source / callee                   | 当前实现的源码定位与目标说明                                   | 不证明执行版本、外部生命周期、幂等性或结果类型         |

“名称不能成为隐藏的执行契约”不等于禁止显式使用字符串键。目录登记必须消除键歧义，并在本次选择与接纳范围保持键到契约的关联；元信息名称没有这种默认唯一性要求。当前服务的 `save` 明确关联 name 为 `saveResult` 的声明，`document` 关联 `processDocument`，已经体现这一区别。

仅修改展示信息不应改变内核身份与 CP 依据。但目录键若进入已保存的业务 state，或其对应声明及续接语义发生变化，必须遵守该业务 CP 的版本规则，不能笼统称为“只是改名称”。

### 17.3 catalog 的产生与消费

候选范围来自父层显式登记的可选能力，不是自动把所有 children 公开给模型。注册/uses 限制真实行动；目录还需要表达当前业务是否允许选择。决策、材料准备、记忆收尾等子声明可以由父流程直接组织，不进入可选目录。

```text
已声明、已装配的子能力
  → 父流程显式登记 use、选择键、公开参数、输入构造与结果接纳
  → 依据已接纳事实筛选，形成这一步的只读 catalog
  → 决策能力消费请求、进展、最新交付、反馈及 catalog
  → 父层接纳提案时复核键、当前可选条件和参数
  → 固定已接纳决定（如声明了 CP）
  → 构造普通子输入，通过当前 Work 创建、运行并接纳
  → 已接纳结果进入父层进展，再形成下一步候选
```

目录是选择依据，不预占资源，也不是允许执行的凭据。提供给决策者的是固定的本次数据；不因外部状态变化重新解算在途 Work 或向其注入可变父上下文。外部前提在实际操作时按对应端点契约核验。

以下沿用现有目录字段表达职责，省略记录、CP 和结束分支；`schema` 与普通输入构造保持类型关联：

```ts
const saveOffer = {
  name: 'save',
  use: saveText,
  description: '保存本次已接纳的回答',
  schema: emptyArgumentsSchema,
  available: (state) => Boolean(state.answer && state.destination && !state.saved),
  input: (_, state) => ({ path: state.destination, text: state.answer.content }),
  accept: (receipt, state) => ({ ...state, saved: receipt }),
};

// 另一父流程可以使用同一声明，公开不同参数，并构造同一正式 Input。
const editorOffer = {
  name: 'save',
  use: saveText,
  description: '创建指定文本文件',
  schema: saveArgumentsSchema,
  available: (state) => state.editingAllowed,
  input: (args) => args,
  accept: (receipt, state) => ({ ...state, lastCreated: receipt }),
};
```

这里复用的是声明及其不变的处理契约，没有在目录中替换资源供给、注入位置配置或改变执行实现。需要不同业务资源契约时，仍按 §16 的结论注册不同 O/A 声明，复用业务函数。目录说明可采用声明说明的默认值，再解释本次使用目的；选择键和公开参数不得靠元信息猜测。

### 17.4 A 的形态通过机制组合，源码只提供定位

A 表示不继续创建 REOA 子调用。本地处理、文件访问、外部交互与增量输出可以出现在同一 A 中，分别由处理逻辑、资源端点、独立 Interaction 和 output 契约承担；不建立 LocalAttempt / ExternalAttempt / StreamingAttempt。需要独立子接纳、错误归属或恢复边界时，应由 O 明确拆分。

```ts
async function execute(work) {
  const document = await work.resources.files.read(work.input.path);
  const interaction = work.resources.creator.start(document);
  work.output.emit({ kind: 'submitted', interactionId: interaction.id });
  const feedback = await work.resources.reader.wait(interaction, { signal: work.signal });
  return parseFeedback(feedback);
}
```

该例仅推演组合：解析失败不撤销外部发送，调用取消不结束独立 Interaction，增量不证明最终接纳；一次 A 也不构成原子事务或可安全重试的证明。实际续接与不重复发送必须由明确保存点及交互读取契约实现。单一 callee 无法表达这些机制，不应成为 A 的分类依据。

源码定位应允许缺失，候选形状为 `{ module, symbol? }`：`import.meta.url` 可减少手写模块路径，但编译后通常指向 JS，不自动提供 TS 行号、符号位置或历史源码快照。宿主负责路径映射与公开范围；内核不从路径读取源码，也不把定位信息作为恢复身份。缺失时不提供源码入口，不伪造路径或把普通记录标记为来源不完整。本轮不引入构建插件或运行期堆栈猜测。

### 17.5 当前实现证据与不能省略的迁移

| 当前事实                                                    | 依据                                                                                     | 对后续实施的要求                                                                    |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |

### 17.7 下一实施闭环的范围

可以实施的主线是：共同描述契约 → 声明解算与 Bound → 普通/恢复调用事实 → 被动进展与可选记录 → Observer 投影及历史兼容。实施前需把公共字段形状、记录的缺省目标/源码表达、服务结果解释的识别方式定成一套明确契约；不能只把字段收进 meta 就算完成。

其中普通活动与恢复活动仍走各自的既有出口：恢复通过 CP activity 事实及 installed 基线表达，不因此重播普通进展、旧 submission 或原 Recorder。描述传递一致不等于合并这些交付生命周期。

验收至少包含四层、工厂与类两种声明写法、绑定后原声明变化、不装记录、无源码、同名异构输出、真实目录关联、正常与恢复活动、历史记录读取，以及原有取消/异常/资源/输出/CP 回归。描述变化不新增身份，目录键和业务续接含义变化则按既有版本契约处理。元信息沿现有绑定固定，不以动态 getter 或祖先可变状态重新计算 Work。

不新增全局目录、通用条件引擎、同声明资源分支、A 子类树、自动扫描能力或新的持久化实体；ContextView 合并及整体类型因式分解继续独立讨论。

## 18. P05 接纳候选与 P06 类型推演（2026-10-19）

本节基于后续讨论已选择的候选进行编译验证，不是生产接口发布。REOA 位置、资源供给／阶段申请、InvocationControl 活动窗口继续沿用前面的小闭环；本轮没有修改运行实现。公共元信息字段的最终形状仍按 §17 的实施门槛确定，未在原型中擅自固定为 `meta`。

### 18.1 本轮采用的接纳候选

父声明登记接纳契约；契约关联真实直接子声明与本父采用的 Accepted 值契约。同一个子 Result 可以由不同父处理成不同 Accepted。它没有独立执行阶段、资源或生命周期，接纳回调继续使用当时的阶段 Work。

```ts
const saved = reception(generate, receiptContract);
// 父声明：children: [generate], receptions: [saved]
const call = work.children.create(generate, input);
await call.run();
const receipt = await call.accept(saved, (result) => files.write(result));
const previous = work.children.facts.accepted(call.ref, saved);
```

这里 `accepted(ref, contract)` 是要求已接纳且契约匹配的读取，返回 V，不以 `undefined` 表示缺失，因为 V 自身可以是 `undefined`。普通 `facts.get` 继续负责状态读取。每次调用仍由 ref 区分，契约或 key 都不能取代关系身份。

接纳开始前核验本父注册、直接子归属与窗口，进入 receiving 时固定本次契约；后续失败或恢复不能偷偷换成另一个契约。正常结果检查与持久编码分别承担职责，不能用编解码往返替换正常成功引用。实体已落实后检查或保存失败，不回滚既成事实，也不授权重做实体操作。

这是待实施的语义增量。跨进程需要父 CP 契约版本、父内接纳契约注册位置与准确子关系共同定位，格式须显式升级，不能把新编码静默塞进 Frame v2。原型保留既有 raw accept 的类型形态，但没有证明 raw 历史与新契约的迁移，也不能给旧事实补贴一个新契约标签。

### 18.2 类型构成与推导停止的位置

```text
Definition = InvocationCore + level 位置 + 该位置允许的注册结构
Work       = 本次值 + 本阶段资源 + 分支能力 + 阶段动作 + 可选输出
```

R/E/O/A 保留四个作者入口；能力累加不采用类继承链。A 的注册结构显式禁止 children／父接纳契约，R/E/O 的 children 按位置表约束。E 使用普通 Input，没有专属 entry；显式子输入适配仍可使用父事实与 key。

| 类型关联       | 必须保留                                                      | 不继续向外传播                                     |
| -------------- | ------------------------------------------------------------- | -------------------------------------------------- |
| 定义消费签名   | level、Input、Result、Delta                                   | 全部处理函数、资源申请、整棵 children 与所有 CP 点 |
| 工厂／定义作者 | children、各阶段 requires／uses、阶段函数的准确参数           | 不由函数体反推扩张申请或登记集合                   |
| 单个 ChildCall | 当前子签名、准确 ref、Result                                  | 父层整张接纳注册表                                 |
| 接纳操作       | 子签名与当前契约 V                                            | 不由接纳回调反推扩大 V                             |
| 单个 CP point  | owner I/O/level/输出能力、本点 State/Slots、resume 资源／行动 | 不把所有点的 state 和 refs 合成大联合塞进 Core     |
| helper         | 它确实使用的操作与 I/O                                        | 不为取得一个结果反向解算完整 Definition            |
| 观测及记录     | 自己消费的事实与资源                                          | 不拖入业务声明树的泛型                             |

“窄消费签名”只是同一声明对象的一种类型视图，不新增实体、不删除生产者的 run/checkpoint。原型工厂用 `declare` 返回该视图来隔离验证；真实工厂如何保留完整处理函数、receiver 与绑定解算，仍需生产迁移证明。不能因为原型没有实现函数体，就宣称消除了异构存储边界的类型擦除。

Work 不能简单只剩叶子／分支两种：execute 可写输出／保存点，accept 有 delivered／continue，handle 有异常及 Resolution，resume 有专属恢复行动。run 省略 uses 为全部登记子；exceptions／resume 省略 uses 为空。正常 execute/accept 共用 run 资源，其他阶段独立申请。历史 facts/open 不因当前 uses 变窄而失去访问，真正启动／恢复仍检查当前资格。

### 18.3 编译推演暴露的三个卡点

**一、宽 CP 槽位与具体槽位直接交叉，会丢失具体键集合。**

```ts
// 有问题：公共 references 若含 Record<string, Slot>，会带回 string 索引。
type SpecificPoint = PointIdentity & { references: SpecificSlots };
// 原型改为先移除宽字段，再安装本点的具体字段。
type SpecificPoint = Omit<PointIdentity, 'references' | StateKey> & { references: SpecificSlots; [StateKey]: State };
```

宽类型适合异构登记与存储；作者 save 必须保留本点的精确字段。引用槽位还应受所属 level 的直接子位置限制，但不受当前阶段 uses 限制。owner 的 Input/Output/level 保持关联；Delta 按能力兼容，无输出或更窄输出的点可接入较宽 owner，不能发出 owner 不支持的增量。

**二、helper 直接接收泛型 create 方法，可能丢失行动集合约束。**

`Pick<ChildCalls<D>, 'create'>` 看似精确，但泛型方法之间的结构兼容可能放过不属于该端口范围的声明。仅拆成 Allowed/D 两个参数也不自动解决。原型与当前公开包类型都复现了此反例；所需修正是具体操作投影：

```ts
interface StartPort<D extends ChildDefinition> {
  readonly create: (definition: D, input: DefinitionInput<D>) => ChildCall<D>;
}
function start<D extends ChildDefinition>(port: StartPort<NoInfer<D>>, definition: D, input: NoInfer<DefinitionInput<D>>): ChildCall<D> {
  return port.create(definition, input);
}
```

只取结果的 helper 则直接用 `{ run(): Promise<O> }` 推导 O，不从 `OutputOf<D>` 反解 D。确实需要身份时再保留 ref。这样无需新增公开 grant 对象，也没有拆出方法而丢失 receiver。

**三、异构动态候选已经成为联合类型时，NoInfer 不保证输入成对关联。**

```ts
const selected = condition ? readFile : summarize;
children.create(selected, { path: 'notes.md' });
// 如果选中 summarize，而它需要 {text}，上述组合仍可能静态通过。
```

类型只看到了两个联合，没有证明实际选中的声明与输入对应。当前候选保留这个可编译反例：同 I/O 的候选可以直接选择；异构候选在分派处先收窄选择，再构造／校验对应输入。模型返回的 unknown 参数必须按选中契约核验。Binder 的对象身份与 uses 检查本身不能替代输入校验；不声称所有动态联合已经被类型系统证明，也不因此引入通用分派平台。

## 19. P06 受限类型整理实施（2026-10-19）

本轮基线为 `e07a217`，范围是 §18.5 第 1 项及其工程效果复核。四个作者入口和既有公共类保留；没有把原型中的 `declare` 工厂当作实现，也没有引入平行的声明实体。父接纳契约及新 CP 保存格式仍按第 2 项另行闭合。

### 19.1 完整声明与消费签名分开

`DefinitionContract<Level, Input, Output, Delta>` 只携带层级与类型签名，表示原声明对象的消费视图。`ChildCall`、`ChildOptions`、facts、refs、阶段 `Allowed` 及绑定内的身份查询消费这个视图。完整 `ChildDefinition`、`ChildrenOf` 继续用于注册、声明解算、资源收集与 Bound 构造；工厂仍返回完整定义，具名类的 receiver 和私有实现继续成立。

```ts
const read = defineAttempt<ReadInput, ReadResult>()(/* 完整定义 */);
const target: DefinitionContract<'attempt', ReadInput, ReadResult, never> = read;
// target 是同一对象；调用消费者无需继续理解 read 的资源和处理函数。
```

签名是必需的 type-only 见证，没有运行字段。独立审查发现两种风险：可选签名允许先抹去成 `{ level }`，再赋给错误 I/O；输入协变允许把具体输入扩大为 `unknown` 后传入任意值。即使运行期核验身份，这两种情况下仍是同一个对象。现在签名必须保留，且 Input 同时保留读写方向、按不变关系检查；Output 与 Delta 维持协变。异构登记上限只在输入约束处使用明确的擦除，具体调用仍从真实 D 推导，不把无关输入和输出拼成一个新契约。这些边界均加入反例。

声明快照先逐项检查全部真实字段，再局部保留原定义的类型见证；这不替代原对象身份认证，不增加运行时 symbol。

共享 `DefinitionChildren<Level>` 表达完整注册结构；工厂的可选输入形状单独称 `FactoryChildren`。`ChildContractsOf<Level>` 表达消费端的层级上限，A 为 `never`，R 不能成为任何 ChildContract。类型上限、实际注册、阶段 uses、历史关系依旧是四项不同检查。

### 19.2 推导在所属范围停止

| 位置                   | 本轮处理                                                                                                | 保留的责任                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 工厂 run / exceptions  | `uses` 从已登记 children 取值，不能反向扩张 children 的推导                                             | 具名类的宽上限仍由绑定核验真实登记；阶段资源仍从 requires 推导         |
| CP point               | 单独保留 State、精确 Slots、resume requires/uses；移除宽 slots 交叉，check/resume 不反推扩大 state/refs | owner、真实点登记、直接子归属、引用认证和 Frame 编解码                 |
| ChildEntry             | 子调用消费 definition 与输入适配；不携带完整定义的 getter 要求                                          | 原 InvocationEntry 继续保留 run/exceptions，供 Sequence 的资源收集使用 |
| 服务 capability helper | 只接收当前目标的具体 create 操作，以及历史 open/facts                                                   | 选中参数先按对应 Schema 解析；接纳前仍以 facts.require 核验目标        |
| Sequence               | 第三泛型 Uses 累积每一步声明；run 只消费 create/entry，并检查具体创建范围                               | 步骤完整定义仍用于 requests，顺序、输入构造、输出与接纳行为保持        |

这里没有把 execute、accept、handle、resume 合成一个任意组合的 Work。阶段动作、资源和输出能力仍各自准确；历史 facts/open 不受本阶段 uses 收窄，启动与恢复仍受窗口约束。

工厂返回端的资源参数也使用 `NoInfer`，避免左侧显式 `*Definition` 标注反向补出并未申请的资源。普通和带 Delta 的工厂均验证了直接显式注解、正常／异常阶段分别申请与错误资源拒绝，不要求作者拆成临时变量绕过推导。

### 19.3 明确的兼容性收紧

1. A 具名类不能声明 children；JavaScript 或绕过静态检查的输入在绑定时也明确拒绝，包括空数组。此前静默丢弃该字段，不是合法子结构能力。本轮调整了原输出回归的通用 fixture，使 A 不再声明 children，输出断言保留。
2. 显式 `InvocationCheckpointPoint` 的 Allowed 缺省为 `never`，对应 resume 未声明 uses 时没有新行动；历史读取仍成立。显式类型如需行动，必须提供准确 Allowed 或由 `checkpointPoint` 推导。
3. 非空 Sequence 不能再用仅 `Sequence<Input, Outputs>` 的标注抹去步骤范围。通常保留推导即可；必须显式标注时使用 `Sequence<Input, Outputs, UsedDefinitions>`。扩大成 `ChildDefinition` 会要求更宽的调用端口，不能借此通过窄阶段 grant。
4. 类型签名必须随完整声明和浅视图保留；只剩 level 的对象不构成可调用的消费契约，也不能改变输入的接受范围。对象式定义由现有 `define*` 工厂形成，不能再把裸字面量直接标注为完整 `*Definition`。现有三处这类类型 fixture 改用工厂，保留原有组合、资源与层级断言；具名类写法不变。业务不增加运行字段或手工制造签名。
