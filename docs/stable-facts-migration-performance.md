# 稳定事实迁移：计算范围复验

日期：2026-11-07。使用生产固定值边界、Frame v6 增量提交及 SQLite v7；同一组公开 `Scene → Group → Node → Runner` 工作量对照[迁移前报告](checkpoint-computation-results.md)。

结果分成两部分：**有界 current 选择下，保存不再随已接纳历史增长；完整 all 选择仍有显著成本，而且 SQLite 在 N=512 的该路径比原实现更慢。** 因而本轮不能宣称所有作者写法已经获得有界保存成本。

## 测量口径

- Apple M3 Max、Darwin 25.6.0、Node 22.23.2、SQLite 3.51.3，与旧报告环境相同。
- 18 个主耗时配置各一个独立进程；Memory/current/2048、SQLite/current/2048、SQLite/all/512 各追加一次独立复测。最后针对提交内机械优化另测3个配置。6 个配置另开进程计数，计数模式的耗时不用于结论。
- 每个 CP 进程先预热8步，再新建结构和 Store。无真实模型、网络、已有数据库、记录器。保存点仍是每步 dispatch/accepted，父层 `2N+1` 次；没有靠减少恢复屏障取得结果。
- `checkpointMs` 包含完整 `work.checkpoint` 同步调用及其 Store.save；finish 单独统计。报告的父累计只包含目标 Group。Store 中新增了增量事实认证，不能把 Store 时间直接称为磁盘 I/O，也不能与旧版 Store 的职责切分机械比较。
- 当前版本大多数配置只有一次观测，关键点两次；旧版为三次独立进程中位数。表格用于复核计算范围和量级，不构成专用机器上的统计性能承诺。
- SQLite/all/2048 第一遍与约10秒的恢复小测试重叠。它完成了全部工作，但只作完成性、计数及剩余增长的辅助证据，不用于无争用精确比较，未再重复约3分钟的该配置。
- manifest 固定源码与构建摘要。首批和复测之间，失败诊断格式化的构建发生修正；调用、固定值、CP 与 Store 的执行构建摘要未变化。新增基准文件、README及未发射的源码变动也记录在清单中，不能仅以 Git HEAD 声称完全相同工作树。

## current：旧关系不再重复处理

固定 H=1 KiB、V=64 B，每次只选最后一个孩子；作者仅检查当前 state 和该选择。

| Store  |    N | 本轮父 save 中位数 |     本轮父累计 | 旧版父累计 |
| ------ | ---: | -----------------: | -------------: | ---------: |
| Memory |  128 |           0.191 ms |        0.053 s |          — |
| Memory |  512 |           0.174 ms |        0.195 s |          — |
| Memory | 2048 |    0.150／0.153 ms | 0.671／0.672 s |   48.296 s |
| SQLite |  128 |           0.820 ms |        0.219 s |    0.295 s |
| SQLite |  512 |           0.781 ms |        0.856 s |    3.733 s |
| SQLite | 2048 |    0.757／0.747 ms | 3.496／3.469 s |   57.812 s |

N=2048 的末次 accepted：Memory 为0.146／0.152 ms，旧版24.206 ms；SQLite 为0.745／0.768 ms，旧版29.571 ms。单个末次观测容易抖动，增长曲线和独立计数比这一项更有解释力。

独立 diagnostic 中，N=128/512/2048 的父增量关系条目累计分别为256/1024/4096，等于每个孩子派发、接纳各一次。旧 N=2048 为4,198,400条全量捕获关系。

末次 accepted 的计数在三个规模下相同：

| 回调／材料                                 | 本轮次数 |
| ------------------------------------------ | -------: |
| 父 input encode/decode                     |        0 |
| 子 input encode/decode                     |        0 |
| 新子 output encode/decode                  |      各1 |
| 新 reception encode/decode/check           |      各1 |
| 当前 state encode/decode、作者 point.check |      各1 |
| 提交的变更关系                             |        1 |

接纳发生时的 check 与首次持久化往返后的 check 分别有意义；这里的1次是当前 save 内首次认证新接纳材料，没有重新检查旧接纳。

N=2048 的父累计提交量为9,485,997 B，末次2,694 B。**这是实际 delta 提交量，不是原报告中完整逻辑 image 的累计量，更不是物理磁盘写入量。** 只能据此说明本轮没有再提交全部旧正文，不能把两种字段名当成相同统计。

## 固定输入和大返回值

输入实验先建立128个孩子，再保存同一组合16次。第一次仍发布输入和全部尚未持久化的关系，后15次只提交当前 state/refs；固定不是零成本，而是改变付费时机。

| H       | Memory 16次中位数 | SQLite 16次中位数 | 旧 Memory | 旧 SQLite |
| ------- | ----------------: | ----------------: | --------: | --------: |
| 500 KiB |          0.104 ms |          0.780 ms |  8.667 ms | 18.123 ms |
| 2 MiB   |          0.100 ms |          1.883 ms | 28.495 ms | 68.574 ms |

2 MiB 独立诊断中，第一次写入128条关系；之后每次关系条目为0，input/currentInput正文提交为0，旧输入／旧输出／旧接纳的 codec/check 次数均为0。当前 state 的 codec 和作者 point.check 仍各执行一次。

SQLite 在两个 H 上仍有可见差异。没有采样将其拆到具体函数，本轮不能进一步宣称整个 Store 路径已经与输入体积严格无关。

V=16 KiB、N=128、SQLite/current 的末次 accepted 为1.721 ms，父累计0.310 s；旧版为22.336 ms和3.022 s。新输出和新接纳各自形成材料的成本仍在；已有128份输出没有每次重做。

## all：仍完整提交、读取选择，且存在 SQLite 回退

all 没有改写成增量选择。作者每步构造累计 refs 数组，每次提交完整数组，check 通过 `facts.references.children.at(-1)` 消费全部选择。数组构造在单次 CP 计时之外，在整次 run 之内。

| Store  |    N |       本轮父累计 | 旧版父累计 | 本轮末次 accepted |
| ------ | ---: | ---------------: | ---------: | ----------------: |
| Memory |  512 |          1.803 s |          — |          3.155 ms |
| Memory | 2048 |         29.205 s |  211.234 s |         15.282 ms |
| SQLite |  128 |          0.899 s |    0.382 s |          7.427 ms |
| SQLite |  512 | 11.831／11.164 s |    6.520 s | 21.170／20.652 ms |

SQLite/all/512 的两次独立结果确认了回退，不能用 current 的收益掩盖。存在以下明确的计算来源：

1. 完整 refs 数组每次产生新的持久值，需认证所有引用。
2. Store 已使用按 contextId 的索引，消除了旧 `find` 的 `O(RN)`，但仍需 `O(R)` 次引用认证。
3. 当前 SQLite 逐项认证会读取、解码每条关系的元数据。表述为“有索引”不意味着这些读取免费。
4. 作者读取完整 `facts.references.children` 仍构造 R 项查询结果；本例最后只使用一项，公开写法没有表达点查意图。

N=2048 的 all 诊断仍只提交4096个变化关系，但累计父提交为689,620,926 B；末次335,245 B，其中 references 单字段332,728 B。**旧事实正文的重编码已经消除，完整选择材料与其认证尚未消除。** 后续若收敛选择操作或访问端口，需要独立契约和测量，不能在这里偷偷省略认证或把任意只读数组当作增量依据。

## 最终构建：提交内机械优化复测

初次测量后，SQLite 在单次提交内复用 SELECT 语句及同 ID 的读取结果，并避免在引用净变化为0且材料／认证标记未变时更新原值的 metadata。复用不跨提交，不豁免完整 refs 认证，也没有改变恢复范围；固定材料仍按原逻辑预算核验。

待最终 Invocation／诊断／Store 构建完成后，另开三个独立进程复验：

| SQLite 配置                  |     优化前父累计 | 最终父累计 |  优化前单次中位数 | 最终单次中位数 |
| ---------------------------- | ---------------: | ---------: | ----------------: | -------------: |
| all，N=512                   | 11.831／11.164 s |    9.669 s | 12.330／10.862 ms |       9.367 ms |
| current，N=512               |          0.856 s |    0.730 s |          0.781 ms |       0.667 ms |
| H=2 MiB，N=128，16次输入保存 |          0.112 s |    0.084 s |          1.883 ms |       0.736 ms |

最终 all/512 末次 accepted 为18.361 ms，仍高于旧版14.255 ms；父累计9.669 s也仍高于旧版6.520 s。机械优化缩小回退，**没有消除完整选择的成本**。

H=2 MiB 的首次保存仍需72.973 ms；之后小提交的中位数下降，符合不再触及未变大正文所在行的改动方向。这是一次最终复测，不给出严格性能误差界限。

所有计数保持：growth/512 的 Group 1025 save、512个 Node 各一次save/finish、Scene一次save；输入实验 Group16次save、128个Node。没有把保存次数减少混入机械优化收益。最终三组均未与大型测试并发。

复测后又将传入 Store 的四个小提交头对象显式冻结，并加入请求不可被端口改写的断言；没有再次运行压力组。表格严格对应 manifest 中的测量构建，最后的全仓验收另覆盖这项保护，不将两者描述为字节完全相同的构建。

## 无 CP：真正形成稳定值需要多少成本

`fixed-boundary.mjs` 使用真实 Runner 三层调用；没有 CP、记录器、数据库。每种配置两个独立进程，每进程10次运行，表内为各进程中位数。原始对象每次进入都需要隔离；可信值在计时前显式固定，预固定成本另记。

| 输入              |       原始输入每run | 已固定输入每run |          预固定一次 |
| ----------------- | ------------------: | --------------: | ------------------: |
| 2 MiB文本字段     |     0.278／0.280 ms | 0.266／0.246 ms |    约0.007–0.009 ms |
| 100,000个普通记录 | 133.121／136.846 ms | 0.252／0.229 ms | 151.675／147.813 ms |

字符串本身不可变，长度大不等于逐字符复制。大对象图确实要在未知输入进入时遍历一次；已经固定的结果通过 Group/Scene 复用，不在每层复制100,000项。上述对照来自同一版本，**不是迁移前后性能比较**，也不证明大对象初次固定没有成本。

另以真实 `createConversationScene(createMaterialAnswer(), createMaterialPreparation())`、资源和实体运行；每次新建相同32条历史，固定 View，离线 Provider 返回完整 ModelReply并输出两段预览，正式追加user/assistant。两个独立进程各5次：

| 固定历史正文 |     每run中位数 |
| ------------ | --------------: |
| 128 KiB      | 1.589／1.582 ms |
| 2 MiB        | 5.764／5.722 ms |

这些服务耗时包含材料读取、Schema验证、JSON请求构造、资源操作、正式消息写入及稳定调用边界。不能全部归因于 `stableValue`；也没有模型网络延迟、并发、记忆提取或持久化性能含义。

## 容量和产物

夹具保留两条不同的拒绝验证：8 MiB单输入在进入 Store 前拒绝；4 MiB输入在完整逻辑镜像中出现两次，虽物理正文可复用，仍在增量 Store 的逻辑预算认证中拒绝，未发布候选 Group head。未为通过基准提高内核8 MiB限制。

产物根目录：`.capix/stable-facts-migration-20261107/`。

- `cp-timing/`：18组耗时、准确计划和逐次保存。
- `cp-repeat-*`：3个关键配置的第二次耗时。
- `cp-final-*`：最终构建的3个定点复测，保留优化前后两套产物。
- `cp-diagnostic-*`：6组独立计数与提交材料统计。
- `no-cp-boundary/results.json`：12个独立进程的无CP结果。

基准与无CP夹具共12项通过，覆盖保存计数、增量材料计数、逻辑／物理容量区分，以及离线服务确实完成模型请求、两段预览和正式消息追加。

本基准的 Group 恢复函数仍明确拒绝。它证明计算范围和当前性能，不替代恢复切点、认证、回执不确定及外部效果安全测试。
