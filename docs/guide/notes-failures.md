# 第 6 课：用失败检查理解边界

一次任务可能读成功、写成功，却没能把最终回答交给用户。只把执行结果分成“成功”和“失败”，不足以解释已经发生的业务变化。这一课用仓库现有验证，观察每个失败位置的真实结果。

## 先运行，再读断言

```sh
node examples/notes/verify.mjs
```

预期最后打印「便签助手验证通过：读取、写入、回答、固定值、换素材及失败分支。」其中的失败是验证主动构造并断言的预期结果，不代表命令执行失败。

文件先验证两组素材的完整运行。`verifyOfflineRun` 同时检查请求次数、读取顺序、新便签内容和最终回答；它还核对原便签没有被改写，以及传入对象后来变化不会修改已追加材料。成功判断由真实数据支撑。

然后看四个反例：

| 注入的问题                | 失败发生在哪里                 | 本例核对的结果             |
| ------------------------- | ------------------------------ | -------------------------- |
| 合法 UUID，但便签不存在   | `Notes.read` 查询实体          | 调用拒绝，便签仍为两张     |
| ID 为 `not-a-uuid`        | 工具参数校验                   | 脚本拒绝失败反馈，没有写入 |
| `append` 被替换为抛错操作 | 写入执行                       | 调用拒绝，仍为两张         |
| 第四次 Provider 请求抛错  | 写入后，生成最终回答的模型请求 | 调用拒绝，新增便签仍存在   |

前两个尤其值得一起读。格式校验只能回答“这像不像一个 UUID”；实体查询才回答“这里有没有这张便签”。离线脚本也会检查工具反馈，不能收到错误后继续编造成功文本。

## 已写入，不会因为回答失败而消失

在 `failingFinalReply` 一段中，前三轮仍交给正常脚本；第四轮明确抛出 `Final reply unavailable`。此时测试断言整个 `runner.run` 失败，同时检查 `writes.length === 1`、Notes 有三张便签、新便签仍可读回。

这给出了具体的先后关系：`append` 已安装内容，写入反馈已进入下一轮请求，生成最终回答的第四次模型请求随后失败。调用终态不会自动回滚实体。对于文件或远端服务，也不能从“最终没有成功返回”推导“外部效果没有发生”；资源自身必须说明真实提交结果。

本例既没有隐式重试，也没有恢复点。若直接重新运行 CLI，它会创建另一份内存材料，并不是接着这次失败继续执行。自动重做写入是否安全，需要另行设计业务去重或恢复依据。

## 练习：用断言解释一次失败

打开同一验证文件，找到第四次请求抛错的位置，再找到它之后对便签数量、实际正文和第四轮反馈的断言。重新运行上面的命令，预期仍通过。试着按“已经发生什么、失败在哪里、留下什么”复述这一个案例。

终端读写日志是宿主回调；这里使用的是可执行断言。若要长期记录调用事实，应另外接入[记录与观测示例](../examples/runtime.md)，不能把 CLI 文本当作内核记录或流式事件。
