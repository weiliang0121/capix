# CP 相邻保存复用验证

> 历史设计／验证记录：下文版本、测量和“下一步”保留当轮语境，不是当前兼容承诺。现行接口见 [Checkpoint](checkpoints.md)、[增量引用选择](checkpoint-selection.md)；旧格式与数据库策略见[开发期兼容](development-compatibility.md)。文档脉络见[导航](README.md)。

日期：2026-11-06。基线：`aea2c01`。本文保留两阶段结论：第一阶段定位边界和成本，未改生产实现；第二阶段实现并验证旧镜像推进依据和已固定纯值复用，见末尾。两阶段均不改 Frame v5、业务编解码或保存频率，不调用真实模型。历史正文保留已在基线完成，分叉仍是独立议题。

## 验证问题与结果

需要区分四个边界：业务活值，经 codec 编码与复制固定，成为 CP 纯值；纯值组合后还要通过完整 Frame 校验；最后由 Store 确认提交。某一层已成立的证明，不能自动替代下一层的证明。

[复用边界测试](../test/checkpoint-reuse-boundaries.test.mjs) 使用真实 Invocation、父子关系、保存和 MemoryCheckpointStore，而不是用模拟函数代替 CP 链路。候选缓存只以命中条件作反例对照，不进入运行路径。

| 验证                                                | 实际结果                                            | 对候选缓存的约束                        |
| --------------------------------------------------- | --------------------------------------------------- | --------------------------------------- |
| returned/reception 引用不变，嵌套返回值及接纳值改变 | 两次 CP 正文不同，旧镜像仍保持原值                  | 两个关系引用不足以认证完整子项不变      |
| 首次保存后修改嵌套原输入                            | Store 拒绝第二次推进，原 head 保留，调用不再 finish | 缓存第一次 input 会隐藏现有固定输入检查 |
| 返回后、首次保存前改变结果                          | 首次 CP 捕获改变后的值                              | 首次保存时缓存不等于返回时固定          |
| codec 解码出 Date，点检查冻结后修改 Date            | 下一次检查获得独立、正确的 Date                     | 冻结外壳不能保证任意业务对象可共享      |
| 恢复时 decode 规范化正文，随后再次 encode           | 新 CP 可与原子交付编码不同，准确关系仍保留          | 不能假定现有 codec 有字节恒等往返规则   |
| 输入、输出及 codec 对象冻结，但 encode 使用外部版本 | 关系引用不变，两次编码结果仍不同                    | 值冻结不能证明 codec 纯度或确定性       |

这些测试刻画当前边界，不推荐作者原地修改结果或编写依赖外部变化的 codec。是否收紧这些行为，需要单独确定契约。恢复测试使用保存前缀建立新的 Store 并走真实恢复，不声称完成进程崩溃实验。

相邻回归同时覆盖整个镜像认证、整体容量、返回/接纳、handled、存储损坏、历史正文退休、提交失败和回执丢失。失败后的测试仍要求停止调用，不把复用设计变成同次调用自动重试。

## 性能测量方法

复用现有 `examples/tool-host-study/run.mjs`，实际经过宿主、Runner、串行 ToolLoop、Interaction 和 SQLite，仅模型传输使用离线替身。新增 `--cpu-profile`，通过 Node Inspector 在每次 `entry.run` 前后采样，不改写源码或 dist，不注入生产端口。模型完成后的维护仍正常运行。

原始 V8 profile 保留，汇总按完整调用栈互斥分类。旧 head 的解压/认证归旧 head 读取，子关系 codec/复制归捕获，新镜像存储 JSON/Brotli 归存储编码；不会重复累加嵌套工作。GC、idle、未分类及脚本统计字节的工作单独保留。未分类包含模型协议、实体等正常执行，不能都算成 CP。分类器的三项合成测试检查覆盖总量、嵌套归属和无法识别的样本。

`sampleMs` 是按 V8 `timeDeltas` 加权的采样估计，不是每阶段精确 CPU 或 wall time，也不是调用次数。原生工作只有在调用栈保留归属时才分配到阶段；采样启动和停止有少量边界开销。`cpuMs` 是入口区间进程 CPU；Store 的 save/finish 同步耗时另外精确计时。采样增加开销，不是优化版本，不能将两组差值视作优化收益。

本轮发现并修正了旧测量脚本的 finish 计时：它原先在 JSON 字节统计后才取结束时间；现在与 save 一样，在 Store 返回后立即固定耗时。早期报告数字保留，但其 Store 合计的 finish 部分略含测量工作。本报告正式样本在修正后重新运行，先前诊断样本不混入统计。

三对基线/采样依次执行，使用独立进程、新数据库和新输出目录；不与测试、构建或其他压测并行。第一对包含小、中、大三个样本，后两对只复测最大样本。Node 22.23.2，arm64，本地机器；不清理系统文件缓存，不代表服务器吞吐上界或长期稳态。

正式产物：`.capix/cp-reuse-study-20261106-153447/`。首轮诊断产物 `.capix/cp-reuse-study-20261106-153141/` 仅用于发现计时问题。两者均使用新实验数据库，不访问本地对话库或凭证。

## 本轮决策边界

关系状态身份可以作为关系变更依据，不能单独作为完整业务内容的复用依据。先评估已固定编码纯值和已提交镜像的重复处理；跨次跳过业务 encode/decode，必须先明确固定时机、codec 法则和恢复后的解释。

Store 缓存尚未实施或证明。若下一步评估上一份镜像复用，必须保留准确 head/镜像身份、修订、终态和损坏检查，明确缓存失效与容量；只读 revision 不能自动证明正文完整。整份镜像组合仍须核对全局关系、refs、深度及累计容量。

本轮没有修改保存频率或存储格式，没有实现差量 Frame，也没有证明任何候选缓存的提速。完整镜像的序列化、压缩及写入依然存在；下一步按已测成本选择一个不改变业务固定语义的小闭环。

优先候选是 Store 上一份镜像的重复解码/认证，以及 CP 包对已固定纯值的重复遍历。前者要先设计缓存与实际持久事实的对应依据，后者要保留完整镜像的组合校验；都不能用缓存静默改变业务值的固定时间。跨次业务 codec 缓存、缓存后峰值内存和真正的性能收益仍未验证。

## 第二阶段：两个候选的实现与验证

在上述反例约束下，实现范围限定为两个已有模块内部的复用，不增加作者配置或新的运行实体。以下结果取代第一阶段中“候选尚未实施”的状态；第一阶段的反例和成本定位保留。

### Store：复用已提交镜像的推进依据

实现位于 [新服务 SQLite CP Store](../services/conversation/src/persistence/checkpoints.ts)。save/finish 并不需要旧 Frame 的全部子关系，只需要确认真实 head、终态、固定 owner/contract/input 和 revision。因此缓存保留完整 SQL 行与这些推进依据，不保留旧 Frame/子树。

每次推进仍走以下路径：

```text
读取实际 SQL 行并检查行形状
  → 与缓存的所有字段比较（包含 body、delivery、两侧身份和修订）
  → 完全相同：复用已核验的推进依据
  → 不同或未命中：完整解压、解析、认证并核对 head
  → 原有固定字段比较、CAS、压缩新镜像、同步事务
  → 事务真实返回后安装新的推进依据
```

revision 相同不足以命中。正文、关联镜像或终态被改变时仍会重新核验。公开 read/listRoots 始终完整解码，不从该缓存构造恢复镜像。数据库触发器在插入时改写正文，也不能让新行与旧依据无条件配对：下一次读取会发现行不同。

生命周期有界：每个 Store 最多 64 项，按完整行字符串和固定依据的编码大小计费，合计不超过 16 MiB；LRU 淘汰不影响正确性。提交失败或 finish 释放对应项，宿主关闭清空全部项。这个计费值不包括所有 JS 对象开销，不能称作精确堆配额。首次依据按实际 JSON 存储语义建立：例如 `-0` 读回 `0` 后仍沿用原先的严格比较行为，不能因为缓存保留了写前对象而改变拒绝条件。

这项缓存只接入新对话服务的 SQLite 实现。旧 Observer 的 Store 保持原路径。完整 SQL body 仍需读取和比较，不宣称推进核验成为 O(1)。

### 纯值：复用 CP 自己固定的准确根

实现位于 [checkpoint/value.ts](../server/checkpoint/src/value.ts)。纯值成功复制、深度冻结并通过 JSON 容量检查后，私有 WeakMap 仅给产物根记录三个统计：节点数、估算字节、相对深度。后续组合遇到准确同一对象，可直接引用冻结值并累加统计。

- 原始业务输入、调用者自己 freeze 的对象、反序列化值和包裹代理都不能继承证明。
- 同一值出现两次，数量和字节计两次；嵌套位置改变后重新计算整体深度。
- JSON 编码后的 8 MiB 检查、完整 Frame 的关系、顺序、refs、continuation 校验继续执行。
- 只记录成功产物根，不给全部后代建立缓存，不保存第二份 JSON 文本。WeakMap 不延长产物寿命。
- 不缓存业务 encode/decode、point.check，也不把“首次保存时固定”改成“返回时固定”。

因此，`cloneCheckpointValue` 可能共享本包已经固定的值身份；对未知业务对象仍独立复制。第一阶段的六个反例在候选下仍须成立。

### 四组性能对照

产物：`.capix/cp-reuse-candidates-20261106-155132/`。Node 22.23.2、arm64、本地同一机器，沿用真实宿主链路与离线 Provider。没有访问服务对话库或凭证。

### 收敛结论

两个候选都值得保留：Store 对真实持久行的检查保持完整，但不重复展开已验证的旧镜像；CP 只复用自己证明过的纯值，不越过业务固定边界。全量新镜像 JSON、摘要、Brotli、SQL 提交、子关系捕获和业务编解码仍然存在。

这一轮到此闭环。后续若再评估捕获/解码成本，应继续以第一阶段反例为门槛，不从引用相同推断业务内容不变。差量 Frame、减少保存次数、跨次业务 codec 缓存与历史分叉仍是独立议题。

最终验收：`pnpm check` 通过，全仓构建、类型检查、3,101 项测试（0失败、0跳过）及格式检查全部通过；独立复审未发现阻塞问题。代码与文档未提交，实验数据库及构建对照保留在被忽略的 `.capix/`。

## 第三阶段：父层保存集中度与合并边界复核

对后续交叉评审的接纳：第一阶段只按计算阶段分解，确实欠缺按业务父层的分布。评审引用的是第一阶段基线，不能代替第二阶段已经完成的候选对照；但它指出的 ToolLoop 热点成立，应成为下一项保存粒度分析的对象。本阶段只核对实现并补充离线测量，未修改生产保存点或恢复契约。

### 成本确实集中在 ToolLoop

核对 `cp-reuse-study-20261106-153447/baseline-2/eight-models-32-slots.json` 的逐次保存数据：

| 项目                 |      ToolLoop |                   全部调用 | ToolLoop 占比 |
| -------------------- | ------------: | -------------------------: | ------------: |
| save 次数            |           465 |                        742 |        62.67% |
| 累计 CP 逻辑 payload | 365,278,426 B | 399,717,665 B（含 finish） |        91.38% |
| Store 同步耗时       |       4.905 s |                    5.353 s |        91.63% |

465 次准确分解为：8 次模型派发前的 `model-waiting`、8 次模型接纳后的 `tools`、224 次工具派发前的 `tools`、224 次工具接纳后的 `tools`、1 次 `completed`。两个工具边界都使用 `tools` 点；不是一个 waiting 点与一个 processing 点可以直接按名称二选一。

ToolLoop 自身最大镜像 1,056,092 B；前文全局最大 2,799,139 B 属于上层 Scene，不能混同。基线库里 ToolLoop 当前 body 长度为 28,615 字符，所有当前 image body 合计 183,425 字符；这是 Brotli/base64 封装后的字符串长度，不含 delivery、索引、其他表和 WAL，不能称作整个数据库占用。累计逻辑 payload 与现存压缩正文衡量不同的成本。

组合优化后的 `combined-3` 次数和字节不变，ToolLoop Store 耗时为 1.452 s，占总计 1.706 s 的 85.12%。因此热点仍值得处理；缓存收益也已经存在，两者不是互相排斥的方向。

### 固定材料与模型次数，只改变工具数

补充产物：`.capix/cp-loop-review-20261106-164605/`。实验副本复用同一测量脚本，仅替换离线计划并定位原 helper，保留原脚本摘要与生成副本。使用当前两项组合优化后的构建，固定输入材料为 32 KiB、工具模型请求 4 次、维护请求 1 次、同一历史内容及每工具读取范围；前三次模型回复各请求 1/2/4/8/16/32 个工具，最后一次返回正文。每档三次独立进程与新数据库，交错正反顺序，无 CPU 采样。

### 为什么不能直接改为每模型轮保存一次

现有工具执行路径为：

```text
创建子调用与准确 ref
→ 父 CP 保存派发关系
→ 工具执行、子结果持久化
→ 父接纳并固定写入工具反馈
→ 父 CP 保存 accepted/handled 与 cursor
→ 下一工具
```

1. **删除派发前保存：** 工具已经产生效果或反馈，而旧父 CP 没有该 childContextId/ref。`confirmExchanges` 会拒绝“反馈没有准确工具子关系”。模型 toolCallId/同名 key 不能代替调用身份；新建子调用的固定接纳 operation 也不同。可读取模型 Interaction 反馈，并不能证明所有工具资源效果可重新执行。
2. **删除接纳后保存：** 对成功子结果，可研究从原 waiting ref 读取成功终态、再确认固定反馈。但对已处理失败，旧父仍是 waiting、子 head 已 failed，`resolveCheckpointChild` 明确拒绝；反馈槽位存在不能代替父 CP 的 handled 事实。若延迟保存，就是扩大该区间的不可恢复窗口，须明确业务承诺。
3. **提前创建整批子关系并保存：** 也不能自动解决。未启动子调用没有自己的首个 CP；现有等待恢复不把“没有 CP”解释成“肯定未执行”。需要另外证明计划与实际执行的区分，不能无条件把所有 waiting 重新启动。

来源：[ToolLoop](../services/conversation/src/tools/loop.ts) 的 `receiveTool`、`processTools`、`confirmExchanges`，以及 [子恢复](../server/invocation/src/checkpoint/children.ts) 的 `resolveCheckpointChild`。现有测试已覆盖保存前缀恢复、handled 事实、未知派发及缺首个子 CP 的拒绝；本阶段未声称完成删点版本的故障注入验证。

更窄的候选是合并相邻边界：例如最终无工具回复的接纳后 `tools → completed`，或成功工具接纳后与下一工具派发前的两次保存。后者之间目前存在 `await preflight`，仍有让出与失败边界；不能仅因代码位置相邻就视为等价。失败 handled 的及时保存需要单独保留/论证。局部合并大致减少常数成本，不自动消除 O(n²)；按模型轮批量保存才会触及更大的恢复粒度变化。

### 评审中需修正的判断

- 当前 Store 缓存不只核对 `{imageId, revision}`，而是比较实际完整 SQL 行，正文或 delivery 同修订改变也会被发现；不退回更弱命中依据。
- 分类器每个采样只归一个阶段，嵌套认证没有重复累加。Invocation 传给 Store 的同一完整 image 已命中 WeakMap，不再第二次全量认证；磁盘解码产生新对象的认证归旧 head 读取。采样没有 contextId，不能把各阶段百分比精确分配到某一调用。
- “采样开销可忽略”没有证据。首对小、中样本的采样时间分别高约 9.5%、7.5%，大样本又有方向相反的波动；仍按前文保留扰动限制。
- model-provider 等其他成本继续独立，不计入 CP 的收益预期。

后续建议：保留已经验证的两项复用；下一小闭环先列出相邻保存点合并的崩溃与恢复矩阵，再比较减少的保存量和恢复窗口。不因热点集中就先接受“465 → 约16次”的恢复承诺变化。

后续验证已完成第一版，见 [恢复承诺与保存组合验证](checkpoint-recovery-coverage.md)。真实进程中断确认：省略派发前保存可能重复工具效果，省略 handled 保存缩小恢复覆盖；最终回复与预检拒绝的两个窄候选在所测组合中保持基线承诺。生产保存点仍未修改。
