# Checkpoint 恢复承诺与保存组合验证

> 历史设计／验证记录：下文版本、测量和“下一步”保留当轮语境，不是当前兼容承诺。现行接口见 [Checkpoint](checkpoints.md)、[增量引用选择](checkpoint-selection.md)；旧格式与数据库策略见[开发期兼容](development-compatibility.md)。文档脉络见[导航](README.md)。

日期：2026-11-06。对象是当前 ToolLoop 的有限恢复，而不是任意程序或所有框架的最小检查点定理。本轮保留生产保存点，只在测试装配中删去特定作者保存调用，再用真实持久数据和新进程验证。此前已完成的纯值/Store 复用与性能结果见 [CP 复用验证](checkpoint-reuse-validation.md)。

## 从承诺反推边界

保存次数不是恢复强度的充分指标。需要分别验证：

| 维度               | 验收条件                                                                     |
| ------------------ | ---------------------------------------------------------------------------- |
| 安全性             | 不重发已有模型请求、不重复已落实工具效果、不把失败伪造成成功或补造父子接纳   |
| 覆盖范围           | 对承诺可继续的中断位置，真实恢复完成；明确拒绝只能满足安全性，不能算恢复成功 |
| 允许重新计算的内容 | 固定反馈确认与纯映射可以在约定窗口重做；单独记录次数，不把重算称为完全等价   |
| 完成条件           | 模型与反馈槽位、实际工具效果、父层 accepted/handled、最终交付相互对应        |

可选检查点是业务恢复策略的一部分。粗粒度配置可以明确缩小范围，但必须拒绝范围外的危险重做；简单删掉保存点，不会自动获得这项安全拒绝能力。没有 CP、缺首个子 CP、模型反馈未知、终态及契约变化等条件，仍按现有机制判断，不能把缺失解释成“肯定没执行”。

“批次中途不恢复”还需要可判定的依据：例如已保存的在途标记、准确效果凭据或宿主资格检查。若只保留上批次末尾的 CP，系统可能无法知道下一批次已经产生了效果。没有这类依据，不能自动从旧 CP 继续，也不能把事后文字声明当作安全门控。本轮没有为此新增内核机制。

## 有限场景与持久事实

场景使用真实 Scene → ToolLoop → Node 结构、资源操作、独立模型 Interaction、ModelExchanges 及 SQLite CP。模型传输是确定性的离线替身：第一次回复请求成功工具、可处理失败工具和未知工具；第二次返回最终正文。工具不是全部只读：成功工具向独立存储写入一次效果，使重复执行可被发现。

效果按准确工具调用身份留下凭据；同一调用恢复可以确认已存在的效果，新的调用身份不能被当作原调用。该工具的初始恢复点只确认原效果，未知则拒绝；完成恢复点交付原值。这是夹具明确提供的业务工具恢复契约，不代表任意资源写入都可恢复或具备幂等能力。失败工具在运行后抛出可处理业务异常，ToolLoop 保存真实 failed/handled；未知工具由固定预检政策生成反馈。

| 事实                               | 持有者                     | 不能代替的事实                      |
| ---------------------------------- | -------------------------- | ----------------------------------- |
| 固定模型请求、最终反馈             | Interaction / 宿主持久端口 | 工具效果及父子接纳                  |
| 已生成回复、工具反馈、准确接纳凭据 | ModelExchanges             | 未保存的父直接子关系和 handled 状态 |
| 工具效果与确认凭据                 | 工具业务资源               | 父层是否接纳及下一步进度            |
| 子身份、直接关系、进度与接纳状态   | 调用 CP                    | 跨实体统一事务或未保存的业务事实    |

这些存储分别提交。测试必须覆盖它们之间的间隙，而不是只在 `checkpoint()` 返回之后中断。

## 试验方式

测试在 build 前装饰 ToolLoop 的 run 与各 point 的 resume.run，向原处理函数传入同形状的 Work，仅在候选位置省略 `work.checkpoint` 调用。点身份、codec、refs、原处理逻辑和恢复检查不变。

这不是在 Store 丢弃写入后返回成功回执：所有实际提交仍由真实 Store 完成并进行 CAS。过滤会在恢复路径中继续生效，二次中断不会悄悄退回更密集的保存策略。此入口只存在于测试夹具，没有新增生产策略开关。

矩阵使用自定义 `test.matrix.scene` 和直接 `Runner.resume`，没有经过 CLI/Web 的 `createConversationHostAssembly` / `assertToolConversationRecovery` 宿主资格预检。因此结论是这套工具场景与原语的覆盖证明，不能直接称为生产宿主覆盖证明。省略作者保存也省去了该次保存触发的 codec/check 执行；保持原函数实现，不等于其执行次数不变。本夹具使用固定纯映射与 codec，不能据此替任意依赖外部状态的检查作等价承诺。

每个切点使用子进程直接退出，绕过异常捕获与 finally，随后由新进程载入原数据库恢复；不是把普通抛错当作进程崩溃。不模拟掉电、文件系统损坏或远端进程故障。独立效果/审计存储与 CP/交互的边界不构成事务。

对拒绝分支检查模型请求、工具效果及交换事实没有新增；恢复失败收尾可能写入失败终态，不要求所有 CP 字节不变。对完成分支检查每个逻辑工具效果只发生一次、请求没有重发、槽位没有重复、最终回答正确，并区分映射重算。

## 候选与证明范围

先穷举两个窄候选的四种组合：保留/省略最终回复接纳后紧邻 completed 的保存，以及保留/省略预检拒绝后的中间保存。再以成功接纳、handled 接纳、派发前保存和整批保存作为挑战组。

最小性只相对于这组场景、切点与候选集合。即使某组合全部通过，也不证明所有输入、任意 codec、任意工具实现或任意调度下等价；没有覆盖的契约必须明确保留。若删除某点出现反例，它证明该点承担了职责，不证明只能以当前这次 save 来承担。

生产迁移另需确认是否扩大纯映射重算窗口、是否改变预检/恢复资格，以及业务 CP 契约版本如何处理。本轮结果首先用于选择下一闭环，不直接减少生产保存次数。

## 实测矩阵

夹具：[tool-checkpoint-matrix.mjs](../test/fixtures/tool-checkpoint-matrix.mjs)。正式回归：[checkpoint-recovery-coverage.test.mjs](../test/checkpoint-recovery-coverage.test.mjs)。离线探针原始数据保留在 `.capix/cp-recovery-matrix-20261106-172516/`，每格使用新库并先后启动 crash/resume 两个进程；8 种策略 × 14 个切点，共 112 格。无凭证、真实模型或服务数据库访问。

过滤标记只表示“试验中省略哪一类作者保存”，不是生产 API：`dispatch` 为工具派发前，`success` 为成功工具接纳后，`handled` 为失败已处理后，`rejected` 为预检拒绝后，`final` 为最终正文接纳后的 tools 点（保留紧邻 completed 点）。`batch` 为省略 dispatch/success/handled/rejected 的负例。

| 中断切点                             | 基线                 | 同时省略 final/rejected | 关键依据                                    |
| ------------------------------------ | -------------------- | ----------------------- | ------------------------------------------- |
| 成功工具派发关系已存，首个子 CP 未存 | 拒绝                 | 拒绝                    | 缺首子 CP，不能猜测未执行                   |
| 成功工具效果已写，完成 CP 未存       | 继续                 | 继续                    | 本夹具 prepared 点可确认原调用的效果凭据    |
| 成功子交付已存，反馈尚未写           | 继续                 | 继续                    | 原子交付及准确父子关系                      |
| 成功反馈已存，父接纳 CP 未存         | 继续，纯映射重算一次 | 同左                    | 用原交付、原 operation 确认反馈，不重做效果 |
| 成功父接纳保存位置之后               | 继续，映射不重算     | 同左                    | accepted 与固定凭据已保存                   |
| 失败工具派发关系已存，首个子 CP 未存 | 拒绝                 | 拒绝                    | 缺首子 CP                                   |
| 失败子交付已存，反馈尚未写           | 拒绝                 | 拒绝                    | 不复活失败子调用                            |
| 失败反馈已存，父 handled CP 未存     | 拒绝                 | 拒绝                    | 反馈存在不能补成父 handled                  |
| 父 handled 保存位置之后              | 继续                 | 继续                    | 真实 failed/handled 事实                    |
| 预检拒绝反馈刚提交                   | 继续                 | 继续                    | 固定政策与反馈槽可重复确认                  |
| 预检拒绝后的保存位置                 | 继续                 | 继续                    | 同上；候选在此不保存                        |
| 最终模型反馈已持久化                 | 继续                 | 继续                    | 原模型引用与持久反馈，无新发送              |
| 最终模型接纳后的 tools 保存位置      | 继续                 | 继续                    | 候选用原模型交付重新确认接纳                |
| completed 镜像保存后，根终态之前     | 继续                 | 继续                    | 完整完成事实                                |

这里“保存位置”指业务代码走到同一位置，候选可能省略保存；测试不会把未提交的事实说成已提交。基线的 4 个拒绝位置是当前已知覆盖边界，不因候选数量更少而隐藏。最终根交付已经保存后再次 resume 明确拒绝。

### 不同候选的结果

| 策略                  | 14 切点恢复结果        | 语义变化                                                   |
| --------------------- | ---------------------- | ---------------------------------------------------------- |
| baseline              | 10 继续 / 4 拒绝       | 参照承诺                                                   |
| 省 final              | 10 / 4                 | 本矩阵未发现覆盖或业务效果变化                             |
| 省 rejected           | 10 / 4                 | 本矩阵未发现覆盖或业务效果变化                             |
| 同时省 final/rejected | 10 / 4                 | 同上；构成两个窄候选的全部四种组合                         |
| 省 success            | 10 / 4                 | 成功接纳位置中断后，纯成功映射由一次变两次，效果仍一次     |
| 省 handled            | 8 / 6                  | handled 后及下一预检反馈后的两个位置新增拒绝               |
| 省 dispatch           | 12 次流程完成 / 2 拒绝 | **不是安全扩大覆盖**：两处效果重复，一处已失败工具重新执行 |
| batch                 | 6 次流程完成 / 8 拒绝  | 其中两处效果重复，且多个原可恢复位置丢失                   |

最重要的安全反例是：

```text
旧父 CP：模型已接纳，但没有工具 ref
→ 新工具调用产生效果
→ 反馈尚未保存时进程退出
→ 恢复读取旧父 CP，看不到原工具关系或反馈
→ 创建新的工具调用身份
→ 同一个业务效果再次执行
```

实测 effects 为 1 → 2，两个 contextId 不同，而模型请求仍然只有 tools/final 各一次。到了反馈已经提交的切点，恢复才会因缺准确子关系拒绝。因此“Interaction 不重发”并不足以证明工具效果不重复；“删点后只是少几个可恢复位置”也不是普遍结论。

### 局部最小性与范围承诺

无中断基线共 18 次 save，其中 ToolLoop 10 次；同时省 final/rejected 后为 16 次，其中 ToolLoop 8 次。成功效果、失败事实、三份工具反馈、两次模型请求与最终回答均一致。这是固定的小场景，不把 20% 的父层保存减少直接推广为密集样本的性能收益。

在“保持基线可恢复切点，且不扩大成功映射重算范围”的要求下，这个 8 次组合是**本轮五类候选和切点内的局部不可再删组合**：从它再删 dispatch，出现重复效果；再删 handled，失去原覆盖；再删 success，扩大映射重算范围。正式测试包含这些从已缩减组合继续删点的反例。它不证明全局最小，也没有证明其他未纳入候选的模型边界无法合并。

如果业务明确接受更宽的纯映射重算窗口，success 就成为可继续评估的选项，而不是内核统一强制保留。这需要把恢复后的编解码、映射确定性及固定反馈核对纳入契约，不只比较效果次数。保留或省略 CP 的意义由这组承诺确定。

正式回归还对四种窄策略执行连续进程中断：effect-after → 恢复后 rejected-checkpoint → 再次恢复后 final-processing → 最终恢复。恢复阶段确实继续采用同一过滤策略，效果只发生一次；根终态之后再次恢复被拒绝。声明没有获得任意位置恢复承诺。
