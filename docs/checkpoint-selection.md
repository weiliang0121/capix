# Checkpoint 的增量引用选择

本轮处理作者每次重新提交完整 `refs` 数组的成本。Context／Relation 仍持有已经成立的调用事实；选择只表达作者打算在恢复点使用哪些孩子，不决定哪些孩子属于事实，也不扩大恢复范围。

## 作者写法

```ts
const selected = work.checkpoint.select(node);

const call = work.children.create(node, input);
const occurrence = selected.add(call.ref);
work.checkpoint({ point: waiting, state, refs: { children: selected } });

await call.invoke();
work.checkpoint({ point: received, state: nextState, refs: { children: selected } });

// 只移除这一次出现；关系、返回和接纳事实都仍保留。
selected.remove(occurrence);
```

`select` 属于本次调用的 checkpoint 写端口。创建选择不写入存储，`add` / `remove` 改变待保存的选择；准确保存回执到达后，内部才推进已提交依据。没有安装 CP 时没有这个端口，普通业务仍可使用自己的数组。

同一选择可以显式传给多个兼容恢复点；恢复点不会隐式继承上一个点的槽位。每次保存仍核对槽位名、one/many 和固定子声明位置。不同调用的选择、不同声明的孩子、伪造的出现项都不能混用。

原来的单引用不变。many 接受两种有不同含义的输入：

| 写法                           | 含义                   | 提交成本                 |
| ------------------------------ | ---------------------- | ------------------------ |
| `refs: { children: [a, b] }`   | 完整替换当前选择       | 按完整数组处理           |
| `refs: { children: selected }` | 使用这份选择的当前版本 | 按新增、移除的出现项处理 |

这是有序列表，重复的孩子引用有各自的出现项凭据。`add` 追加并返回凭据；`occurrenceAt(index)` 可取得已有项凭据；`remove` 只删指定项。首版不增加任意插入或排序方法，需要整体改序时显式给出完整数组。

## 恢复与查询

```ts
resume: {
  uses: [node],
  async run(work, state, saved) {
    const selected = work.checkpoint.select(node, saved.children);
    const first = selected.occurrenceAt(0);
    if (first) selected.remove(first);

    const child = work.children.create(node, nextInput);
    selected.add(child.ref);
    work.checkpoint({ point: waiting, state, refs: { children: selected } });
    return child.invoke();
  },
}
```

`saved.children` 保持只读数组接口。它携带本次恢复的准确选择依据，`select(node, saved.children)` 据此接续原选择。传入自己复制或新构造的数组表示首次导入，不根据正文相等猜测选择身份。

`point.check` 中的 many 也是只读数组查询接口：`length`、索引和 `at(-1)` 按实际访问取值，不因为只读最后一项而构造全部事实。遍历、`map`、`find` 等仍承担相应读取成本。查询仅在本次同步 check 内有效；已取出的稳定事实值仍可保留。恢复数组的访问受恢复 Work 窗口约束。

当前有序选择以链表维护出现项：首尾访问为 O(1)，顺序访问合计 O(R)，任意位置跳转最坏 O(R)。这不是一个承诺任意随机下标 O(1) 的持久向量；收益来自保存时无需读取旧项，以及常见的末项查询不扫描历史。

## 持久边界

物理保存分别表达：当前 head 选用了哪些选择版本、这次哪些出现项新增或移除。每个出现项保留独立身份、追加顺序及准确孩子引用；删除不会删除孩子关系。完整数组替换沿用完整处理路径。

选择变化与 CP head 使用同一 Store 提交和 revision 比较。对新增项核验真实父子身份、round、order 和固定声明位置；删除核对准确出现身份、顺序及原引用。提交失败或回执不确定不冒充已成功推进。选择并不提供资源效果或跨实体事务。

冷读取完整重建逻辑 `references`，重新检查选择汇总、出现项、关系及容量；可序列化的恢复依据不以进程内对象身份作为信任来源。逻辑 Frame v6 的全部关系与 refs 语义保持不变，8 MiB／值节点／深度限额仍按逻辑出现次数计费，不以紧凑物理表示放宽。

Conversation SQLite 当前存储版本为 8，包含选择与出现项表；新库直接创建，旧格式不迁移。Observer 在自己的 CP 表旁使用同义表。删除的出现项保留身份与顺序墓碑以拒绝复用；未被当前 head 选择的已发布集合仍可在同进程稍后显式重选。冷恢复只取得当前 head 选中的集合，不恢复业务闭包中其他选择句柄；核验选中集合时仍检查其历史墓碑。终态不自动退休这些行，本轮不承诺总存量或冷读取成本恒定。

## 收益的边界

- 热保存不再为未变化的累计选择重新编码全部引用。
- 同一选择跨兼容恢复点使用，不重新复制历史。
- `state` 仍按作者提交的完整内容编码；`point.check` 仍每次执行。
- 作者全量遍历、冷恢复、完整数组替换仍是全量工作。
- 选择和关系的总存量仍随实际历史增长。本轮没有加入自动分段、隐式退休或 continue-as-new。

ToolLoop 使用增量选择保存模型和工具引用，原有业务检查与恢复核对保留。因此减少 refs 提交不等于其所有历史检查都已增量化。

## 验证结果（2026-11-07）

增量选择完成时，构建、类型检查与全仓 3,379 项测试通过，格式检查通过。下列数字和基准记录该阶段；其后的仓库收尾移除了旧格式兼容与迁移，当前支持范围见 [开发期兼容边界](development-compatibility.md)。此次增加或适配的验证包含：

- 作者类型与真实 Runtime：单引用、完整数组、增量选择可组合；准确声明位置、调用归属、point 布局不能绕过。类型负例覆盖不同孩子、one/many 和伪造选择。
- Invocation：重复出现、精确移除、无变化保存、跨点使用、保存时禁止改动、错误被作者 catch 后仍受保护；回执丢失不推进热依据；冷恢复拒绝正文相同但身份或 revision 被替换的选择。
- Memory、Conversation SQLite 与 Observer SQLite：选择与 head 一起比较提交，事务失败回滚，出现项篡改／墓碑缺口被拒绝，混合槽位与重复别名的完整逻辑容量不被低估。当时的 v7→v8 迁移验证在后续收尾中替换为旧库无损拒绝验证；当前不提供该迁移。
- 既有 ToolLoop 恢复切点矩阵 80/80 通过，保存点、保存次数与原有拒绝反例不变。
- 真实双进程：第一进程保存重复项，移除一个旧项并追加新项，在 Store 提交后立即退出；第二进程冷恢复，继续移除／追加并跨 point 保存。效果文件恰好为 `a\nb\nc\n`，首次续存只提交一个新增项和一个移除项，下一次切点没有选择变化；已保存效果没有重跑。

最后一次公开出口收口仅移除了两个内部 helper 的重导，改用真实公开 Store 路径验证精确容量；checkpoint 重建及对应 20 项存储测试再次通过。

### 相同工作量的独立计时

环境为 Apple M3 Max、Node 22.23.2、SQLite 3.51.3。H=1 KiB、V=64 B，N=128／512／2,048，每个配置两次独立进程、新 Store／新库；第二轮反转运行顺序，不与构建、测试并行。28 个样本全部完成。

两种模式使用同一份当前实现：`all` 每次完整传入引用数组，`incremental` 追加到选择；两者都用 `at(-1)` 检查最后项。每个孩子仍保存派发前和接纳后两个点，父层最后再保存 completed。因此父保存为 `2N+1`，全树 save 为 `3N+2`，finish 为 `N+2`，逐样本均已核对。没有减少安全屏障或更换返回材料。

在这个固定工作量下，完整 refs 的单次成本随历史增大，增量选择的单次成本基本持平；收益也体现在整次 run，没有仅把扫描搬进 `add`。这不证明任意 state、任意 check 或所有工作负载都具有相同收益。

另开 diagnostic 进程观察实际 SQL 点查和提交，不使用其耗时。下面的“非空关系行”是 JS/SQLite 返回行的次数，不是物理磁盘读取；选择与出现项查询均为点查，仍承担数据库索引成本。

增量模式中，接纳后和 completed 保存都没有选择变更，仍正常提交相应调用事实；父关系变更数始终为 `2N`。新增项的真实关系认证仍执行，没有用缓存身份跳过来源检查。

全量 check 负对照 N=128 仍执行 257 次作者检查，并读取 16,640 条历史关系；局部检查不执行这段遍历。两者提交的新关系、选择变化和保存次数相同。这明确保留了剩余边界：**增量选择不会使作者主动遍历的历史免费。**
