# 稳定交付值：契约与迁移验证

> 历史设计／验证记录：下文版本、测量和“下一步”保留当轮语境，不是当前兼容承诺。现行接口见 [Checkpoint](checkpoints.md)、[增量引用选择](checkpoint-selection.md)；旧格式与数据库策略见[开发期兼容](development-compatibility.md)。文档脉络见[导航](README.md)。

日期：2026-11-06。状态：**迁移目标与实验报告，尚未替换生产交付契约**。

后续见 [稳定事实与增量检查点实验](stable-facts-head-validation.md)：逐节点计量已替换本报告中的整次成本证明，新增独立 fact/head 存储模型和规模/恢复验证。本报告保留当时的迁移盘点与结论，不把旧全仓通过/失败数量当作新算法的兼容性结果。

本轮按“修正固定算法 → 明确稳定值及复用边界 → 自动调用边界盘点 → 恢复切点验证”的顺序推进。生产 Invocation、实体、资源、Frame 和作者类型均未修改。既有工作树中的 CP 缓存与性能研究改动保留；全仓基线和迁移对照使用同一份工作树、同一次构建，不将这些前置改动的效果归于本轮。

## 1. 结论

建议将以下规则作为正式迁移目标：

> 调用消费和交付的是稳定的数据内容。未知数据在边界隔离，可信稳定值直接复用；业务加工产生新值。内容固定不等于成功交付，也不等于持久保存。

本轮已经证明：

- 首次固定不需要沿 DAG 重复展开；单次记忆表可保留安全共享。
- 稳定输入必须在资源 capture/refine 前形成，不能只在 Context 构造后补做。
- 返回候选在内核取得后、等待接纳和关闭 Work 前固定；父接纳正常值和失败替代值共用固定边界。
- 自动插入可以保持取消、关闭、受保护故障和已有 CP 恢复的关键区别。
- 实体生产者与调用边界使用同一可信机制时，可以直接复用内容；不需要公开认证注册表。
- 当前全仓有真实的兼容迁移面，不能将这一变更当作不改变语义的缓存优化。

尚未证明或完成：生产只读类型迁移、任意富对象交付、生产持久编码格式、所有公开组合的兼容、单次 CP 增量计算。**稳定值是增量保存的前提，不是增量保存本身。**

## 2. 契约归位

### 2.1 数据成立的位置

| 数据                  | 固定边界                                            | 后续变化                                  |
| --------------------- | --------------------------------------------------- | ----------------------------------------- |
| 调用输入              | 首次 validate/capture/refine 等相关消费前           | 同次调用内不变；调用者自己的原草稿可变    |
| 返回候选              | 内核取得正文或 resume 的结果后，进入额外等待/清理前 | 清理仍可能使交付失败，不能修改候选内容    |
| accepted / handled 值 | 父接收函数交回候选后，正式接纳检查及发布前          | 父层可产生自己的新值，不改写孩子 returned |
| 恢复的 I/O 与接纳值   | 持久材料按原 codec 解码后，在业务消费前             | 重建新进程可信值；不继承旧进程证据        |
| 实体内容              | 实体本次更新校验成功、形成该版本时                  | 实体指向新版本，已交付旧版本保持原内容    |

“返回时”不指生产者源代码中 `return` 那个瞬间。Promise 兑现至内核 await continuation 之间仍可能运行其他微任务。需要更早固定的生产者，可以自行通过共同固定原语形成稳定值；不能承诺内核能回到生产者的词法 return 时刻取样。

输入统一固定不包含宿主 options、结构对象、Work、ResourceAccess、实体或能力端点。普通资源操作可能返回受控 reader/记录实体，不能在 `resources.operation` 上无差别套纯值复制。原 Error 仍用于传播、捕获和故障归属；需要把失败送入另一次调用的数据输入时，应显式形成诊断或业务失败数据。

### 2.2 本轮选定的隔离方式

采用“未知数据复制并深固定；可信产物复用”，不采用“原引用不变、作者承诺不改、以后扫描检测”。原对象不被原地冻结。修改生产者草稿不影响正式值；严格模式下修改正式值失败，非严格模式可能静默写入失败。

这是对现行原引用条款的有意修订方向。生产仍遵循 [调用边界](runtime-boundaries.md)、[接纳](checkpoints.md) 与 AGENTS 中的现行条款，本实验不静默覆盖它们。正式实施时要同步更新 Context、Runner、子调用、输出与接纳的公开文档和只读类型，保留内核内部同一交付值的一致引用，移除的是对作者原草稿身份的承诺。

### 2.3 支持域与身份

本轮验证的数据域为普通记录、稠密数组、undefined、null、boolean、string、有限 number（含 -0）。字段缺失与显式 undefined、null 与 undefined、-0 与 +0 分别保留。

Date、Map、类实例、函数、Error、访问器、Symbol 属性、环、稀疏数组等明确拒绝，不静默转换。这个范围已足以运行大量现有链路，但**还不能直接宣称是所有作者的最终支持域**。全仓盘点发现真实 Date codec 和 Error-as-input 测试，见 §6。

业务身份应来自明确字段。正常路径可能保留 DAG 内部共享，恢复不保证共享拓扑或旧 JS 指针。固定失败是边界技术故障，不允许通过普通 result.failed 把不合法成功值改成成功交付。先前实体效果仍可能已经成立，不新增事务或回滚承诺。

## 3. 复用证据与算法

### 3.1 两张不同的表

| 依据                        | 生命周期                           | 作用                                       |
| --------------------------- | ---------------------------------- | ------------------------------------------ |
| 源对象 → 本次副本           | 单次固定操作                       | DAG 去重；跨次不能缓存可变源               |
| 已成功固定的副本 → 私有证明 | 该固定机制实例内，WeakMap 随值存活 | 后续直接复用，未知 freeze/类型断言不能伪造 |

祖先集合进入时 add、退出时 delete。检查环先于读取本次 memo，不能把未完成父副本当成合法共享。只有整个固定操作成功才给新副本发证。

实体与调用需要共同可信实现，不要求整个进程有公开注册中心。实验用一个共享模块验证跨包消费；可选生产落点是无宿主依赖的共同纯值实现，再由包公开端点消费，不把 CP Frame、8 MiB 镜像限制或业务 Schema 认证混入它。当前实验仍使用 Node/assert/Buffer，不可直接复制为 contracts 实现。

公开原语应自行检查并产生稳定值，不能开放 `markFrozen(raw)`。即使注册入口隔离了 raw，也必须将实际固定副本交回生产者使用，不能给仍可变的原对象签发证明。不同机制实例及新进程重新检查，安全退化为复制；私有证据不是持久协议。

### 3.2 算法结果

| 样本                     | 固定工作                     | 持久表示                               |
| ------------------------ | ---------------------------- | -------------------------------------- |
| 9 对象、8 层双边共享 DAG | visits 767 → 10；memo 命中 8 | 仍是展开的 767 个值、18,441 UTF-8 字节 |
| 101 对象、100 层共享 DAG | visits 102；memo 命中 100    | 编码前预检拒绝，未构造展开标签树       |
| 同一可信根连续转交       | 旧正文访问增加 0             | 不等于 codec 或 CP 检查自动减少        |
| 可变源再次固定           | 重新读取当前源，旧副本不变   | 不复用上次 raw → copy 关系             |

固定复杂度按本次新对象、属性/元素、文本和接入的可信子图计，不按树路径重复展开。可信根直接复用为 O(1)。编码先用 DAG 动态规划计算展开体积，再允许有界树展开；不先展开再量字节。

### 3.3 预算不是一个数

实验分别约束深度、对象、属性/数组项、文本 UTF-16 单元、编码展开值数和最终 UTF-8 字节。每个实例的预算固定。共享子图嵌入新容器仍核验组合限制；编码还核对失去共享后接收方需要的对象/文本预算，避免同限额下自身 encode 成功而 decode 失败。

当前复用证明使用整次固定成本作为内部子节点的安全上界，避免建立每个节点的传递去重集合。它可能保守拒绝：从大图拿出的很小子值，组合时可能连同原大图成本计费。**这是实验的明确局限，尚不适合作为无解释的生产内容配额。** 正式迁移需区分内容限制与保守计算预算，不能把构造路径相关的收费宣称为精确内容大小。

完整算法、单位、边界与 16 项新增测试见 [算法验证](../examples/checkpoint-facts-study/algorithm.md)。限额是实验配置，不是新增的生产全局上限，也不是 Proxy/恶意代码沙箱。

## 4. 自动迁移探针

`migration-hooks.mjs` 使用 Node 22.23.2 的同步模块加载 hook，只在测试进程内改写本仓库刚构建的指定模块。源码和 dist 文件均不改写。每个替换要求准确出现次数；源码变化会让探针明确失败，不静默跳过。共同值模块只记录边界标签、计数和拒绝原因，不记录调用正文。

覆盖：

- Runtime `construct` 在 scope.prepare 前固定输入；低层 Builder 在 refine 前固定。
- InvocationContext 直建输入与恢复 currentInput。
- Execution 在取得 execute/resume 结果后、settle/close 前固定候选。
- Relation 在 accepted/handled 共用路径、check 前固定接收值。
- 恢复 target 的输出以及 CP 解码后的各项 I/O/接纳值。
- 固定失败接入现有受保护故障判断，不成为普通业务 fallback。

有意不覆盖：资源返回值、错误对象本身、输出 delta、业务 point.state、纯值以外的能力对象、生产只读类型、codec 缓存、CP 表示。实体复用只在第二个探针中让真实 Memory.prepare 与 Transcript.accept 使用同一 creator，不改实体生命周期。

一个经审查修正的探针错误：第一版把整个 decoded Frame 固定为一个值，导致多份内容累加触发 1 MiB 文本限额，误使大文本 HTTP 与记录测试失败。第二版逐个固定正式值，机制容器只保持原有冻结；两项恢复通过。`decodeCheckpointFrame` 也在普通 save 检查中运行，不能因路径名把其成本误记为仅恢复成本。

另一个真实反例：固定时 Proxy 可抛出 undefined，若错误包装再直接读取 `cause.message`，二次 TypeError 会绕过受保护故障类型，让父 result.failed 吞掉该失败。探针现已保证未知抛出值均转为受保护固定故障，只以安全数据描述符匹配有限拒绝码，不能读取 getter；日志不抄录任意异常 message。新增测试涵盖 undefined/null/字符串/Error/不可读 message/不透明 Proxy。仍不宣称阻止 Proxy 元操作或撤销其效果。

## 5. 自动小场景结果

9 项自动边界测试在“仅调用边界”和“调用＋实体生产者”两种配置下均通过。没有在测试正文里手工替代内核的输入/返回/接纳边界。

验证了：capture 之前的隔离；清理修改生产者别名不改返回；关闭失败仍阻止成功；首次 CP 前修改原返回/接纳对象不改事实；CP 开关内容一致；handled 值固定而原 Error 保持；Date 成功值拒绝不可被 failed 掩盖；资源能力保持原对象；真实 Memory 快照直接复用。

实体复用的收益与限制分开：同一 Memory.snapshot 不再重新遍历，Transcript.snapshot 仍创建前缀数组，新数组首次固定仍有成本。没有修改 View 的全量更新，也没有宣称完整材料捕获已增量化。

实际 CP 计数反证：同一个子结果，父保存两次时，**子输出 encode 仍调用 2 次、point.check 仍调用 2 次**；关闭 CP 时均为 0。稳定内容本身没有改变当前 CP 的调度。

独立 `stable-types.ts` 通过编译，包含 22 个编译失败断言，覆盖可变输入供给、深只读 Work/返回/接纳、tuple/array、undefined/void 及具体 Callable 成员 I/O 关联。不使用类型断言或 any 掩盖错误；移除失败标记后恰有 22 个预期诊断。它也保留可编译反例：结构类型不能排除所有自定义原型/访问器，readonly 可经另一个可变别名绕过，所以类型不是固定性凭据。生产 Runner、ChildCalls、reception、Sequence/Dynamic 的整体推导仍待迁移验证。

| 类别                   | 代表证据                                                                  | 迁移含义                                                                                       |
| ---------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |

| Proxy/观察夹具         | conversation-recording-capture                                            | 固定本身需检查属性；即使未开启记录也会触发 Proxy 元操作，不能继承“任何任意值完全不检查”的承诺  |

本次日志没有直接证实生产业务在写已冻结正式值，但不能反向断言不存在：不少测试先被旧引用断言中断，后续资源关闭、流订阅清理等断言未执行。没有批量删除或改写这些断言。

下一次正式迁移要先处理支持域、预算归属和只读类型，再将旧断言改为“内容稳定＋内部交付一致”，继续执行其后续断言。不能仅以 3,097 项通过宣布迁移完成。

## 7. 回执不确定与恢复矩阵

15 项定向测试通过，其中 12 项 Runner/SQLite 测试启动 27 次独立进程，使用 5 类硬退出切点；另外 3 项验证公开 Invocation 的准确关系与接收保护。安装自动稳定边界后，这 15 项再次通过。

| 留存状态                                                       | 新进程结果                                                       |
| -------------------------------------------------------------- | ---------------------------------------------------------------- |
| 孩子 finish 提交成功、父仍 waiting                             | 核对准确身份/输入/契约后读取交付，不重跑孩子                     |
| 孩子提交成功后回执抛错；旧父内存已失败，但父 failed 提交前退出 | 磁盘仍 waiting，仍可读取准确子成功；不能把内存失败误认为持久终态 |
| 父 failed 已提交                                               | 根终态拒绝恢复                                                   |
| 父 succeeded 已提交但回执丢失                                  | 根终态拒绝再次执行                                               |
| 有合法子 continuation、没有成功交付                            | 进入作者声明的 resume，不重放原正文                              |
| 缺首子 CP 或 owner/input/contract 不符                         | 明确拒绝，不盲目重跑                                             |

活调用中 CP 故障仍 `receptionAllowed=false`，父不能 handled。这与崩溃后按持久事实处理不矛盾。finish 抛错后不二次写失败覆盖可能已成立的成功，也不重跑正文。

详见 [恢复切点报告](../examples/checkpoint-facts-study/receipt-recovery.md)。测试使用真实 SQLite 提交加注入故障，不模拟存储介质损坏；通用 Runner 恢复通过不扩大对话宿主资格，也不承诺所有外部效果恰好一次。

## 8. 下一步：从稳定内容到增量 CP

本轮可以收敛稳定内容的方向，但暂不进行全仓生产替换。正式迁移还有三个具体门槛：

1. 支持域与只读作者类型：保留普通原始值/数据结构，如何迁移现有 Date codec、Error-as-input 与依赖身份的校验；不能用 `as` 掩盖不可变输出仍可写的类型。
2. 预算与复用证明：固定值、模型请求、CP 聚合分别拥有预算；解决内部子节点证明过粗的保守拒绝，不引入新的全局配额中心。
3. 持久表示：当前标签格式仅用于单值语义验证；生产 Frame v5 和业务 codec 未改。undefined/-0 的保真不能由普通 JSON 假定，版本兼容需明确。

之后的 CP 小闭环应处理：

- 同一已固定内容的持久表示何时正式成立，由哪个契约拥有；编码失败不改写原内容。
- 哪些新事实首次认证，哪些活动关系继续变化；“内容稳定”不能证明 codec 无闭包状态或 check 没有新消费条件。
- 保存只处理新增事实和必要活动集合，refs/state/关系认证、Store 读写分别测量，不能只消除复制。
- 恢复重新读取并完整核验外部材料；不能把进程内凭据写成持久信任标记。

这四项才对应“第二次 CP 对旧事实正文访问为零”的后续验收，本轮没有实现或宣称达成。
