# 真实调用生命周期与事实表示：第九轮验证

2026-11-07。承接[调用事实与局部推进版本](invocation-facts-progress-validation.md)。继续验证现有 Invocation、显式恢复点和准确父子接纳；不改为协调重放，不增加推进实体，不要求长调用分段。本轮只新增隔离实验及报告，没有修改生产调用、Frame v5、服务或宿主恢复资格。

## 1. 本轮回答什么

前几轮证明了稳定材料、事实行和紧凑 head 的可能性，但实验 `FactCall` 的简化状态不能直接代表真实调用。本轮将真实调用的创建、返回、接收、失败和退出接入同一实验事实库，再把它重建为 Frame v5，交给真实恢复代码消费。

结果支持继续沿当前路线建模：**活动可以重新建立，已成立的内容与归属不必重新成立；恢复消费最后正式保存的依据，不从最新内存状态猜测依据。** 这不是所有生产能力已经迁移完毕的证明。

三条验证链分别是：

```text
真实 Invocation / Context / Relation 的准确边界
  → 固定边界事实
  → 实验 FactStore 的新事实 + 当前选择，同事务保存

已固定边界事实
  → 独立重建 Frame v5
  → 与真实 Invocation 生成的 Frame、公开回执逐项比较

硬退出
  → 新进程完整核验实验事实库
  → 重建最后正式 Frame / delivery
  → 真实 prepareCheckpointRestoration / Invocation.restoreChild
```

没有把真实 Frame 拆成差量后冒称“事实能够独立重建”。真实 Frame 在保存时只作对照，不作为输入、关系或接纳事实的补充来源。作者 point、state、references 仍直接来自本次保存申请。

## 2. 归属与成立时机

实验的 `LifecycleFacts` 只是对照表示，不是新增的生产调用对象。它使用原 `FactCall.capture/save` 保存材料，刻意不使用旧实验的简化子关系状态机。

| 事实               | 所有者      | 保存内容与边界                                                                        |
| ------------------ | ----------- | ------------------------------------------------------------------------------------- |
| 本次输入           | 本调用      | 固定身份、原输入的编码值及声明契约；在适配器创建调用时取得                            |
| 子关系建立         | 父调用      | 准确孩子身份、声明位置、parent round、从 0 开始的 order、可选 key、原输入与子 CP 契约 |
| 工作终态           | 本调用      | Context 实际 complete/fail 的结果；不是业务正文刚 return                              |
| 持久交付           | 本调用的 CP | 实际 finish 提交的 succeeded/failed/cancelled；与工作终态分开                         |
| returned           | 父关系      | 父层实际收到的成功值或失败诊断及归属；不由子磁盘结果替代                              |
| receiving          | 父关系      | 已确定的接收契约及进入接收的事实；不保存 Promise、活动窗口或回调闭包                  |
| accepted / handled | 父关系      | 回调和接纳校验通过后安装的值；handled 不改写孩子的失败                                |
| 接收失败           | 父关系      | 失败诊断与可取得的归属；不能冒充已成立接纳                                            |
| CP 选择            | 本调用      | 本次 point/state/refs 及准确边界尾引用；指向当时已成立的事实                          |

普通 key 不是关系身份。同一 key、同一声明的多个孩子保留不同 contextId 和 order。接纳契约仍核对准确父登记位置与 childPosition。

事实库中每份边界有本调用 owner、序号和前驱。冷读取除核验通用事实存储外，还核验边界发布顺序、每个 CP 在当时选择的尾、最后 CP 和最终交付。一个“通用 carrier 的摘要都正确，但新 CP 谎称选择更早边界尾”的反例仍被拒绝。

这里不能把两种选择混淆：业务材料可以选择一个旧的固定前缀；**新 CP 不能用旧的调用关系截面抹去已发生的子关系。** 本轮没有删除上一轮局部材料自由选择的能力。

## 3. 真实接线发现并修正的缺口

### 3.1 工作、持久交付、父层收到的结果必须分开

真实测试重现：

```text
孩子 Context：succeeded
孩子 CP：succeeded 已提交
孩子 finish 回执：失败
父关系 returned：failed，受保护
```

实验能够保存这组不同归属的事实，不覆盖为一个共同终态。父层不能通过普通 failed 接收把持久回执故障当成业务失败处理。

但恢复判断还要区分最后保存到了哪里：

- 父层已提交 failed 终态：拒绝恢复。
- 父层未提交终态就崩溃，最后 CP 仍为 waiting，孩子成功交付已保存：现有恢复机制可以核对准确身份、输入与契约，读取孩子交付后继续。

第二种情况没有重跑孩子正文，也没有使用旧进程未保存的失败重新改写 CP。它是现有有限恢复语义，不是本轮扩大了覆盖范围。

### 3.2 恢复 receiving 是新活动，不是第二次建立接收事实

交叉审查发现首版适配器把“恢复后重新进入原接收回调”错误识别为又一次 `pending → receiving`，导致合法恢复被拒绝。

真实 Relation 允许从已保存的 receiving 按**同一份已绑定契约**重新进入活动。跨进程固定的是父契约版本及接纳登记位置／含义；新进程建立准确绑定对象后，再由真实 Relation 检查本次对象身份，不要求跨进程保留旧 JS 引用。修正后：

```text
已保存 receiving(contract 0)
→ 冷恢复安装该事实
→ 按 contract 0 重新进入接收活动
→ 回调完成、检查通过
→ 新的 accepted 事实
```

适配器只对准确恢复基线承认这一次重入，不放宽普通重复接纳。切点测试中，接收入口进入次数为 1→2，完成映射次数为 0→1；孩子正文与效果各总计一次。换用父层另一份已登记契约，真实机制仍在回调前拒绝。

这条区别比“所有状态都只向前一次”更准确：**关系事实可以已经成立，执行该关系所需的活动仍可能重新建立。** 未完成回调中的业务副作用依然需要自己的固定确认，不因恢复 receiving 自动获得幂等性。

### 3.3 启动前取消也是事实，但没有第一轮工作

真实孩子可能在 `run()` 前就被取消，进度仍为 round 0。首版实验只接受 round 1，导致采集失败反而盖住了真实取消。

修正为允许记录 round 0 的失败／取消诊断，同时拒绝 round 0 成功、接纳及可恢复 Frame 投影。未开始运行不等于没有发生过返回失败；能够记录也不等于能够恢复。

取消的分类仍由真实机制决定：本次有效 signal 的取消令牌得到 cancelled；其他 signal 的令牌、普通错误恰逢 abort、取消与关闭失败的复合错误仍是 failed。实验不以 `signal.aborted` 代替准确归属。

### 3.4 事实值、持久编码和回执是三个检查位置

非 identity codec 测试覆盖父／子输入、输出及接纳值，业务形状与持久形状不同，重建结果仍与真实 Frame/finish 一致。

实验在成立边界额外执行确定性的纯数据 codec，并立即固定其结果。它没有证明任意有闭包状态、非确定性或有损 codec 与当前“保存时编码”契约等价；也没有把 codec 错误从原来的保存阶段前移到生产。

另一个实际接缝是回执摘要：现有 digest 受序列化字段顺序影响，`deepEqual` 通过不代表回执通过。候选按真实 v5 的固定字段顺序独立构造 image/frame/progress/failure，再使用公开回执校验；没有借用真实 Frame 替换候选以绕过比较。

## 4. 恢复矩阵

独立子进程在切点 `process.exit(73)`，绕过 finally；新进程通过实验事实库和真实公开恢复入口继续。只传原根 ID 作为定位。JSONL 用于统计执行次数，不作为恢复材料。

下表的效果是夹具中指定执行位置的计数，证明这些位置没有重入。本轮没有调用真实外部 API，不据此推导任意外部副作用恰好一次。

| 保存或中断位置                       | 真实恢复结果       | 正文、映射及效果                   |
| ------------------------------------ | ------------------ | ---------------------------------- |
| 父 waiting，孩子没有首个 head        | 拒绝               | 不创建恢复孩子，不执行孩子正文     |
| 父 waiting，孩子 active              | 继续原孩子         | 子 resume 一次；原正文和效果不重跑 |
| 父 waiting，孩子 succeeded 已持久    | 读取既有交付       | 不执行子正文或子 resume            |
| 子成功提交后丢回执，父 finish 前崩溃 | 按旧 waiting 继续  | 不重跑正文／效果，父接纳完成一次   |
| 父 receiving 已保存                  | 同契约重入接收活动 | 可重新进入未完成回调，孩子不重跑   |
| receiving 改用另一已登记契约         | 拒绝               | 不进入新的映射                     |
| 父 accepted 已保存                   | 安装已成立接纳     | 不重跑映射                         |
| 父 handled 已保存                    | 安装已处理失败     | 孩子仍 failed，不重跑处理映射      |
| 父 waiting，孩子 failed／cancelled   | 拒绝               | 不调用恢复构造 callback            |
| 根已 succeeded／failed 终结          | 拒绝               | head、孩子及计数不变               |
| 篡改子 owner／input／contract        | 拒绝               | 没有新孩子工作或映射               |
| 篡改父 order／refs                   | 拒绝               | 没有新孩子工作或映射               |

篡改试验只改变公开 Store.read 返回值，不改原持久事实。它测试真实恢复核对，不代表摘要能够抵御可改写全部存储的攻击者。

当前接收失败、受保护失败、普通未处理失败不能生成新的可恢复 Frame；旧有效镜像保持原样。accepted 的后置通知失败则保留已成立接纳，不能倒退成接收失败。恢复过程中发现依据缺失，真实父调用可能正式写入 failed 终态；这不同于根终态预检时完全不启动调用。

## 5. 计算范围：有收益的部分与尚未替换的部分

计数脚本实际运行 Invocation，分别创建 32／128 个串行孩子。每个孩子前后各保存父 CP，孩子也保存首个 CP 并 finish。输入与输出为小纯值；不是时间或吞吐基准。

最终产物记录于 `.capix/invocation-lifecycle-facts-20261107-final/summary.json`，含源文件指纹与逐次数据。

| 指标                                    | 32 个孩子 | 128 个孩子 |
| --------------------------------------- | --------: | ---------: |
| 父保存次数                              |        64 |        256 |
| 父边界事实数，含工作终态                |       129 |        513 |
| 父新事实编码总数，含输入、CP 选择和交付 |       195 |        771 |
| 已编码旧边界再次编码                    |         0 |          0 |
| 实验 Store 热保存读取旧正文             |         0 |          0 |
| 实验 carrier head 字节范围              |   829–832 |    829–833 |
| 真实 v5 对照累计子关系数                |     1,056 |     16,512 |
| 候选完整 Frame 投影累计子关系数         |     2,112 |     33,024 |
| 冷读取父事实正文数                      |       195 |        771 |

两次候选投影分别用于真实 Frame 比较和独立镜像认证。这个开销刻意保留，不能把新事实行的编码成绩称为整条 CP 已经增量化。

业务 codec 计数也保留了旧成本。例如孩子输入 encode 为 2,272／33,664 次，接纳 encode 为 1,056／16,512 次；这些包含现有 Invocation 的全量捕获和实验额外的成立时编码。**旧边界的 carrier 编码为零，不等于真实业务 codec 调用为零。** 真正替换全量捕获、解码和检查路径仍是后续任务。

紧凑 head 只引用材料，不意味着所有 state/refs、关系历史、内存驻留和冷读取都已取得上界。本轮 state 固定很小、refs 为空，作者大 state/完整 refs 的成本仍由前几轮反例约束。测量脚本为了核对旧编码还显式扫描统计表，不把这段诊断计算冒充增量运行实现。

## 6. 仍未完成的生产接缝

1. **现在是两套状态的对照仪器。** 实验包装公开 Context/Children/Relation 方法，并使用严格观察来定位同步变化；它没有新增生产机制端口。普通 Observation 缺字段、可隔离且恢复时不重播，仍不能独自充当完整事实来源。
2. **没有把稳定值安装给真实业务消费。** 修改输入或返回值别名，生产对象仍会变化；候选与真实 Frame 比较明确失败，不能靠重新捕获来隐藏差异。现行“保持原引用”条款尚未修订。
3. **尚未覆盖真实资源 capture/refine 前的稳定输入接线，以及无 CP 声明调用的完整适配。** 本轮模型要求有 CP 契约；不能据此给未配置 CP 的调用增加保存要求。
4. **失败保存仍遵守实际资格。** 事实表示能容纳诊断，不代表旧错误对象、访问窗口、Promise 或未确认外部效果可恢复。旧 round/continuation 没有获得新执行入口。
5. **调用事实归属与数据库生命周期不同。** 底层 FactCall 在这里仅是事务与材料载体，carrier 的 active 字段不是 Invocation 的状态；实际终态由明确的 durable delivery 检查。不能将这个实验复用方式原样变成生产第二份调用状态机。
6. **覆盖是公开 Invocation 边界，不是完整宿主资格。** 本轮没有把 Conversation、实体固定凭据、模型请求核对和资源窗口装配全接到新格式；没有宣称 Frame v6 可以生产替换。

## 7. 下一步应收敛什么

继续沿本次事实模型推进，下一步应把“事实在原所有者中怎样成立”收敛成准确的内部契约：

- Context／Relation 在自己的状态转移中固定相应内容，CP 消费同一份依据；生产不再依赖外置观察器镜像另一套运行状态。
- 区分首次事实成立、冷安装旧事实、恢复活动重入。接纳契约和调用身份不因活动重建改变。
- 先明确固定或编码失败发生时，哪个操作尚未成立、哪个结果已经成立，错误如何继续归属；不让采集故障覆盖原始失败。
- 将全量 Frame 保留为冷恢复与对照形式，验证热保存可只认证新增事实及当前组合；仍以本轮真实拒绝矩阵约束，不能先删除核对再声称性能改善。

这是原调用机制的内部收敛，不需要先增加独立推进实体，也不需要为了简化内存或存储问题改变调用边界。正式契约与生产迁移仍待下一小步证明后进行。
