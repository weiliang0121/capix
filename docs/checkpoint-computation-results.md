# Checkpoint 单步计算基准实测

日期：2026-11-06。对应 [基准设计](checkpoint-computation-benchmark.md) 和 [可执行示例](../examples/checkpoint-computation/README.md)。

这轮验证了计算范围问题：**即便串行处理、只有一个活动子调用、只引用当前子调用、作者只做局部检查，保存仍会重复处理全部已完成历史。** 全部 refs 随历史保留时，又叠加逐引用查找全部关系的成本。固定输入则形成另一个独立的重复处理维度。

本轮只增加基准、测试和报告。生产保存点、Frame v5、恢复承诺及已有缓存实现保持原样；没有采用哈希链或固定业务 codec 的编码结果。

## 1. 实验边界

- Apple M3 Max、16 个逻辑 CPU、64 GiB 内存；macOS Darwin 25.6.0 arm64，Node 22.23.2、V8 12.4、SQLite 3.51.3。
- 基线提交 `aea2c0170664a3a88e9f5b79fa688c5a7cf1aba6`，叠加此前尚未提交的 CP 纯值证据复用与 SQLite head 校验缓存。每批 manifest 保存实际源码和 dist 的文件摘要、dirty 清单及 diff 摘要，不能把提交号单独当作完整基线。
- 公开 `Scene → Group → Node → Runner`，真实 MemoryCheckpointStore / ConversationStore。无真实模型、网络、业务文件读写、Recorder 或原有会话库。
- 每个耗时配置三次独立进程，正序／逆序／正序；诊断配置各一次。每进程先做 8 步预热，再建立新的结构与 Store。无强制 GC，机器未做专用性能隔离。
- 耗时与字节／codec 计数分进程运行。正式计时内不做额外 JSON 字节统计，不保留历史 image 对象。构造、build、finish、Store 关闭与最终只读检查分别处理。

主实验共 **120 次耗时运行，全部完成**：32 个首批配置 × 3，加上 8 个扩展配置 × 3。普通 Group 实测至 2,048 个子调用，未提高 8 MiB、100,000 值节点或 4096 直接关系的限制。

`checkpointMs` 从作者调用 `work.checkpoint` 到同步返回，包含 Store.save；两者不能相加。表中的累计 CP 只计目标 Group，包含 dispatch、accepted 和最终 completed 点，不包含子 Node、Scene 或 finish。各列分别取三次独立运行的中位数，不保证来自同一个进程。

## 2. 关系增长：小活动集合没有限制计算范围

固定 H=1 KiB、子返回值 V=64 B、局部 check。每一步父层 dispatch 保存一次、accepted 保存一次，最后 completed 保存一次，共 `2N+1` 次。子业务只是返回同一个固定字符串；不存在工具或模型等待。

两种 refs 策略使用同一个 many 槽位：current 只保留最后一个引用，all 保留全部引用。Node 输入是固定宽度的 8 字符步骤标识。state 只有固定形状的数字进度，数字位数变化会带来少数字节变化，不能称为严格等长。

### SQLite：相同阶段与整段成本

| 子关系 N | current 末次 accepted | all 末次 accepted | current 父 CP 累计 | all 父 CP 累计 |
| -------: | --------------------: | ----------------: | -----------------: | -------------: |
|       32 |              0.774 ms |          0.958 ms |            0.040 s |        0.045 s |
|      128 |              2.105 ms |          2.580 ms |            0.295 s |        0.382 s |
|      512 |              7.281 ms |         14.255 ms |            3.733 s |        6.520 s |
|    1,000 |             13.133 ms |         42.021 ms |           13.486 s |       33.520 s |
|    2,048 |             29.571 ms |        156.909 ms |           57.812 s |      227.376 s |

精确 N 的末次 accepted 每进程只有一个观测，故报告中位数及范围，不给可靠 p95 的暗示。完整逐次数据还保留 accepted 的数量分段分布；该分布含不同 N，不是固定规模的置信区间。

### N=2,048：Memory 与 SQLite 对照

| Store / refs     | 末次 accepted 中位数［最小–最大］ | 父 CP 累计中位数 | 其中 Store.save 累计 |
| ---------------- | --------------------------------: | ---------------: | -------------------: |
| Memory / current |         24.206［23.463–27.061］ms |         48.296 s |              0.014 s |
| Memory / all     |      154.627［151.165–156.100］ms |        211.234 s |              0.018 s |
| SQLite / current |         29.571［27.802–31.611］ms |         57.812 s |              8.420 s |
| SQLite / all     |      156.909［155.022–160.295］ms |        227.376 s |             11.803 s |

每次均为目标 Group 4097 次 save；全树 6146 次 save、2050 次 finish。独立复核原始结果与汇总一致。

N 从 512 增至 2048 时，current 的父累计成本增长约 15.5 倍、末次成本约 4 倍，符合单次随历史增长、累计接近二次的趋势。all 增长更陡：N=2048 时，末次成本约为 current 的 5.31 倍（SQLite）／6.39 倍（Memory）。

这些样本中，SQLite Store.save 占父累计 CP 的约 14.6%／5.2%；Memory 也需要约 48／211 秒。**关系增长问题不能归因于数据库慢，也不能按 Store 耗时乘二估算完整 CP。** 但这不意味着所有场景的 Store 比例都低，固定大输入的结果不同。

## 3. 固定输入：独立且显著的重复成本

固定 128 条已接纳关系、一个 ref，随后在 diagnostic 点重复保存同一 state、refs 与关系 16 次。每个进程先取这 16 次的中位数，再汇总三个独立进程。关系建立成本不计入下表。

| 原输入正文 H | Memory 完整 CP | SQLite 完整 CP | SQLite 内部 Store.save |
| -----------: | -------------: | -------------: | ---------------------: |
|            0 |       1.742 ms |       2.200 ms |               0.429 ms |
|        1 KiB |       1.750 ms |       2.177 ms |               0.451 ms |
|       50 KiB |       2.407 ms |       3.828 ms |               1.363 ms |
|      500 KiB |       8.667 ms |      18.123 ms |               9.676 ms |
|        2 MiB |      28.495 ms |      68.574 ms |              39.761 ms |

N=0 的独立对照也成立：Memory 从空输入约 0.030 ms 增至 2 MiB 输入约 19.424 ms；SQLite 从约 0.191 ms 增至 49.522 ms。因此输入成本不依赖累计子关系才会出现。

H=500 KiB、N=128 的实际 image 为 1,097,097 B；input/currentInput 的 JSON 字段各 512,002 B，children 为 72,467 B。保存时 input 的 encode 和 decode 各执行两次。

这支持“固定输入被反复处理有可观成本”，不证明“输入只编码一次”在当前契约下是免费的改动。当前机制仍允许保存时观察业务值、重新执行 codec 并拒绝不一致；固定时机需另做契约决定及反例验证。输入大小与关系成本也不保证简单相加，不能把某条拟合直线的截距全部解释为输入。

## 4. 诊断：重复的具体范围

字节和 callback 计数来自独立 diagnostic 运行，其耗时不混入上面的性能结果。

在 accepted 点保存 N 个成功子调用时：

| 当前保存内的回调                 |    次数 | 含义                          |
| -------------------------------- | ------: | ----------------------------- |
| 子 input encode / decode         | 各 `2N` | 每条关系的 input/currentInput |
| 子 output encode / decode        |  各 `N` | 全部已返回结果                |
| reception output encode / decode |  各 `N` | 全部已接纳值                  |
| reception.check                  |     `N` | 解码后重新核验接纳值          |
| 父 input encode / decode         |    各 2 | 父 input/currentInput         |
| 父 state encode / decode         |    各 1 | 当前点状态                    |
| 作者 group.check                 |       1 | 局部检查，没有遍历历史        |

N=2048、current 的实测保存中，子 input encode/decode 各4096次，子 output 与 reception 编码/解码各2048次，reception.check 2048次。**这不是重新执行子业务或 succeeded 映射，是 CP 重新编码和验证旧事实。**

### 引用匹配是另一项成本

[新 image 认证](../server/checkpoint/src/value.ts) 与 [声明槽位核对](../server/invocation/src/checkpoint/facts.ts) 都调用 `checkpointReferenceChild`，通过 `children.find` 找引用。该夹具无 continuation，引用有效、关系唯一，Store/回执对同一已认证 image 的重复检查命中已有证据缓存。

于是，对 i 条关系的一次保存，两轮查找比较量为：current `2i`，all `i(i+1)`。以下是**按实际保存轨迹和当前算法推导的比较量**，不是 CPU 指令插桩，也不涵盖所有扫描。

|     N | 父层累计捕获关系条目 | current 两轮引用比较量 | all 两轮引用比较量 |
| ----: | -------------------: | ---------------------: | -----------------: |
|    32 |                1,088 |                  2,176 |             24,992 |
|   128 |               16,640 |                 33,280 |          1,447,552 |
|   512 |              263,168 |                526,336 |         90,266,112 |
| 2,048 |            4,198,400 |              8,396,800 |      5,739,210,752 |

父保存次数为 `2N+1` 时，三列分别是 `N²+2N`、`2N²+4N`、`N(N+1)(2N+7)/3`。全 refs 因而引入累计三次增长的算法项；**不能据此宣称整个 CP 墙钟耗时已实测为精确三次复杂度**。

2048 的两份 SQLite 诊断也与公式吻合。最后 accepted 镜像 current 为1,164,833 B，all为1,497,384 B，约增28.5%；末次保存耗时却增约5.31倍。这支持引用匹配是独立成本，而不只是正文体积增加。

### 当前链路的处理范围

| 环节                    | 当前处理范围                                       |
| ----------------------- | -------------------------------------------------- |
| 子关系捕获与 codec      | 全部 N 条，与仅选择一个 ref 无关                   |
| 镜像 JSON／摘要         | 完整镜像字节                                       |
| 两轮 refs 匹配          | `O(RN)`，本夹具可按位置推导比较量                  |
| Frame 解码与接纳值校验  | 全部 N 条                                          |
| Runtime 构造 check 事实 | `O(N+R)`，这里已使用 Map                           |
| 作者局部 check          | `O(1)`                                             |
| SQLite 旧 head 缓存命中 | 仍读取并比较完整旧存储行；省去旧正文解压和重新认证 |
| 新镜像落盘              | 完整编码、压缩及写入                               |

## 5. 存量与重复处理量是两件事

N=2048、SQLite/current 的独立诊断：父 CP 传入 Store 的累计逻辑 image 为 **2,391,550,170 B（约2.23 GiB）**；关闭后全库保留2050份当前 image 正文，共1,124,219 B，另有470,822 B的终态交付，数据库文件13,414,400 B。

这是不同口径：累计逻辑 payload、当前压缩 image 正文、终态交付存量、数据库文件长度。它们都不能直接当作累计物理磁盘写入量。只保留 head 正文确实控制了保留存量，但未消除累计编码和校验。

MemoryStore 也保留当前 heads 与已用 imageId，并非零存储。报告的进程峰值 RSS 包括导入、预热和结果检查，不能称为目标 Group 的独占内存。

## 6. 补充对照与测量扰动

### 返回值体积

SQLite、N=128、H=1 KiB、current、局部 check，仅改变每个子返回／接纳值 V：

|      V | 最后 accepted 完整 CP | 父 CP 累计 |
| -----: | --------------------: | ---------: |
|   64 B |              2.105 ms |    0.295 s |
|  1 KiB |              2.970 ms |    0.460 s |
| 16 KiB |             22.336 ms |    3.022 s |

历史值体积与关系数量都是独立变量。V=16 KiB 的128子调用仍完成，不能将2048个64 B结果的可达范围套用到2048个大结果。

### 文本压缩特性与作者检查

N=128、H=500 KiB 时，重复字符输入与固定种子文本相比，Memory完整单次CP中位数约8.353／8.667 ms，SQLite约13.876／18.123 ms，SQLite Store约5.408／9.676 ms。输入字节数相同，存储路径对可压缩性的差异明显；这些数字不是压缩函数的独占耗时。

另加一遍作者的轻量全关系 order 检查：N=128父累计0.297 s、N=512为3.690 s，局部检查对照分别0.295 s和3.733 s。本次轻量检查的差异没有从跨运行波动中清晰分离，不能说“全量检查反而更快”或“作者检查无成本”。主实验不用它仍出现明显增长，足以排除“只是作者 check 写得太重”的解释。

### 计时包装

相同N=128场景，独立比较timing与control，各三进程。control不包装Work.checkpoint、不做逐次计时，但保留Store计数与数值记录，不能称为零测量开销。

| 场景             | timing 整次run中位数 | control 整次run中位数 | 中位数差异 |
| ---------------- | -------------------: | --------------------: | ---------: |
| Memory / current |           230.281 ms |            229.236 ms |     +0.46% |
| Memory / all     |           312.656 ms |            307.809 ms |     +1.57% |
| SQLite / current |           343.948 ms |            341.353 ms |     +0.76% |
| SQLite / all     |           434.277 ms |            426.757 ms |     +1.76% |

两种模式分批执行，差异含测量开销与运行噪声，不是严格的开销上界，也不据此校正每条样本。额外空函数计时校准：同一进程3批各100,000次，两次`performance.now`包住空函数，中位差均约0.000041 ms；不从CP时间中扣除。

## 7. 后续决策依据

这次可以将问题分成三个明确方向：

1. **引用认证的检索方式。** `O(RN)` 来自每个 ref 重扫关系，先评估准确索引能否保留原身份、顺序、位置与槽位核验。索引化不等于允许省掉认证，也解决不了全 Frame 编码。
2. **固定输入的表示与固定时机。** 相同大输入反复编码、认证和压缩已有独立实测依据；是否只处理一次，需先明确后续修改与非确定性 codec 的语义。
3. **已接纳历史与活动状态的分离。** 单 ref 仍有二次累计趋势，说明缩小 refs 不会自动缩小捕获范围。后续表示应避免每步重做全部已封口历史，同时能在恢复时完整核验。

不从此基准直接选择哈希链或增量日志，也不先删除恢复屏障。性能夹具的 Group 恢复函数明确拒绝；它证明计算代价，**没有验证新的恢复覆盖范围**。优化仍须复用 [恢复切点矩阵](checkpoint-recovery-coverage.md)，并加入固定值修改、历史依据缺失、摘要不符和提交失败反例。

这不是 ToolLoop、真实文件工具、模型上下文压缩或服务器并发吞吐测试。子结果在同一次运行中相同，压缩特性不代表不同大文件的输出；普通 Group 的2048子调用也不改变生产 ToolLoop 的轮数上限。保留这些区分，才能将结果用于内核计算范围，而不外推成服务器容量或市场框架排名。
