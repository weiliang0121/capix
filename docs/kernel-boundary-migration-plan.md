# 客户端、协议与实体边界收敛计划

状态：2026-11-11，分阶段实施中；P0 基线已提交为 `d78fa14`，P1 客户端交接与两仓独立验证已完成，P2—P6 尚未实施。基于当前工作树、[实体能力盘点](entity-capabilities-audit.md)和[Memory 收敛设计](memory-convergence-design.md)。已确定的领域边界不再重复推翻；尚需证明的接口以明确验收点收口。

目标是让业务作者能够提供自己的实体，经资源、View、调用和可选记录／CP 使用；框架机制不依赖某套对话数据或客户端展示。已有专用实体、结构预设和可复用集成继续保留，不以减少包数为目标。

## 1. 现状与范围

下表记录规划起点。规划基线为 18 个公开包、2 个私有客户端包；此前讨论的三个私有包为 `client-runtime`、`client-http`、`observer-content`，其中 observer-content 当时已在未提交工作中交接到 Lab。P0／P1 完成后，三个私有包均由 Lab 本地维护，CAPiX 只构建、测试和分发 18 个公开包。`protocol` 是公开包，不是第三个客户端实现包。

| 部分                         | 当前状态                                        | 本轮目标归属                                                |
| ---------------------------- | ----------------------------------------------- | ----------------------------------------------------------- |
| observer-content             | CAPiX 工作树已删除实现及测试，Lab 持有内容组合  | 完成现有交接核验，不重新迁移                                |
| client-runtime / client-http | CAPiX 私有包，面向 Conversation／Observer       | 源码、测试、行为文档一起迁到 Lab，保留私有身份              |
| protocol                     | 混有领域类型、共同运行词汇、记录规则和业务 wire | 按所有者及真实跨端需求拆分，不能整个搬走                    |
| contracts                    | 已有稳定值、调用身份及共同操作契约              | 只补实际共享的最小契约，不收容所有实体类型                  |
| memory                       | 强制 Transcript、topic 和来源；已完成领域设计   | 外层 UUID＋总结正文＋业务 metadata；独立写入和固定确认      |
| 通用实体接入                 | Lab 已证明组合可行，生产公共接缝未完全收敛      | 公共能力契约、适配方式及框架自身验证；不要求继承统一 Entity |

源码盘点确认的关键反向依赖：

- `changes` 从 protocol 取得 InvocationOrigin。
- `resources`、`invocation` 直接认识 TranscriptEvent／MemoryEvent。
- `transcript`、`memory` 从 protocol 取得自己的领域数据。
- `records` 不只导入类型，还调用 protocol 的输出解析、记录校验函数；其通用归档信息却位于 `protocol/observer/archive.ts`。
- 两个客户端使用 protocol 的运行时常量、接纳器以及 Conversation／Observer DTO。

因此，**客户端可以先不改行为地迁出；协议解耦必须先归位定义和运行规则，再迁出业务 wire。** 前者是仓库归属，后者是语义归属，两步各自可验证。

## 2. 最终边界

```text
CAPiX
  contracts           实际共享的进程内协作契约与稳定值
  resources           受控操作、窗口、准确操作关联
  changes             捕获、发布、消费故障语义
  structure           Scene / Group / Node 与预设
  invocation          单次调用、关系、接纳、退出
  checkpoint          已成立事实的保存与有限恢复
  runtime             绑定、机制接线、Runner
  view                来源范围、成员和固定读取
  transcript / memory / model-exchanges
                      各自领域值、操作、持久与可选适配
  records             通用记录实体、关系、查询、校验
  protocol            经确认的框架级跨端 DTO 与接纳规则
  其他公共集成／预设   继续按现有职责维护

capix-lab
  客户端两个私有包    当前对话／Observer 的消费和 HTTP 适配
  参考业务协议        Conversation、Observer 的请求、反馈及展示 DTO
  observer-content    内容组合、默认活跃策略、业务同步
  services / apps     提取策略、持久装配、展示和产品流程
  examples            研究和业务场景验证
```

这是职责图，不预先新增同名目录或平台包。Lab 的业务协议可采用一个私有 workspace，由服务和客户端共同使用；具体名称在搬迁时确定，CAPiX 不依赖它。

protocol 不以“客户端可能需要知道”为收录标准。公开包的类型可以直接由其公开出口消费；只有实际传输且明确编码／接纳／版本的形状才是协议。若拆分后没有独立的框架级 wire 责任，应提出 protocol 的退役方案，不为了保留包名建立空门面；已发布版本不删除，本计划也不自动执行发版或弃用。

## 3. 实施顺序

### P0：收口既有工作与建立基线

范围：当前 observer-content 迁出、运行测试夹具去耦、文档和分发配置的未提交改动。

- 核对工作树，保留并区分已实施修改、审查结果与候选设计。
- 验证既有内容交接，记录准确源码和产物批次；实施时形成独立可回退的提交，不夹入后续客户端或 Memory 变更。
- 建立协议归属台账：定义、语义所有者、运行时函数、实际消费者、目标出口、对应测试。表中明确区分现状与目标。
- 清点当前文档中已过时的包数、旧路径及来源承诺，后续随所属阶段更新，不将历史报告改写成新事实。

完成条件：既有迁移可独立解释、可验证；接下来每个提交都能确定属于哪一步。此计划本身不执行提交。

### P1：先迁两个客户端，行为保持

范围：`packages/client-runtime`、`packages/client-http`，包括包内测试、类型负例、夹具、配置和客户端行为文档。

- 迁入 Lab 私有 workspace，保留现有包名；初始仍消费当前 CAPiX protocol，不在搬目录时改会话语义。
- CAPiX 移除这两个 workspace、锁文件 importer、包边界白名单及专属消费夹具。业务协议暂时留存是一项有明确后续的过渡，不增加兼容层或第二份实现。
- 候选分发从当前 20 包改为 18 个公开框架包；同步 integration pack/check、产物消费测试及文档，不让 CAPiX 继续为 Lab 打包客户端。
- Lab 本地客户端使用 workspace 依赖，去掉覆盖它们的 tarball／候选 overrides；导入脚本仅安装框架产物。
- 将框架约束的最小回归保留在所属核心包，客户端队列、重连、预览、HTTP framing 等具体行为测试随客户端走，不能用删除测试使迁移通过。

完成条件：CAPiX 无客户端实现或测试依赖；Lab 从公开产物加自身 workspace 构建。两仓各跑自己的验证，Lab CI 不是 CAPiX 合入前置。

### P2：固定共同能力和领域事实转交接缝

这是协议解耦与 Memory 迁移的共同前置，先做一个窄闭环。

- 将 InvocationOrigin 等真实共同词汇归 contracts，保留原语义，不把 contextId 升格为资源操作身份。
- 固定读取明确区分项身份、读取依据和正文；参考 `{id?, basis, value}` 的能力形状，但具体实体自行定义必要身份和依据，不统一 revision、状态机或全量 snapshot。
- 继续使用现有 ViewSource；资源暴露实体操作，View 只持有索引与来源依据。
- 将 resources／invocation 的消息、记忆特判替换为类型匹配的有限事实转交。领域事实归生产者，解释与记录投影由明确适配提供；不能只换成 unknown 或全局事件总线。
- 用普通业务对象和现有实体各证明一次接入。证明变化后操作抛错、并发操作、确认旧效果、未知来源、关闭窗口及 strict/isolate 行为仍准确。
- 新增公共端口时给出低层精确形式和最小作者用法，避免把登记、解释、关联全部变成每个节点的重复配置。

完成条件：新增一种实体无需修改 resources／invocation／CP 的领域事件联合；具体类型不会从低层丢失；正式来源不能由“当前调用”或到达时间猜测。尚未收敛的接线形式在这里小范围验证，不将猜测直接迁到全仓。

### P3：Memory 完成独立迁移

采用已确定边界，细节以 [Memory 设计](memory-convergence-design.md) 为准：

```ts
type MemoryItem<Metadata = never> = {
  id: string;
  value: { content: string; metadata?: Metadata };
};
```

- 集合统一写入；单项 UUID 不随更新改变；不持有 Transcript，不保留核心 topic，不强制来源。
- 保留批次检查、按真实变化推进 sequence、固定操作确认、静默 restore 和当前格式拒旧规则。
- 修复已发现的依据 getter 重入及不可能固定回执，形成 Memory 自身回归。
- 实施前明确提交结果不确定后实例的可用边界；不能把本地未安装当成外部未提交。
- 完整固定材料、持久／CP codec、观测投影分别表达；不要求所有 metadata 直接 JSON 化。
- 新 Memory 类型归 memory，资源和 View 适配同步接通。旧的记录／wire 消费方做必要适配，不保留填假 topic／空来源的兼容层。
- Lab 的来源、提取、画像或业务推进规则另行适配，不提升为 Memory 的字段约束。

完成条件：无 Transcript 的 Memory 可独立运行、保存及恢复；CP 开关不改变读取内容；固定空效果、确认旧效果、提交未知和发布失败都被覆盖；已读材料不会随实体更新变化。

### P4：完成其他领域归位，并迁出业务协议

这一步清除剩余反向依赖，不能只按 protocol 的目录名搬文件。

| 当前内容                                         | 目标判断                                                                |
| ------------------------------------------------ | ----------------------------------------------------------------------- |
| Message、Transcript 的位置／范围／变化           | 领域语义归 transcript；纯跨端副本另明确 wire 形状                       |
| Memory 正文／mutation／回执／事件                | 归 memory；展示 DTO 是明确投影                                          |
| 调用来源、确实共享的关系身份或过程词汇           | 共享最小部分归 contracts；实现专属部分归 invocation                     |
| Record、归档身份、记录树约束、输出解析与校验     | 归 records 或其实际机制所有者；不能因当前在 observer 目录就一起移到 Lab |
| 通用记录树读取与查询                             | 留在 records，避免随界面迁走通用能力                                    |
| Conversation 提交、admission、文件展示、服务检查 | 归 Lab 业务协议及服务适配                                               |
| Observer overview、界面选择、内容展示及会话聚合  | 归 Lab 协议／投影；通用事实片段仍来自框架公开出口                       |
| 确有独立消费者的框架跨端 DTO／接纳器             | 留在精简后的 protocol；检查编码、格式及无平台实现依赖                   |

- 检查 records → observer/archive、记录 helper → 展示 snapshot、measurement → protocol.Message 等实际链路，分别迁移定义和运行时规则。
- 将参考业务 wire、解析和业务测试与 Lab 服务／客户端一起改为本地协议依赖。baseline 和增量使用同一投影，字段替换不能遗留旧值。
- CAPiX 的公开类型、实体和机制不反向依赖 Lab，也不为客户端界面保留类型别名或旧 API。
- 为破坏性公开出口变化记录明确变更和版本计划；发布另行执行，不恢复旧格式读取支路。

完成条件：低层机制和实体不依赖业务 wire；protocol 不承担实体本体或运行规则的所有权；无导入环、无跨包私有路径、无两份含义不清的同名定义。

### P5：收口通用实体的作者入口

P2 已证明机制，P3／P4 已清除专用假设；这里验证作者能否自然使用这些能力。

必须交付公共契约、可复用适配和完整的最小例子。至少覆盖：可修订业务状态、只追加材料，以及新的 Memory；三者进入相同 Resource／View／调用／可选 CP 与记录链路。

- 业务只负责自己的 value 和更新规则，不需要补 topic、消息角色、来源列表或固定业务状态枚举。
- 自己的实体可逐项选择稳定读取、View 索引、变化捕获、持久化或固定写入确认，不需要实现一个巨大接口。
- 若仍需反复手写相同固定与版本管理，比较“业务对象＋适配”与“可选泛型容器”的实际代码，形成最小复用实现；其公开命名和包位置在证明职责后确定。
- 专用实体不继承该容器；容器不自动获得历史查询、事务、幂等、授权或 CP 重做能力。
- 单项读和单项变化不得隐式处理全部历史；显式全集读取仍按实际成本说明，不为本轮扩展成实体历史治理项目。

完成条件：在 CAPiX 自身的独立消费例子中，作者不用改内核或协议枚举就能接入新的业务实体。交付不止是一套泛型类型，也不以必须新增 `Entity` 类或包作为成功标准。

### P6：仓库与契约收尾

- 更新 AGENTS、项目组织、contracts/protocol、实体／记忆／观测文档及公开出口说明；研究报告保留历史状态。
- 清理已无消费者的旧类型、helper、协议出口和测试夹具，删除前查实际引用，不因为名字旧就删能力。
- 完成干净产物构建、类型与负例、包内和仓库检查、frozen-lockfile 安装、发布产物与仓库外公开入口验证。
- 更新依赖白名单、测试发现、候选包清单、Changesets 和文档链接。包数来自实际清单，不能只替换文字中的 20／18。
- 形成分阶段提交、迁移说明及单独的发布准备；没有发布、推送或清空现有数据的隐含动作。

完成条件：当前文档描述真实实现；无 Lab 检出也能证明 CAPiX 全部框架契约；Lab 独立使用新框架产物完成自身适配。

## 4. 顺序、并行与提交边界

```text
P0 既有工作收尾
  → P1 客户端归 Lab（暂用现有协议）
  → P2 共同能力／领域事实接缝
  → P3 Memory 独立迁移
  → P4 剩余领域类型归位／业务协议归 Lab
  → P5 通用实体作者入口验收
  → P6 文档、依赖、产物总验收
```

P1 期间可以只读盘点 P2／P4；P2 之后，P3 的 Memory 与 P4 的消息／记录归属可以分支推进，但共享契约变更要先合并。P4 的业务协议迁移必须等待相关领域出口稳定。Lab 的策略与 UI 适配可随对应产物独立推进，不让两个仓库共用一个必须同时通过的测试流水线。

每个合入单元都保持构建与相应回归通过。类型移动涉及全部生产者／消费者时，作为一个原子改动合入；不提交需要下一提交才能编译的半套接口，不长期保留双实现。代码验证与模型语义评估分开，本轮普通验证全部离线。

## 5. 谁验证什么

| 契约                                     | 测试所有者                                 |
| ---------------------------------------- | ------------------------------------------ |
| 稳定值、共同材料类型、错误身份           | contracts                                  |
| 资源窗口、操作关联、类型化事实转交       | resources；真实调用关联由 invocation 验证  |
| 捕获、发布与消费故障                     | changes                                    |
| UUID、内容固定、批次、固定确认、持久失败 | 对应实体包                                 |
| scope／stamp／稀疏读取／成员变更         | view 及具体来源适配所属包                  |
| 调用接纳、退出、CP 保存与恢复不扩大      | invocation／checkpoint；组合接线归 runtime |
| 记录实体及通用关系、投影适配             | records／实际适配所属包                    |
| 保留 wire 的编码及接纳                   | protocol                                   |
| 包依赖、公开出口、产物安装               | CAPiX 有限仓库检查与 integration 消费夹具  |
| 会话队列、HTTP、具体服务持久／恢复、页面 | Lab 的各所属包和服务                       |

框架发现的违约必须落在 CAPiX 可独立执行的回归，不能只在 Lab 测过就算完成。Lab 不承担证明框架正确性的角色；它也不能因为 CAPiX 测试通过就省掉自己的业务适配验证。

## 6. 本轮完成的可检查定义

全部满足才称为这轮“内核边界清晰”，而非宣称框架从此没有其他设计问题：

1. 新业务实体不需要修改资源／调用／CP 的特定实体分支；所需能力由明确契约组合。
2. Memory 不依赖消息实体或固定业务来源，更新与恢复承诺仍完整。
3. contracts 没有变成领域类型汇总；protocol 仅拥有真正的跨端责任。
4. 通用记录保留真实关系，业务展示不倒灌为运行事实；记录与恢复依据分开。
5. CAPiX 中没有当前参考客户端、参考装配、服务协议的隐式必需依赖。
6. CP、资源、实体各守自己的承诺，不引入统一事务、全局当前调用、自动历史或强制生命周期。
7. 测试跟随所有者，CAPiX 与 Lab 独立构建验证，跨仓消费只走明确公开产物。

P0＋P1 已完成；下一步是 P2 的共同能力与领域事实转交接缝。Memory 的领域选择已经明确，后续应转为实施与验收，不再回到“用一种记忆承载所有业务对象”的讨论。
