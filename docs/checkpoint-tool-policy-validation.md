2026-11-07，第七轮隔离实验。承接[作者契约验证](checkpoint-author-contract-validation.md)。本轮新增实验代码和报告，未修改生产 Invocation、Frame v5、ModelExchanges、ToolLoop 或数据库格式；没有提交代码、调用真实模型或重启服务。

## 1. 交叉分析后的判断

Claude 建议的三个验证方向都值得推进：按成立时机拆检查、固定交换前缀、按 key 缩小关系查询。但需修正几个依据，不能直接把建议变成内核规则。

| 评审意见                               | 核对源码后的边界                                                                                                                    |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 预检拒绝形成新交换版本，只记录在 state | 反馈已经由 `ModelExchanges.complete()` 保存。它推进同一交换的 revision 和 `state.current`；所有槽位完成后才追加到 `state.exchanges` |
| 让每个交换记录唯一前驱                 | 实体目前允许 `[A,B]`、`[B,A]`、`[B]` 等明确选择，`closed()` 不推断因果顺序。唯一前驱不能强加给交换本体                              |
| 历史断言成立后只检查一次               | 必须固定该断言的全部依据。模型输入稳定，不代表作者后来选择的 refs 次序、前缀或当前 state 没有变化                                   |
| key 索引替换 find                      | key 不是身份。不同模型回复可重复 key；同一查询范围也不能偷偷假定唯一。还要保持作者 refs 的首次匹配顺序                              |
| ToolLoop 只有最多 32 次模型调用        | 成立，但每次还可能派发多项工具。这个约束不能推导通用 Invocation 的子关系数量上限，也不能用模型 token 成本掩盖 CP 的同步计算成本     |

本轮把“交换的固定内容”与“某次流程选择的交换序列”分开：后者使用独立的前缀元数据实验，不把前驱写到生产实体上。**这是表示候选，不是新增内核实体或生命周期的决定。**

## 2. 对照的不是简化版业务规则

[夹具](../examples/checkpoint-facts-study/tool-policy-fixture.mjs)通过公开包构造真实 `ToolLoop`：

- 热检查直接调用原声明的 `point.check`。
- 外部确认直接调用原 `completed.resume.run`，实际经过 `confirmExchanges` 和 `finalText`。
- 人工回复、固定操作和反馈槽位经过真实 `ModelExchanges` 保存/校验；接纳凭据按公开形状构造，操作身份来自夹具关系，未覆盖真实资源 reception 取源。
- 不调用模型或工具；事实适配器代替已经认证的 ChildFacts，不伪称获得了 Invocation 的真实引用权限。

13 个连续快照覆盖：模型等待、模型接纳、工具等待、成功接纳、预检拒绝、失败 handled、关闭交换、第二次模型请求复用相同工具 key，以及最终回答。

测试分清了三个认证位置：

```text
关系/值/槽位认证       作者 point.check           恢复时实体确认
真实身份与合法状态 → state 与所选事实吻合 → 正文、反馈、凭据仍有准确依据
```

不能拿其中一个代替另外两个。以下基线行为被如实保留：

- `children 数量 === refs 数量之和` 只检查数量；重复某个 ref 并漏掉另一个，可以骗过这项数量核对。最终的实体确认仍可能拒绝。实验没有把去重覆盖检查冒充等价优化。
- `closed(prefix)` 核对准确版本和完整反馈，不检查作者的前缀顺序。乱序前缀可以通过单独的实体确认，但会被作者 check 拒绝。
- 外部反馈已经保存、父关系仍 pending，可以通过原实体确认，留给后续接纳路径确认固定效果。这不是“所有父关系 pending 的调用都有宿主恢复资格”。

## 3. A/B 拆分成立，但依赖失效规则必须明确

[候选检查](../examples/checkpoint-facts-study/tool-policy.mjs)保留原业务条件，采用显式的事实更新、引用追加/替换和前缀追加/替换操作。

| 变化                             | 候选的检查范围                             |
| -------------------------------- | ------------------------------------------ |
| 新模型被选择                     | 检查它的固定输入与对应前缀                 |
| 当前交换关闭并追加               | 补查原当前模型的接纳凭据与新增关闭引用     |
| 某个已选模型事实变化             | 重新检查该模型的所有选中位置               |
| 模型 refs 重排、移除，或前缀替换 | 对历史关联重新做完整 A 检查，不冒用原证据  |
| 工具 refs 重排                   | 重新建立作者出现次序索引；仍按首次匹配选择 |
| state/current/cursor/active 变化 | 每次检查 B，即使没有新关系                 |
| 冷恢复或无已确认的检查基线       | 完整 A+B                                   |

只有检查成功且实验投影收到准确版本确认后，才清除待检查变化。check 失败不安装部分证据；确认前发生变更，旧确认 token 失效；提交结果不确定后禁止继续复用，重新进入冷验证。

这里的 token 只是**实验检查投影的版本凭据**，不等于 Store 回执。前几轮 FactStore 的 owner/revision/cursor/chain/headDigest 认证仍是独立机制；生产绑定尚未把两者连接起来。

这是作者明确拆分一份业务策略，不是内核缓存任意 `check`。Schema/policyVersion 固定也不能证明闭包是纯函数。实际迁移仍需保留映射/选择策略的纯函数契约及冷恢复复验。

### 查询计数

产物见 `.capix/tool-policy-validation-20261107-final/summary.json`。计数用于检查范围，不是 CPU 或完整 save 的性能对比。

| 范围                     | 结果                                                 |
| ------------------------ | ---------------------------------------------------- |
| 原检查，13 个快照        | 31 次模型 `require`，44 项完整关系枚举               |
| 候选，13 个快照          | 8 次模型前缀断言；不重查已离开当前推进位置的历史模型 |
| 候选再次检查相同最终状态 | 0 次模型前缀断言；仍执行 1 次当前组合查询            |
| 测试快照转增量命令适配器 | 88 次比较，单独记录，未隐瞒在“增量成本”之外          |

原模型 `require` 包含 A 和 B；候选 8 次统计的是 A，不能直接相除宣称提速比例。候选 B 的工具处理仍检查当前回复已经处理的槽位，并非每次只读一个事实。

**完整快照到命令的 `feed()` 只是测试设施。** 它扫描原快照来生成变化，不能成为生产增量实现；未来绑定必须消费真实的事实/选择变化。另有直接调用增量命令的用例，验证重复检查不需要该适配器。

本对照故意保留旧输入 `{exchanges: [...]}`，新模型检查仍要读取自己的完整前缀，累计这部分仍可能 O(M²)。因此它证明 A/B 的语义，而不是已经完成整个 ToolLoop 的增量迁移。

## 4. key 索引保留多值、区间和作者顺序

[关系索引](../examples/checkpoint-facts-study/tool-relations.mjs)的范围为：

```js
relations.query({ parentId, position, contract, key, after, before });
```

它返回区间内所有候选，不覆盖同 key 项。调用者继续核验准确输入、引用选择、接纳状态和凭据。

两个原规则有细微区别，实验没有抹平：

- 热 `check` 对当前工具只使用 `child.order > model.order`。
- 恢复 `confirmExchanges` 还要求 `child.order < nextModel.order`。

作者 refs 的顺序不一定等于创建顺序。通用兼容辅助明确保留扫描成本；ToolLoop 候选则维护“每个孩子在所选数组中的首次位置”索引，在匹配候选中取最小位置。正常追加局部维护，任意重排重新处理其选择范围。重复出现不消失，也不删除真实关系。

4096 项相同 key 加 4096 项其他父级关系的索引测试，区间内两个候选只进行了 24 次比较、返回两项；这证明缩小了查询范围，不证明任意 key 分布都 O(1)。重复候选很多时仍按候选数付费。

[索引版外部确认](../examples/checkpoint-facts-study/tool-confirm.mjs)与真实 `completed.resume.run` 对照：原回复、预检反馈、feedbackDigest、原 operation，以及 reply/feedback/tool output 字节限制均保留。冷恢复完整重建索引、遍历实体反馈；只移除了每条反馈再扫描所有工具 refs 的重复工作。

最终样本冷建 6 条关系、处理 6 个 refs 次序、3 次候选查询和 3 次准确输入比较，读取交换实体 4 次。实体/反馈完整认证并未变成常量成本。

## 5. 前缀是固定选择，不是交换本体的唯一历史

[ToolPrefixIndex](../examples/checkpoint-facts-study/tool-prefix.mjs)使用独立 SQLite 元数据作隔离验证：

```js
// 同一交换可以被另一个明确的选择序列以不同顺序引用。
const next = prefixes.append(previous, exactClosedExchange);

// 候选 child input / state 保存紧凑 token。
const input = { previous: next };

// 真正生成请求时仍明确读取完整材料。
const entries = prefixes.materialize(input.previous);
```

每个前缀节点保存自身身份、明确的选择 owner、collection/scope、前一个 token、准确关闭引用、数量和摘要。单次新追加核对真实实体的 `closed([ref])`，并在自己的事务中比较当前 tip。它不遍历祖先。

其中 owner 是该实验明确选择序列的身份；scope 仍是业务分组，不从它推断调用权限。单一 owner 内线性追加及不重复交换是 ToolLoop 候选策略，不能升格成所有 ModelExchanges 使用者的规则。两个 owner 可以对同一实体选择不同顺序。

内容读取与追加位置分开：历史 token 代表自己的祖先材料；后续 tip 用于新追加的并发核对，不能把后来内容自动纳入旧请求。冷打开已有元数据不自动建立缺失的 owner；缺少所选祖先、交换或准确版本时拒绝。

128 次追加的组件计数：每次新追加进行固定数量的元数据点查和一次准确交换检查，累计祖先遍历为 0；紧凑输入仅因 count 位数增加 2 B。完整请求展开则明确访问 128 项。SQLite 的索引成本、反馈检查和元数据大小仍存在；不能把“点查次数固定”写成严格常数 CPU。

这组 128 项只测前缀表示组件，不伪称突破了生产 ToolLoop 的 32 次模型调用预算。完整模型请求与原数组路径逐项等值。

## 6. 前缀与 CP 不原子，但交接可确认

[硬退出实验](../examples/checkpoint-facts-study/tool-prefix-process.mjs)使用三个独立库：真实交换实体、前缀元数据、前几轮 FactStore/FactCall。head 的 state 仅保存紧凑 token 和固定确认依据。

| 硬退出切点                   | 新进程处理                        |
| ---------------------------- | --------------------------------- |
| 实体已保存关闭反馈，前缀未写 | 确认原反馈，再建立一次前缀        |
| 前缀已提交，CP 尚未保存      | 按准确 previous/ref 确认原前缀 ID |
| CP 写入但事务未提交          | 沿用旧 head，再确认原前缀         |
| CP 已提交                    | 读取 token，完整核验其所指材料    |
| 最终交付已提交               | 保持终态，不推进任何库            |

这些切点使用子进程直接退出，绕过 finally。恢复均不再次写入已成立的实体反馈，不补造模型请求或工具调用。缺前缀行、损坏正文、缺实体、缺准确交换或 CP input fact 均拒绝。单独还验证前缀事务内两处退出回滚、提交后退出准确确认。

这里验证的是**固定交接与实验 head 的组合**，没有实际运行模型/工具，也没有承诺跨库事务或真实宿主完整恢复资格。前缀写入后 CP 失败仍会留下先成立的元数据；本轮不做退休或自动回滚。

## 7. 本轮结论及尚未合并的接缝

已得到实际证据的部分：

1. 真实业务 check 可以按成立时机拆分，前提是对选择和状态的变化有明确失效规则。
2. key 索引可以减少关系匹配范围，同时保持原选择顺序和多值语义。
3. 紧凑前缀能准确代表已选择的关闭交换材料，并与实验 CP 进行可确认的持久交接。
4. 不需要改变调用身份、强制分段、continue-as-new 或自动丢弃历史。

尚不能宣布作者契约或 Frame v6 已完成：

- A/B 对照仍用旧数组输入，前缀表示实验是另一组。两者还没有与完整 Invocation 事实、typed refs/reception、point 绑定合成一条生产恢复链。
- 原工具 Completion 的更深层输入、资源捕获、独立 Interaction 请求核对必须一起适配，不能只把顶层 state 改成 token。
- 候选稳定值仍只在实验内成立；生产“保持原引用”契约、codec 往返语义和跨包固定证据尚未迁移。
- 索引来自已经认证的关系。单独调用原作者 callback 不能代替身份、order、成员、Schema 和拒绝恢复的机制核验。
- 内存驻留、持久保留和冷恢复全量成本仍各自存在；没有用封口来替代这些议题。

下一步宜把完整 Invocation 事实按生命周期逐项映射到实验事实行：输入、等待、返回、receiving、accepted/handled、失败与最终交付；把作者槽位身份、检查基线和恢复资格连起来。前缀保持业务侧候选，验证它能通过普通资源兑现紧凑输入即可。任何改变真实交付含义、恢复覆盖范围或结构生命周期的决定，另行明确讨论。
