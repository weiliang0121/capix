# 固定事实与增量 Checkpoint：生产迁移

2026-11-07。承接[接入设计](checkpoint-facts-integration-design.md)及用户对生产迁移的授权。本文说明正式调用数据和持久表示的变更，不把实验模型变成另一套运行对象。

本文保留首次生产迁移的实施与测量记录；下文的“本轮”“未完成”和兼容安排均指当时阶段，不是当前待办或兼容承诺。后续已完成增量选择，且当前只接受 Frame v6、Conversation schema 8 / Observer schema 6 的完整当前库，不迁移旧库、解析旧 v5 或读取旧文本交互。当前契约见 [Checkpoint](checkpoints.md)，增量选择及后续验证见[增量引用选择](checkpoint-selection.md)。

## 1. 已采用的决定

这轮沿用之前逐次验证的决定：Context/Relation 持有固定事实，Invocation 协调活动，CP 消费同一份依据。没有新增 FactCall、Progress、Action 实体，没有改用重放或要求长任务切段。

交叉审查中的范围收缩已接纳：

- `point.check` 查询只在同步检查内有效；已取出的固定值可以留存。
- 每次仍执行 `point.check`，不建立作者按 point 维护的增量认证基线。
- many 仍提交完整有序数组，保留重复出现与逐点布局；本轮不增加增量选择 API。
- `currentInput`、完整直接关系及逻辑 Frame 8 MiB 边界保留。

原“成功保持调用者原引用”改为“正式交付保持系统持有的稳定值”。这是所有调用的公开语义变更，并非仅开启 CP 时的复制技巧。原抛出异常和能力对象不属于正式数据值，仍按原端口和归属传播。

## 2. 固定边界与对象归属

```text
调用者输入草稿
  → stableValue
  → validate / capture / refine
  → Context.input

业务返回候选 → 固定候选 → 原退出、清理和故障判定 → 正式交付
接纳回调结果 → 固定结果 → reception.check → Relation.accepted/handled

Context / Relation 固定事实
  → Children 登记实际变更
  → InvocationCheckpoint 首次编码新增事实
  → 当前 state / refs / point.check
  → Store 同步提交值块、关系变化与 head
  → 准确回执后安装发布依据
```

固定候选不等于成功：输出检查、取消、资源关闭、子调用退出及 CP finish 仍可阻止成功。父接纳、资源效果和 CP 仍分别成立；回执丢失不等于未提交。数据固定不恢复草稿，不承诺外部副作用幂等，也不改变取消后的接纳收尾规则。

共同纯值实现位于 `@weiliang0121/capix-contracts`。普通记录、null 原型记录、稠密数组、undefined/null/boolean/string/有限 number 可作为正式数据；保留缺失字段、undefined 和 -0 的区别。Date、Map、Error、函数、类实例、循环和 accessor 不静默转换，业务显式形成数据表示。Proxy 元操作可能执行，不将它宣称为沙箱。

固定操作复制未知来源，不冻结调用者草稿。私有证据只授予本实现产生的副本；单次记忆表避免 DAG 重复复制，逐节点展开计量防止共享子图绕过预算。可信根与可信子图可直接复用，`Object.freeze` 和类型断言不授予信任。证据不跨进程，也不证明任意 codec 纯度。

输出增量在生产者 delta 契约通过后固定为数据事件，仍是预览，不变成 CP 的历史事实。资源方法的原始结果、资源 origin、Work、signal 和配置闭包不进行一锅式冻结。

普通数据边界的独立限制为深度 64、展开值 1,000,000、展开文本 64 Mi UTF-16 单元（含记录键及重复引用）。它们是防御边界，不是精确内存或最大合法模型请求承诺；CP 仍使用更小的独立持久限制。大值首次固定仍支付实际遍历成本，支持域收窄不会因关闭 CP 而取消。

失败事实保存有界固定诊断，原 Error 不被替换。诊断不求值作者 accessor 或数组 getter；标准堆栈只有在不会间接调用作者 getter/替换格式化器时读取，否则保存明确标记。这修复了将诊断从可选记录移到必经路径时暴露的副作用风险。

## 3. 热保存与冷恢复

正式数据的持久表示在首次需要保存时按准确事实角色和固定契约形成：encode、固定编码值、decode、固定解码值、内容保真比较，接纳契约还检查解码结果。后续保存引用已成立的表示，不再次调用旧事实 codec 或 reception.check。不是按任意 `(对象, codec)` 做全局缓存；同一正文属于不同孩子时仍有不同事实归属。

`InvocationChildren` 直接登记关系变更，不通过可关闭的观测流收集，也不每次扫描全历史找差异。保存的短同步截面内拒绝重入修改；codec/check/观测回调后，提交前复核活动窗口、修订和事实位置。保护不跨业务 await，不锁整棵树。

物理提交 `CheckpointCommit`（v6）包含：

| 内容                    | 每次保存处理范围                                       |
| ----------------------- | ------------------------------------------------------ |
| 输入与已交付/已接纳正文 | 仅首次发布，之后使用 owner 范围内的 ID/digest 引用     |
| 关系身份与状态          | 新增或确实改变的直接关系                               |
| point/state/refs        | 本次完整提交，仍按实际大小编码和核验                   |
| point.check             | 每次执行；点查按需，values/list/完整 many 读取按全量计 |
| head/CAS/容量/引用认证  | 小 head、变更关系、显式 refs 和已认证聚合量            |

没有被 refs 选中的关系也必须通过结构及状态认证。零正文变化仍可有新关系、新选择、新 point 和新 revision。多个事实可以共享正文，不按正文摘要合并调用身份。

低层 writer.save 返回回执；业务 `work.checkpoint` 仍返回 void。需要完整逻辑 Frame 的宿主、诊断和测试显式调用 `Store.read`，该读取不计为增量热写。正常 captured/saved 观察没有扩展为全量镜像。

冷读取重新组装完整 Frame，核验块内容摘要、关系、引用计数、容量聚合、owner/contract/input、修订及终态。`CheckpointHead.publication` 以可序列化的引用元数据表达物理依据，复制 head 后仍可核验；内核不能依赖 WeakMap 身份才能恢复。新的进程不继承本地信任。

随后仍检查准确声明、解码材料、reception 契约、最后保存 point 的 state/refs 和 check，才开放恢复处理。缺首子 CP、失败子调用、旧终态、缺失交互反馈和实体确认等原拒绝边界不放宽。无子 CP 的成功交付仍可由父 CP 首次保存。

## 4. 持久兼容与保留

新 Invocation 写 Frame v6；旧 v5 可读作历史，但不自动升级为稳定事实执行恢复。业务 checkpoint key/version 不替代格式版本。自定义 Store 必须接收增量 Commit，并在 read 中提供可重新核验的完整 head 和 publication；旧的 save 返回完整 Head 的适配器也需迁移。

Memory、Conversation SQLite 和 Observer SQLite 已适配。Conversation 数据库升到 v7，新建值块及关系存储；旧内容、交互、head 和身份依据保留，旧镜像不伪装成新语义。Observer 仍使用自身内容库版本，独立安装 CP 存储表。

每个调用保留当前关系投影、当前 head、终态交付和它们引用的正文。被后续 state/refs 替代且无引用的块正文退休，身份及摘要依据继续防止错误重供；旧镜像 ID 保持拒重。没有自动整树退休、磁盘恒定容量或跨实体事务承诺。压缩按块进行，完整重建仍受逻辑 8 MiB、100,000 值节点、4,096 直接孩子与深度约束；重复引用按展开出现次数计费。

## 5. 验收范围

测试保留并适配原断言的目的，而非删除不兼容用例：原引用断言改为“原草稿隔离、正式值冻结、Context/输出/交付使用同一正式值”；富值正例改成显式业务数据，另保留富值拒绝测试。拒绝时机提前到 Store 认证的用例同时覆盖不产生新副作用。

新增或加强的证据包括：

- CP 开/关下，输入先于 capture/refine 固定；返回先于清理固定；accepted/handled 一致。
- 固定失败不可被业务 failed 接收；原异常身份、并行接纳和取消收尾保留。
- 第二次及以后保存对旧事实的 encode/decode/reception.check 为零，当前 point.check 仍执行。
- 异步 check、保存重入、逸出查询及在下一次保存中使用旧查询均拒绝。
- 低层 check 也不能改写关系 target/contract/progress/reception；只固定新关系的小元数据，不重新遍历已固定正文。
- Store 接收的提交头元数据也不可变，不能在返回回执前改写待核对的请求。
- 恢复中的原输入、子输入及完整 head 比较保留 -0/+0 区别，不能由旧宽松相等算法越过新值域约束。
- finish 输出也进行 codec 保真检查；finish 已提交但回执失败不补写假失败。
- 三个后端的值块篡改、关系拒改、缺失/退休值、重复 refs、CAS、终态、事务失败及冷读取。
- 真正跨进程的并行恢复、默认材料回答、工具反馈与助手消息落实边界，保留原“不重发/缺依据拒绝”的断言。

测试与测量产物集中在 `.capix/stable-facts-migration-20261107/`；本轮不调用真实模型或改动用户运行数据库。

最终 `pnpm check` 全部通过：工作区构建、类型检查、3,289 项测试（0 失败、0 跳过）及全仓格式检查。完整日志为 `.capix/stable-facts-migration-20261107/check-final.log`；`git diff --check` 亦通过。这组迁移、既有优化与前几轮验证已于后续推进前提交为 `ee96942`。

## 6. 性能与尚存成本

详细配置、独立计数及数据见[计算范围复验](stable-facts-migration-performance.md)。保存点没有减少；统计区分完整同步 checkpoint、其中 Store 时间、finish、冷读取和首次数据固定，增量提交字节不与旧完整逻辑 payload 混算。

有界 current 选择、2,048 个孩子时，父 CP 累计 Memory 为 0.671/0.672 秒（旧版 48.296 秒），SQLite 为 3.496/3.469 秒（旧版 57.812 秒）。累计提交关系从旧版 4,198,400 条变成 4,096 条，正是每个孩子派发和接纳各一次；没有省掉派发前的恢复屏障。

完整 all refs 数组仍需全量构造、编码、认证及作者读取。首轮 SQLite/all/512 确认存在回退；去掉每个引用重复准备 SQL、同次提交重复查询及零净变化 metadata 写入后，从 11.16–11.83 秒降至 9.67 秒，仍慢于旧版 6.52 秒。报告保留这项结果，不以 current 的收益抵消，也不把这个写法报告为有界。同次复测的 current/512 为 0.730 秒；2 MiB 输入重复保存的中位数由 1.883 ms 降至 0.736 ms，首次保存仍约 73 ms。

无 CP 的真实三层 Runner 也有成本：100,000 个记录组成的未知输入每次进入约 133–137 ms；显式固定一次约 148–152 ms 后，跨三层运行中位约 0.23–0.25 ms。真实无 CP 对话装配、2 MiB 固定历史、离线 Provider 的整体每次运行约 5.7 ms，包含材料/Schema/JSON/实体等成本，不能全部归因于固定操作。

已明确保留的成本：完整 refs 数组重复提交、作者全量 check、大 state 重编码、首次隔离大输入、实体每个 revision 首次构造完整快照、活调用持有全部关系，以及冷恢复完整认证。它们不因本轮已固定旧正文而自动变成常量。

当轮未同时实施 many 增量 API、实体分块、内存卸载或保留策略；后续 many 增量选择已经完成，见文首现行入口。实体分块等仍是独立问题，不把强制 continue-as-new 当作解决这些问题的前提。

基线提交后的首个小闭环见[关系查询优化与复验](checkpoint-relation-query-validation.md)。它保持存储读回和引用认证范围，只复用准确未变行的解析结果；本节性能数字仍指上面这轮迁移本身。
