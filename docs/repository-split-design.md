# 仓库拆分设计：框架、实验与参考装配

后续归属说明：本文保留当轮盘点、包数和验证事实。Observer 内容组合（ActiveView、ConversationContent、同步及测试）现已整体迁至 `capix-lab/services/observer-content`，不再是 CAPiX 包；尚未成为通用公开预设。当前 CAPiX 为 18 个公开包加 2 个私有客户端包，候选分发共 20 包，见 [当前包边界](organization.md) 与 [分发规则](npm-publishing.md)。

状态：第一版已实施；本文保留目标设计及原盘点，实际完成范围、过渡项和验证见 [拆库实施记录](repository-split-implementation.md)。未创建远端、发布新包或改变可见性。

本文描述目标归属与推进顺序，不替代当前 [项目组织](organization.md)、[模块契约](README.md) 和 [发布规则](npm-publishing.md)。命名依据与公开前准备见 [包命名与开源准备](open-source-preparation.md)。下文的 `capix-lab` 是新仓库候选名称，不指向已有的 `capix-explorations`，也不指向任何外部业务仓库。候选目录不是已批准的新包或新内核能力。

## 1. 目标与划分依据

先形成两个仓库：

- **CAPiX**：维护框架能力、可复用集成、预设、策略与 UI，以及这些能力的契约、回归和发布。
- **实验与参考装配仓库**：使用 CAPiX，维护可运行的参考宿主、完整业务场景、规模验证和历史研究。

未来第一方 Agent 产品独立建仓；本次不提前创建产品仓库。17 个基础包继续在 CAPiX 的同一个 monorepo 内协作，不按包拆成 17 个仓库。

判断归属时分别回答三个问题：

| 层次       | 判断问题                           | 结果                                               |
| ---------- | ---------------------------------- | -------------------------------------------------- |
| 对象与模块 | 谁持有状态、维护不变量、提供端点？ | 决定代码内聚，不因拆库重新定义调用或实体           |
| 包         | 谁提供可独立消费的公开契约？       | 决定入口与依赖，不因目录存在就新建包               |
| 仓库       | 哪些变更需要共同审查、验证和发布？ | 决定协作边界，不按 server/client/services 名称切割 |

通用预设可以留在框架仓库，同时仍然是可替换策略；留仓不代表成为内核规则。参考服务中出现的可复用能力，需要先确定边界再迁出宿主，不能让外部作者复制服务内部实现。

## 2. CAPiX 的目标目录

下面是逐步完成拆分后的目标形态。结合开源命名讨论，长期目标调整为统一的 `packages/<职责>`：源码目录表达独立包，文档表达内核、实体、预设、集成及 UI 等阅读分类。初稿保留现有位置的安排作为迁移中间态，不再作为最终布局。

`server` 容易让执行库被理解为网络服务，但这些包也被 CLI、测试和内嵌宿主消费；移除该目录分类不改变 Node 依赖，也不承诺浏览器支持。`client` 在确实表示远端消费角色时仍然保留在包名中。现有 17 个 npm 包名和公开出口不随目录调整改变。

标为候选的目录，仅在对应能力完成独立契约后建立，不先创建空目录、空包或统一门面。目录迁移单独验证，不与开源可见性切换或全部宿主拆分绑定。

```text
capix/
├── packages/                   # 可复用包平铺；现有公开包身份不变
│   ├── contracts/              # 进程内共同契约、稳定值、统一错误身份
│   ├── protocol/               # 已明确跨端的纯值与接纳契约
│   ├── resources/
│   ├── structure/
│   ├── invocation/
│   ├── checkpoint/
│   ├── runtime/
│   ├── interaction/
│   ├── transcript/
│   ├── memory/
│   ├── view/
│   ├── measurement/
│   ├── records/
│   ├── changes/
│   ├── diagnostics/
│   ├── model-provider/
│   ├── model-exchanges/
│   ├── client-runtime/         # 现有私有包：Conversation／Observer 消费生命周期
│   ├── client-http/            # 现有私有包：上述客户端的 HTTP 适配
│   ├── tool-loop/              # 候选：普通 Group 工具循环预设
│   ├── observer-content/       # 候选：内容组合及 Observer 默认材料策略
│   ├── sqlite-checkpoint/      # 候选：不含业务会话表的 SQLite CP 适配
│   └── react-observer/         # 候选：可嵌入的 React 观测 UI；不是整个参考应用
├── examples/                   # 少量最小用法，持续对齐当前公开 API
├── test/                       # 当前契约、反例、跨进程与公开包回归
│   └── fixtures/               # 本仓回归需要的最小夹具
├── benchmarks/                 # 候选：与当前实现同步的确定性核心基准
├── docs/                       # 当前契约、使用说明、框架设计与证据入口
├── scripts/release/            # 构建、产物校验、本地交互式 npm 发布
├── .changeset/                 # 公开包版本与变更记录
├── .github/workflows/          # CI、自动版本 PR；不自动发布 npm
├── package.json
├── pnpm-workspace.yaml
└── pnpm-lock.yaml              # 本仓唯一锁文件
```

当前 `client/*` 仍是私有包，而且依赖具体对话与 Observer 协议；保留它们不等于已提供任意业务的通用客户端。`packages/client-runtime`、`packages/client-http` 是保留现有职责的目标路径，当前私有身份不会因移动目录自动公开。新增外围包的名称、公开范围和版本分组分别审查，不默认加入当前 17 包 fixed 组，也不把目录层级直接拼进 npm 包名。

不再建立 `packages/core/entities/presets/integrations/ui` 多套强制分层：这些分类服务于阅读，可能交叉，不应决定一个包能否复用或成为运行依赖。包内目录仍按对象与职责组织。

最终目标中，具体参考服务与参考应用不再占据框架根目录。迁移期间允许 `services/`、`apps/` 继续存在，直到依赖和测试交接完成；不能通过删目录来宣称边界已收敛。

这些名字描述职责，不要求一次完成所有重排。搬迁初期可以保留原实验目录名，先保证导入、命令和报告可追踪，再按阅读需要整理。

三个实验目录有不同承诺：

| 目录          | 承诺                                              | 不应混淆的内容                             |
| ------------- | ------------------------------------------------- | ------------------------------------------ |
| `scenarios/`  | 在所锁定 CAPiX 版本下可运行，说明一个完整协作场景 | 不是新的内核 API                           |
| `benchmarks/` | 固定条件、测量口径、依赖版本和运行命令            | 不能把某个宿主的容量上限宣称为框架普遍上限 |
| `studies/`    | 保存当时的问题、候选和证据，标明适用基线          | 不是必须兼容最新包的正式实现               |

参考宿主仍可以是本仓私有 workspace，不必为了跨仓而把完整服务发布 npm。宿主拥有的数据库、归档策略、模型配置、页面入口和部署参数留在这里；不存在框架默认读取实验仓库配置的路径。

## 4. 当前代码到目标归属的映射

| 当前位置                                                                                      | 目标归属                                                | 迁移条件                                                               |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------- |
| `contracts/`、`protocol/`、`server/*`                                                         | CAPiX `packages/<现有包后缀>`                           | 独立迁移目录；不改包身份、执行语义或 CP 格式                           |
| `client/runtime`、`client/http`                                                               | CAPiX `packages/client-runtime`、`packages/client-http` | 保留实际协议范围；外部参考应用采用它们前，先确定分发方式与包名         |
| `services/observer-content`                                                                   | CAPiX 的内容组合／策略候选                              | 与具体服务无反向依赖；默认 ActiveView 策略仍可替换                     |
| `services/conversation/src/tools/{loop,registration,catalog,model,budget,resources,types}.ts` | CAPiX 的工具循环预设候选                                | 梳理对服务内 codecs、反馈读取、pending 类型的依赖；不建立新调度层      |
| `services/conversation/src/tools/answer.ts`                                                   | 参考装配优先                                            | 当前耦合材料类型、提示文本与回答预算；若形成独立可替换策略，再单独晋级 |
| `services/conversation/src/tools/hosting.ts` 及对应宿主代码                                   | 实验仓库的参考宿主优先                                  | 交换归档、历史工具、入口预算与阶段解释按真实职责交接                   |
| Conversation 的材料准备、记忆维护等组合                                                       | 逐项判断                                                | 可复用策略留框架是候选，不以已有 export 自动认定为公共包               |
| 两个服务的 `persistence/`                                                                     | 宿主存储组合随服务迁移                                  | 通用 CP 适配可另行提取；不把业务表与归档预算一起提升为通用存储         |
| `services/observer/src/observation`                                                           | 观测能力提取候选                                        | 分开记录查询／投影与具体会话目录、业务角色和宿主资源查找               |
| `apps/observer`                                                                               | 拆为可复用观测 UI 与参考页面                            | 当前同一个 Vite 应用构建两个入口，不能直接整包划走                     |
| `examples/dictionary.mjs`、`runner.mjs`、少量资源／结构用法                                   | CAPiX                                                   | 使用公开出口、离线、规模小、持续维护                                   |
| 完整对话、真实模型、多会话与大型实验                                                          | 实验仓库                                                | 与其服务依赖、测试和报告一并交接                                       |
| `examples/checkpoint-facts-study` 等历史推演                                                  | 实验仓库 `studies/`                                     | 明确历史基线和探针限制，不宣称已是当前事实模型                         |
| 当前 CP、稳定值、退出与选择契约回归                                                           | CAPiX 或与实现对应的必需集成检查                        | 先解决夹具归属，不因其引用实验目录而删除保证                           |
| 当前 API／不变量文档                                                                          | CAPiX                                                   | 相邻历史材料迁出后保留准确导航                                         |
| 历史实验报告                                                                                  | 与对应实验一起归档                                      | 保留来源提交、结论性质及必要数据口径                                   |

以上是归属设计，不是新包审批清单。尤其不能为了迁走 Conversation，提前要求实现通用持久化平台、通用对话门面或任意业务的客户端。

## 5. 三个需要先解开的实际接缝

### 5.1 服务与预设的接缝

ToolLoop 的主体是普通 Group 预设，但目前位于私有服务包内。`loop.ts`、`model.ts` 仍引用服务内恢复 codec、模型反馈读取和 pending 类型；`answer.ts` 则进一步接入材料和回答策略。

抽离时只移动具有共同契约的闭合能力。服务专用提示、材料选择和宿主归档不作为通用循环的默认依赖。不能在两个仓库各复制一份 ToolLoop，再靠人工同步。

### 5.2 观测 UI 与参考页面的接缝

保留 UI 能力不意味着框架必须托管完整对话产品。框架候选 UI 消费记录、协议值与明确端口；服务地址、路由、具体会话选择和产品页面由参考应用装配。

当前资产路径直接指向同仓 `apps/observer/dist`，见 Conversation 的 `src/web/start.ts`、`src/http/server.ts` 与 Observer 的 `src/http/server.ts`。迁出时改成宿主明确提供资产目录，或由新宿主解析自身构建目录，不能继续猜测相邻 CAPiX 的磁盘布局。源码定位能力同样需要显式宿主依据，不把构建机绝对路径当作跨仓契约。

### 5.3 宿主持久化与 CP 适配的接缝

两套 SQLite Store 除 CP 外还组合消息、记忆、View、交互、业务身份、恢复资格与归档计数。它们不是可以直接改名发布的通用适配器。

如果提取 SQLite CP 实现，范围应限于明确的连接／事务接入、CP 表结构及 Store 端口，保留拒绝旧格式、提交不确定性与恢复校验语义。业务表与跨实体原子性不随之统一。提取不是迁出历史研究的前置条件；迁出参考宿主时，则必须明确这部分实现及回归由哪个仓库维护。

## 6. 验证与文档如何交接

2026-11-10 后续决定：测试跟随包，CAPiX 独立自证，Lab 不作为框架测试仓或通过门槛。下面的归属与流程已据此收敛；包内测试目录和脚本的具体迁移见 [包内测试与框架自证设计](testing-organization-design.md)。初次迁移的依赖闭包清单仅记录文件交接，不代表最终断言责任。

盘点基线中，根 `test/` 有 22 个文件引用 `examples/`，这里按文本引用统计，不代表独立模块数。不能将这些测试和实验目录一并粗略迁出。

原 [CP 选择跨进程回归](../../capix-lab/test/checkpoint-selection-process.test.mjs) 使用长对话实验的测量 helper。框架的中断、冷恢复、选择身份和不重放效果现已提炼到 [Runtime 跨进程选择测试](../packages/runtime/test/checkpoint/selection-process.test.mjs)，不依赖该实验或 SQLite；宿主计量留在 Lab。

| 验证内容                                                | 主要归属                                                                |
| ------------------------------------------------------- | ----------------------------------------------------------------------- |
| 稳定输入／交付、接纳、取消退出、受保护故障              | CAPiX                                                                   |
| CP 准确回执、提交不确定、增量关系／选择、冷恢复拒绝反例 | CAPiX                                                                   |
| 公开入口、唯一错误与品牌身份、类型负例、安装产物        | CAPiX                                                                   |
| 当前确定性核心性能曲线及复杂度回归                      | CAPiX；大型全场景测量另归实验仓库                                       |
| SQLite 实现的事务、损坏、关闭和重启测试                 | 跟随实际适配器实现，不因迁库弱化                                        |
| 完整宿主的持久接纳、进程崩溃、恢复资格、未知外部效果    | Lab 的参考装配验证，不作为框架发布前置条件；框架责任另在 CAPiX 独立自证 |
| HTTP、页面、真实模型质量、多用户压力                    | 对应参考应用或实验仓库                                                  |
| 历史事实模型、旧格式对照、源码注入探针                  | 历史研究，不充当当前内核合格证明                                        |

原则是移动验证的组织位置，不减少现有承诺。核心测试如果依赖服务 Store，拆开内核不变量与具体 Store 行为：框架保证进入所属包独立测试，SQLite 故障证据随真实实现保留。不能用一个简单内存实现宣称证明 SQLite 原子性，也不能以 Lab 已覆盖为由省掉框架回归。

拆库前根 `test:unit` 还会编译 Observer UI 的测试产物；发布清单脚本检查 `services/*`、`client/*`、`apps/*` 下的私有 workspace。相关目录迁出时同步调整命令与边界清单，不保留空目录来绕过检查。

迁入 `packages/` 时，同步核对 workspace glob、锁文件 importer、TypeScript 引用、测试和脚本路径、各包 `repository.directory` 及文档链接。当前发布脚本按 `contracts/protocol/server` 枚举 17 包，迁移后必须继续明确发布清单，不能将整个 `packages/*` 自动公开。完成干净产物构建、公开出口及仓库外安装验收后，才删除旧路径。

文档迁移应维护一份“旧路径 → 新位置 → 适用提交／版本”的索引。当前契约保留关键决定的摘要及证据链接；完整历史报告与实验放在一起。文件所在仓库改变不赋予历史结论新的权威。

## 7. 跨仓依赖与发版验证

每个仓库各有一个 pnpm workspace 和锁文件。实验仓库日常使用精确的 `@weiliang0121/capix-*` 发布版本，参考服务之间可以使用其本仓 `workspace:*`。不把 CAPiX 源码路径、私有 `dist` 导入或长期软链当作正常运行方式，不共享根锁文件。

```text
CAPiX 变更
   │
   ├─ 当前契约、类型、故障与核心基准检查
   ├─ 打包及仓库外消费者验证
   └─ 维护者决定发布 → 本地 npm 发布

Lab 独立实验
   └─ 显式选择发布版本或同批候选 tarball
              └─ 参考装配／实验验证与报告
```

框架分发在本仓的临时消费者中验收，不依赖 Lab。Lab 可另外安装候选实验，记录 CAPiX 提交、包版本和摘要；需要替换的包及其内部依赖必须一致解析到同一批候选产物，不能根依赖用了新 tarball、传递依赖却混入旧 registry 包。候选实验不要求建立新的测试平台、先发占位版本或建立两仓测试依赖。

目前只有 17 个基础包公开，客户端及部分预设仍为私有。因此涉及这些能力的参考应用不能仅改成 `0.1.0` 依赖便宣称完成迁移。应先完成必要包的公开边界与分发；分发未准备好时延后相关宿主迁出，不复制实现或偷偷依赖相邻源码。

GitHub 保留 CI 与版本 PR，本地执行 npm 发布。拆库不自动改成远端发布、自动部署或真实模型测试。哪些外围包加入 fixed 组、哪些独立版本，等包实际形成后确定。

## 8. 历史、配置与数据边界

迁移记录包含来源路径、来源提交、目标路径、依赖版本、运行命令和交接检查结果。不为了目录整齐默认重写 CAPiX 历史；开源前另行确认哪些历史可以公开。将文件迁出当前树不会将其从可达历史中移除，仓库拆分也不等同于完成公开内容审查，见 [公开范围与历史](open-source-preparation.md#5-公开范围与历史单独验收)。

历史研究分为“可在固定版本复现”和“仅保留当时设计／证据”两类。涉及内部模块或构建产物注入的探针，不能声称能使用公开 npm 包直接复现；如需运行，应在显式准备的隔离实验副本中执行，不修改当前 CAPiX 工作区。已废弃行为不因搬到新仓库而恢复为兼容要求。

不自动搬运 `.env`、凭证、真实对话、SQLite 数据库、原始模型输出或 `.capix/` 全部产物。新仓库提供无秘密的配置示例；需保留的实验数据逐项检查，优先保存可重建的合成输入、测量摘要与操作说明。

实验和业务仓库可以消费、只读参考框架。发现缺口时记录复现，在 CAPiX 任务中明确决定变更；不能因实验任务直接回写 CAPiX 的源码、配置或协作约定。

## 9. 分阶段实施与验收

| 阶段                 | 工作                                                               | 完成依据                                                               |
| -------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 0. 固定迁移清单      | 确定新仓库名称、逐项归属、当前回归与历史实验的对应关系             | 每项有来源、目标、维护职责和验证方式；没有未说明的跨仓依赖             |
| 1. 迁出历史研究      | 先处理事实模型、恢复对照等历史实验及报告；收回当前回归需要的小夹具 | CAPiX 当前检查和产物检查仍成立；历史材料有明确基线，导航无断链         |
| 独立步骤：包目录统一 | 将已确定归属的包迁入 `packages/`，更新路径与显式发布清单           | 干净构建、依赖身份、公开出口与独立消费者验证通过；npm 名称不变         |
| 2. 收敛复用能力      | 分别处理 ToolLoop、内容预设、客户端和观测 UI 的真实出口            | 每项能通过公开边界独立消费；未完成者仍留原位，不强行整包迁走           |
| 3. 迁出参考宿主      | 迁移 CLI/Web、具体实体装配、业务存储与参考页面                     | 独立安装／构建／离线运行；HTTP、持久化、崩溃恢复和必要 UI 集成回归通过 |
| 4. 拆开验证流水线    | 框架保留契约与打包验收；实验仓库维护场景、规模与候选产物验证       | 从新检出可分别运行；不存在源码软链、共享锁文件或隐式配置来源           |

拆库第一轮建议只实施阶段 0、1，不在同一个变更里同时抽取 UI、通用 SQLite、工具预设和迁移所有服务。包目录统一可以在清单确定后单独推进，不要求等待所有候选包抽离。每一阶段交接成立后再移除原位置，避免长期维护两份实现。

开源准备可以先从公共包快速开始与贡献说明推进，无需等待整份拆库设计实施完毕；具体顺序见 [开源准备方案](open-source-preparation.md)。

迁移通过的判据不是两个仓库都能编译，而是：**框架可以独立验证自己的承诺，参考装配可以仅依赖明确的分发物运行，原有场景与故障证据仍有维护者和执行入口。**

## 10. 尚待确定的事项

- 新实验仓库的最终名称、位置及可见性。
- ToolLoop、内容组合、客户端和观测 UI 的具体包名与首轮公开出口。
- SQLite CP 适配器是否在宿主迁出前提取，还是先由参考宿主维护并保留对应集成验收。
- 历史研究哪些继续维护可复现入口，哪些只保留基线报告；核心基准与完整场景测量各保留哪些样本。

这些决定影响迁移路径，但不需要重新讨论 Scene／Group／Node、资源、调用、稳定事实或 CP 的语义。本设计也不引入调度、事务、权限平台或强制分段机制。
