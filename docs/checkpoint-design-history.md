# Callable Checkpoint 与执行恢复设计

状态：2026-10-25，有限内核与 Observer 默认内置能力声明已接入 CP；共同 Callable 调用与 Frame v5 已落地，支持声明边界上的宿主显式续接及同轮已处理失败的保存。第 0 节说明当前 API 与限制；其后保留设计推演，伪代码解释职责，不代替源码契约。自动恢复、旧提交交付与恢复 UI 尚未接入。

恢复的目标是：某次 Callable 工作中断后，依据已经保存的事实和声明的续接入口，继续推进该工作。重新建立 Invocation、Context 和资源访问是实现手段；不恢复原 Promise、闭包、调用栈，也不反序列化 Bound 结构。

当前验证覆盖材料准备、普通回答、文件处理与保存、澄清、记忆收尾和有限二次生成；维护预设有局部续接验证，不等于自定义维护已开放宿主恢复。**声明接入不代表任意时刻都能恢复：每次续接仍须取得准确子工作、已保存结果或实体凭据。**未知外部效果不重新执行，明确失败或取消不复活。

外部框架与早期候选路径保留在 [恢复机制研究](recovery.md)。运行、实体、交互和观测行为分别以 [运行边界](runtime-boundaries.md)、[持久化](persistence.md)、[外部交互](interactions.md)、[记录机制](recording.md) 为准。普通服务启动、提交和客户端接回的承诺保持不变。

## 0 当前实现与入口

内核 CP 保持可选；Observer 默认给新产生的调用安装保存端口。新建对话正常聊天即可产生真实 CP，已有对话之后的新调用采用相同规则，不给过去的任务补写 CP。启动不扫描或自动继续旧 QA，没有新增 HTTP 恢复接口或界面恢复按钮。

| 入口                                                                                   | 当前行为                                                                                                                                                    |
| -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CallableDefinition.checkpoint`                                                        | 声明稳定 `key/version`、输入/输出 codec、`points` 数组；每点独立声明 name、`state` codec、引用槽位及 `check(state,facts)` 和 `resume { deps, uses, run }`。 |
| `new Runner(scene, resources, interactions, { checkpoints: { store, observation? } })` | 注入同步保存端口和可选 CP 观察者，随后通过该 Runner 构建结构。未安装时 `work.checkpoint` 为 undefined，原流程不变。                                         |
| `work.checkpoint({ point, state, refs })`                                              | 当前运行或恢复工作阶段使用；固定输入、round、直接子关系与声明状态，检查后提交不可变 CP。保存失败属于结构故障。                                              |
| `runner.resume(contextId, options)`                                                    | 核对绑定归属、当前 head、版本和工作归属，重建本次活动与资源访问，进入声明点；遵守该 Runner 入口占用边界。                                                   |
| `work.children.resume(saved.ref)`                                                      | 开放子 CP 建立续接；固定成功交付提供结果视图。缺失或明确失败/取消拒绝，不退化为重新发起。                                                                   |
| `TranscriptResource.append.applyFixed({position,messages})`                            | 真实子接纳中由绑定取得父子身份；实体核对固定依据并返回原凭据，重复确认不再次追加。                                                                          |
| `MemoryResource.apply.applyFixed({position,changes})`                                  | 由资源端点取得当前 A 身份；整个批次与凭据同事务保存，重复确认不修改记忆或占用新顺序。                                                                       |

资源端点与 CP writer 保持 phase/round 访问窗口。直接子接纳通过私有异步范围关联固定操作，支持并行接纳；逸出已结束接纳的回调不能借用后续接纳身份。没有增加新的恢复编排器或通用 resume/run/accept 预设，声明共享自己的正常阶段函数，Invocation 仍处理父子运行机制。

作者恢复点使用 `checkpointPoint<Kind, Input, Output>()`，具名点通过对象注册和保存；跨进程再以所属契约和点名核验。resume 接收本阶段 Work、已解码业务 state 和准确引用槽位，正常和恢复均经相同的 child.run/accept 接缝。完整作者用法见 [定义作者契约](definition-author-contract.md)。

当前格式为 **Frame v5**：完整直接子关系与业务 state/refs 分开保存，包含已接纳 continuation、与该继续来源精确对应的前轮已处理接纳异常诊断，以及同轮子失败已经完成的 `handled` 接收事实。子声明由父 checkpoint key/version 与去重后的固定声明位置关联，不依赖 JS 身份、key 或同名契约。父接纳契约位置及编码值继续保存，owner 与子身份使用 kind: scene/group/node；成员位置属于固定父声明。新进程必须提供兼容声明；同版本任意改动业务实现不在可检测承诺内。

v1/v2/v3/v4 CP 明确拒绝恢复，不自动迁移或重发。格式升级不改写旧 image；历史消息、记忆和可选记录继续读取。第 1 节以后的历史推演保留当时伪代码，不作为当前作者 API。

父可在 `receptions` 登记 `reception(child, { check, encode, decode })`。进入 receiving 即固定本次契约；accepted 保存值经该 codec 编码，恢复先核对本父注册位置和准确子声明位置，再 decode/check。`facts.children.accepted(ref, contract)` 在恢复点 check 与 resume 中均取得解码后的 V，包含合法 undefined。它要求契约匹配，不能将旧 raw 接纳补成 typed 接纳。raw accept 保留既有纯数据保存行为。

普通接纳只同步检查实际 V，保留原引用；不会编解码来替换它。保存失败不撤回已接纳值或实体效果，也不授权再次接纳。receiving 的续接只能使用已固定的同一契约；需要重入实体写入时，仍由 `applyFixed` 等实体凭据保证，契约本身不提供幂等性。同一契约不可重复登记，注册顺序或含义变化需要提升父 CP version。

`work.children.invoke(child, input, { result: { failed }, reception })` 的失败分支成功返回后，子调用仍是 `returned: failed`，父关系另记 `reception: handled`。v5 保存这两个独立事实及接收后的值；恢复用 `work.children.facts.handled(ref, reception)` 读取经契约解码和检查的 V，不再次调用失败来源或 `failed` 回调。接收回调还在执行时不能保存该同轮失败，普通 raw 接收值仍需符合纯数据边界。`handled` 不代表子成功，也不使失败子调用重新可运行。

CP 保存或最终交付落盘失败不属于可由业务 `result.failed` 处理的失败。调用保留必要机制失败，父层不能用替代正文将它变成成功；磁盘故障与原业务已经产生的内容或外部效果分别记录，不承诺回滚。

若 Group 交付的是后代 Node 的失败，直接关系仍属于 Group，失败诊断保留真实 Node 的 `failure.contextId`。该诊断 ID 只解释来源，不能作为父层直接子引用；`refs`、接收契约和恢复目标仍按完整直接关系精确核对。闭包不会被持久化：业务必须注册明确的点和续接处理，并在保存点之后使用已保存事实推进。

### 0.1 内核事实与保存

实际契约见 [checkpoint/contract.ts](../server/runtime/src/checkpoint/contract.ts)、[definition/callable.ts](../server/runtime/src/definition/callable.ts)。CPF 与业务 state 分开，捕获全部直接子关系，不做正文裁剪。支持运行点、等待关系、成功返回/接纳关系和已经完成处理的子失败；第二轮还可保存**已由本层处理的前轮子声明异常**，作为只读历史诊断。它不重建活异常、不重新进入异常处理、不让失败子调用复活。同轮尚未处理或正在处理的失败、结构故障、取消和异常处理阶段仍不能当作开放恢复点。

返回关系与最终交付保存真实子 round、phase、currentInput，不能从较早 CP 或父 round 推测。固定交付视图不伪造原 execute 中间结果或未保存的后代。GenerateAnswer 的二次生成核对原拒绝码、诊断与真实失败关系，恢复不重置次数或产生第三次生成。

内核提供 `MemoryCheckpointStore`，服务提供 `SqliteCheckpointStore`。SQLite CP/head 独立事务复用宿主 WAL/FULL 独占连接，与内容实体和模型交互的提交边界分开。每个 image、delivery、对话构造依据分别限制 8 MiB；拒绝 getter、函数、活实体、循环和超深结构。head 按 revision 比较更新，终态不可再推进；宿主复用同一端口并独占恢复入口，不承诺跨进程租约或多写者接管。声明版本不兼容明确拒绝，不自动迁移旧 CP。

### 0.2 Observer 声明覆盖

| 范围                                           | 保存与续接位置                                                         | 不允许的替代                                        |
| ---------------------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------- |
| Scene / Task                                   | Scene 等待准确 Task；Task 保存准备材料、决策、能力调用、接纳和收尾进度 | 不重复 R 的输入追加，不根据最近调用或文本猜身份     |
| 理解请求 / 决策 / 显式选择预设                 | 模型与接纳等待、已接纳结果；E 保留步数、候选反馈和已选路径             | 不重新理解已固定决定，不重置预算                    |
| 活跃材料准备 / 维护预设                        | 准备等待与固定结果；维护等待（子 O 有 CP 时）、accepted、completed     | 完成后复用原材料；无固定索引凭据时不猜测已落实      |
| 文件预检 / 文档处理                            | 元数据检查、读文件与生成子调用等待，已取得结果                         | 已保存读取沿用原正文；没有读取结果不能假设文件没变  |
| 回答生成                                       | 组装、准备请求、请求模型、接纳等待与结果；第一/第二工作轮分别核对      | 旧第一轮拒绝仍是拒绝，不因恢复增加模型调用额度      |
| 模型请求 / 发起 / 跟随                         | 固定 Interaction 身份、请求与用途，读取原反馈                          | 无反馈、交互缺失或请求不一致时不重发                |
| 保存结果 / 创建文件                            | 保存等待、固定创建前的 `prepared` 点和创建凭据                         | `pending` 表示结果未知，不从文件存在/内容相等猜完成 |
| 提取 / 落实记忆                                | 准备、模型、接纳、批次落实等待；ApplyMemory 的 `prepared` 点           | 不重新提取已固定批次，不重复创建或更新记忆          |
| 组装上下文 / 准备与接纳模型结果 / 文件读取检查 | 保存纯数据成功结果，供本层完成和父层接纳                               | 子尚无 CP 或最终交付时不自动重新执行                |

E 已移除原先覆盖决策、文件和记忆的 `continuationBarrier`。各等待点核对准确声明、key、固定子输入与已接纳进度；已接纳点核对具体阶段。`answerAccepted` 不能改名为 `completed` 跳过记忆收尾。澄清/不支持结论也使用固定消息追加，恢复不会多发一条澄清。

FunctionDecision 可保存纯数据候选，候选是否可执行仍由 E 接纳逻辑判断，CP 不抢占原业务审查。Observer 宿主目前仍拒绝恢复注入的自定义决策函数，因为没有固定该函数实现版本的契约；默认决策链可恢复。注入自定义维护也暂不允许宿主恢复，即使策略 O 自带 CP；当前没有完整版本化其宿主配置与实现的恢复契约。

当前 Observer 的 Scene/Task checkpoint 契约为 **observer.conversation.scene version 4 / observer.conversation.task version 6**；Frame 为 v5，声明版本与格式版本分开。旧 CP 不自动迁移。默认服务保持单任务的恢复登记，不因 Group 可嵌套就承诺宿主支持任意多任务恢复。

准备 O 的 completed、E 的 preparationAccepted 及已返回交付保存同一份固定材料。恢复核对材料来源及当时值，不读取当前活跃索引替换它。R 从已保存的 executionWaiting 续接准确 E，不重复 append；正式输入已写入但尚无首个 R CP 的窗口仍不承诺恢复。

### 0.3 实体落实与固定依据

消息依据/凭据与消息同事务提交。E 接纳后的 CP 保存对应凭据，恢复向 Transcript 核实；CP 自身不能证明实体已经写入。

记忆按固定 A 身份与效果位置保存完整变更批次、实际变动的 memoryIds、起止 sequence。整批预检查并提交，无变化 update 不占顺序；空批次也可确认。服务保存初始记忆快照，恢复时只允许原 E 子树中、与 ApplyMemory 原输入一致的连续固定批次；同时纯数据核对这些批次之后的当前正文，避免只凭序号认定内容一致。准备材料及其下游仍使用当时的消息/记忆值，写入口访问真实实体。

文件创建由 WorkspaceFiles 的独立日志持有固定操作、路径、正文的 bytes/digest 与凭据；待创建正文由 A 的 CP 输入保存。先登记 pending，再发布并同步文件与目录，最后保存成功凭据。中断后，成功凭据直接确认历史结果，不重新创建；没有日志时可执行原 `prepared` 操作；只有 pending 时明确 `FILE_CREATION_UNCONFIRMED`。文件系统与 SQLite 不是同一事务，这个未知窗口仍保留，不提供任意外部效果恰好一次保证。历史凭据不保证文件此刻仍存在。

`ConversationCheckpointRun` 保存对话与 R/E 身份、输入位置、固定模型配置、声明配置、原文范围/指纹、记忆身份/顺序/当时正文。核对本轮固定原文前缀与正式输入，并验证已准备材料属于原范围和允许的记忆版本；原文定位不是模型材料集合。恢复允许本 E 已确认的固定助手追加与上述记忆批次，拒绝后续新 QA、分段变化或其他写入。复用 E 最终交付不重新建立 E 工作。文件工作区根路径及读写限额通过宿主指纹核对；改变 files、工作区、限额或 maxDecisionSteps 均拒绝。指纹不是文件内容快照，当前访问仍遵守原文件端点的限制。

活跃索引的维护目前没有 `applyFixed` 操作凭据。accepted 点在索引落实前保存决定，恢复时仍要求原复合依据成立；若索引已经改变，即使目标成员碰巧相同，也拒绝把它当作原操作确认。completed 点保存落实后的不可变材料，续接直接返回该值，不再应用索引。不把源内容同事务持久化与索引维护的 CP 原子性混为一谈。

### 0.4 宿主入口与观测

```ts
const environment = conversations.open(conversationId);
const runs = environment.checkpointRuns.list(conversationId);
const rootId = runs[0].rootContextId;
const head = environment.checkpoints.read(rootId);
// 宿主确认旧活动已停止，并明确选择有可用依据的未终结工作。
const unsubscribe = environment.checkpointObservation.subscribe(rootId, (snapshot) => {
  // 有界元数据：当前活动、阶段、恢复关系，不含 frame 或业务 IO。
});
const answer = await conversations.recover(conversationId, rootId);
const observed = environment.checkpointObservation.query(rootId);
unsubscribe();
```

取消不能充当中断：明确失败、取消和完成的顶层工作均不复活。恢复入口不接收旧 Submission 进展通道，不伪造旧 started/input/answer/completed；新实体变化仍能经原同步出口读取。客户端接回与服务执行恢复独立，旧 submissionId 不因 CP 存在就变得可跟随。

内核独立 `CheckpointFact` 出口带稳定 owner 与本次 activityId，区分正常和 recovering 活动。`installed` 表示历史关系基线，`child-restored` 区分续接与固定交付复用；历史安装不重演 started/returned/accepted。恢复调用事实不写原 Recorder/Invocation changes，实体新变化经自身出口发布，旧凭据确认不重复发布。内部事实可能含 IO，不能直接作为公开协议。

Observer 默认绑定 `CheckpointObservation` 元数据载体：按真实祖先归属查询/订阅，每次最多保留 1024 事件、256 活动，每个安装基线最多 64 个子关系，明确标记裁剪；微任务交付、消费者故障隔离。当前只保留本进程数据，未接 HTTP 或可视化页面，不承诺跨进程观测日志。宿主仍可额外注入原始观察者。CP 保存与观察失败分开：默认 isolate，可显式 propagate；最终交付提交后的通知失败不能改写已固定交付。

### 0.5 验证与剩余范围

`test/checkpoint/coverage.test.mjs` 使用真实 ObserverConversations、SQLite、WorkspaceFiles 与声明链，只有 Provider 为 mock。子进程在材料准备、理解、决策、预检、读取、模型反馈、消息追加、文件创建、记忆提交与父层接纳等位置退出，新进程从宿主恢复。断言模型次数、输入/回答数量、文件凭据、记忆身份与顺序，以及恢复活动归属；澄清和第二轮生成另有覆盖。`fixedEffects`、`fixedAppend`、内核历史关系与宿主内容检查测试覆盖事务失败、重复消费、未知窗口及数据冲突。

`test/active-content.test.mjs` 覆盖索引冲突、不可变捕获、源写入及 SQLite v6 事务/恢复；`test/active-context-operations.test.mjs` 覆盖普通 O 策略、等待/接纳/完成点的局部续接与索引歧义拒绝。`test/integration/active-context.test.mjs` 覆盖维护先于捕获、默认完整材料和不隐式裁剪；跨进程覆盖准备结果、父层接纳以及文件/记忆后续链路。均使用测试 Provider，不请求真实模型。

剩余边界是明确限制：子层第一次 CP/交付之前的未知窗口、未保存的外部反馈、文件发布后仅有 pending、未版本化自定义决策/维护、活跃索引落实后尚无 completed CP 的歧义窗口、旧提交交付和自动恢复。这些不以“已有 CP”自动获得支持。正常聊天可验证保存与观测接入；恢复正确性以受控中断测试验证，不能只看普通对话是否成功。

## 1 已确认的心智模型

### 1.1 恢复的是工作范围与进度

REOA 确定工作归属，声明确定工作内容，绑定兑现可用结构和资源。Invocation 处理调用过程，Context 承载本次工作的输入与状态。Checkpoint 从这些来源取得必要事实，并保存声明明确解释的业务进度。

```text
声明与绑定                         一次工作
RuntimeDefinition   → BoundRuntime   → R Invocation + RuntimeContext
ExecutionDefinition → BoundExecution → E Invocation + ExecutionContext
OperationDefinition → BoundOperation → O Invocation + OperationContext
AttemptDefinition   → BoundAttempt   → A Invocation + AttemptContext
                                          │
                                  按声明的边界协调
                                          │
                                      Checkpoint
                                          │
                                不可变的 cp(1)、cp(2)…
```

Checkpoint 是能力；cp(i) 是该能力产生的数据。二者都不构成新的 REOA 层次，也不成为业务实体的所有者。各层可以有 CP，也可以没有；不能因为父层可恢复，就声称任意子层都可恢复。

一个 CP 的范围属于一笔具体工作。不同 CP 可以保存该范围的不同子集，不要求后一个包含前一个的全部正文；但每个可用入口必须取得足够的恢复依据。省略的内容必须不再需要、能由固定事实纯计算得到，或有明确且仍然有效的读取来源，不能依赖“应该还在内存里”。

### 1.2 四个必须能回答的问题

1. **归属**：这是谁的进度，和哪个直接父子关系有关？
2. **事实**：哪些事情已经成立，由哪个调用、关系或实体确认？
3. **位置**：中断后还差哪个动作，允许从哪个入口继续？
4. **约束**：哪些输入和决定必须沿用，哪些条件需要重新检查，哪些操作不能再做？

新增实体时检查它如何确认自身已落实的操作；新增中断点时检查续接依据；新增父子推进方式时检查返回、接纳与后续启动之间的交接。不能用一个通用 `resume()` 掩盖这些问题。

### 1.3 恢复与相邻机制

| 机制             | 本方案中的含义                                     |
| ---------------- | -------------------------------------------------- |
| 客户端接回       | 重新消费服务反馈，不重新运行业务；已有实现保持独立 |
| 内容恢复         | 恢复 Transcript、Memories 等权威实体，不重演原变化 |
| Interaction 读取 | 消费原请求的已保存反馈，不再次发送请求             |
| 工作恢复         | 安装原工作事实，从声明入口继续本层推进             |
| 本地 continue    | 声明允许的下一业务轮，仍受 maxRounds 等限制        |
| 再次发起业务     | 新工作及新效果身份，不能伪装成恢复                 |

恢复不增加本地 round，不重置决策步数、重生成次数等预算。明确失败或取消的工作不能因为存在一个较早的 CP 就自动复活。观测记录不完整，也不能作为“原工作被中断、允许恢复”的充分证据。

## 2 职责与协作边界

| 组成         | 负责                                                           | 不负责                                 |
| ------------ | -------------------------------------------------------------- | -------------------------------------- |
| REOA 声明    | 可恢复位置、状态契约、续接内容、所需资源和子能力               | 修改 Context 内部阶段、伪造父子事实    |
| 绑定与构造   | 解析兼容声明、核对直接关系、供应受限资源、接入保存与观测端口   | 决定下一业务能力、执行业务编排         |
| Bound 结构   | 持有可复用定义与接线，提供建立活动的能力                       | 保存某一次工作的 CP 或局部变量         |
| Invocation   | 协调合法捕获点、调用阶段、父子返回与接纳、实际续接             | 解释回答、计划、记忆内容等业务状态     |
| Context      | 保持本层输入、进度和终态不变量，提供受控事实读取与安装         | 持有数据库、观测载体或访问祖先 Context |
| Checkpoint   | 组合固定事实与声明状态、校验、编码并提交                       | 把任意运行对象变成可恢复对象           |
| 独立实体     | 保持权威内容，确认并落实自身操作                               | 替父调用宣布接纳完成                   |
| 宿主保存实现 | 在各自提交边界原子保存 CP 与进度、实体变更与凭据，提供一致读取 | 解释业务恢复入口、假定跨实体原子性     |
| 观测         | 解释 CP 与恢复过程中真实发生的事实                             | 成为恢复必须依赖的数据源               |

Invocation 主导协作，但不要求 Context 感知 Checkpoint 类。绑定向 Checkpoint 提供窄的事实读取能力；捕获时固定内容，保存的 CP 不携带活 getter、Context、Invocation、资源端点或记录句柄。

普通 execute 内部的业务位置只有声明知道。内核可以在固定调用边界捕获通用事实，却不能自行猜出“已完成选史”“回答待落实”等业务阶段。声明显式提供位置与状态，Invocation 校验捕获是否合法。

## 3 父子接纳与实体落实

### 3.1 三种事实分别成立

```text
子层完成自身处理并返回
          ↓
父层开始接纳 receiving
          ↓
执行声明的接收逻辑
          ↓
实体落实并产生凭据（如果本次接纳包含实体变化）
          ↓
构造本层新的业务进度
          ↓
父层接纳完成 accepted
          ↓
保存能够解释接纳结果与新进度的父 CP
          ↓
后续选择、建立、调用和接纳子层
```

这是当前回答追加场景的顺序，不是要求所有实体变化都移进父层接纳。记忆落实发生在具体 A 内部时，仍由 A 的工作和对应实体负责；适用的是相同的事实确认原则。

子层成功返回不证明父层接纳；实体已经提交不证明父层接纳；父层接纳也不证明该状态已经保存为可恢复进度。应分别表达，不能用一个 `done` 合并。

另需区分两个 receive：本层 Invocation 对自身 execute 返回的接收，与本层作为父调用对直接子层结果的接纳。E 在自己的 execute 阶段里接纳 O 时，父子关系可以是 receiving，但 E Context 的阶段仍为 execute。

### 3.2 固定子层关系后再启动

子层 key 是组合位置，不是唯一工作身份；当前 E 可以多次使用 `decision` 或 `generation`。父 CP 需要关联准确的子工作身份、父 round、同级顺序、声明位置和固定输入。

对承诺恢复的交接，建议采用以下顺序：

```text
父层已接纳的进度
  → 声明选择子能力并构造输入
  → 构造子工作身份与直接关系
  → 保存父层等待该子工作的依据
  → 启动子工作
```

“等待依据已保存”不等于子工作尚未启动。恢复时要查询该子工作的正式进度或结果；缺少子 CP 可能是尚未执行，也可能是执行后未保存，不能自动重复。只有声明明确允许安全重新计算，才可重新进入相应内容。

父层已保存 accepted 进度时，不再恢复该关系上较旧的待返回子 CP。父层尚未接纳时，子层已有完整返回也只能进入父层接纳，不能跳过它。父子一致性由精确身份和关系核验，不按时间戳选择“最近的一批 CP”。

如果子工作已经终结且有可信的最终成功交付，父层读取该结果即可，不再启动子 Invocation。子工作终结只封闭它的执行恢复资格，不取消父层消费原结果的资格。只有未终结且存在合法 CP 的子工作，才需要建立活动继续运行。

## 4 身份和顺序

初版沿用原 Context 身份标识原逻辑工作，恢复时建立新的活动对象；另用本次处理身份区分观测来源。Context 已提供构造期受控安装，业务 ContextView 不暴露该修改入口。

| 身份           | 稳定范围                                           |
| -------------- | -------------------------------------------------- |
| Context 身份   | 同一笔 REOA 工作；恢复保持归属                     |
| 本次处理身份   | 一次原始执行或一次续接活动；重新建立时更新         |
| CP 身份        | 一份不可变恢复数据                                 |
| 声明身份与版本 | 能解释输入、状态、关系和续接内容的契约             |
| 子关系         | 精确父子工作、父 round、同级顺序；key 辅助解释位置 |
| 实体操作身份   | 同一关系、同一声明效果位置；恢复不得重新生成       |
| 记录身份       | 某次观测载体中的结果，不用于代替以上身份           |

不为稳定 Context 身份再创建同义 workId。当前本次处理身份使用 `activityId`。现有结构实例 ID、resource supplyId 都不能替代跨进程契约定位。

顺序仍分域：调用本地顺序、实体 revision、CP 保存版本和交付游标分别管理。观测序号按本次处理来源解释，不允许同一个来源重置序号；旧进程的 monotonicTime 不能与新进程直接相减。跨次处理通过关联解释先后，不建立全局统一时钟。

逻辑工作内的同级子位置需要持续单调推进。裁剪已完成子正文后，仍须保留下一位置依据，不能按恢复后 children 数量重新编号。这与新活动来源的观测序号是两种顺序。

## 5 CP 数据契约

### 5.1 数据分为内核事实和声明状态

```ts
// 方案伪代码，只描述首批支持 execute 内显式位置的保存格式。
interface CheckpointImage<Input, State> {
  readonly id: string;
  readonly formatVersion: 1;
  readonly contract: {
    readonly definition: string;
    readonly version: number;
    readonly point: string;
  };
  readonly frame: InvocationCheckpointFrame<Input>;
  readonly state: State;
}

interface InvocationCheckpointFrame<Input> {
  readonly owner: {
    readonly contextId: string;
    readonly level: 'runtime' | 'execution' | 'operation' | 'attempt';
    readonly parentContextId?: string;
  };
  readonly position: {
    readonly round: number;
    readonly phase: 'execute';
  };
  readonly input: Input;
  // 缺省明确表示与 input 相同，不是从当前环境重新取值。
  readonly currentInput?: Input;
  readonly nextChildOrder: number;
  readonly children: readonly ChildCheckpointFacts[];
}

interface ChildCheckpointFacts {
  readonly contextId: string;
  readonly definition: { readonly key: string; readonly version: number };
  readonly parentRound: number;
  readonly order: number;
  readonly key?: string;
  readonly input: JsonValue;
  readonly state:
    | { readonly kind: 'waiting'; readonly checkpointId?: string }
    | {
        readonly kind: 'returned';
        readonly output: JsonValue;
        readonly reception: { readonly kind: 'pending' } | { readonly kind: 'receiving' } | { readonly kind: 'accepted'; readonly output: JsonValue };
      };
}
```

`JsonValue` 表示经明确 codec 接纳的纯数据；不是给未知对象直接 JSON.stringify 的许可。示例只覆盖成功返回的子关系。需要保存失败结果、异常处理现场或其他阶段时，必须补充对应契约；不能把它们强行转成成功、pending 或普通错误字符串。

CPF 表达本层的结构事实，不塞入业务 point 的含义。`state` 则由 point 的 Schema 解释，例如固定模型返回、等待生成的 E 进度或待落实的回答。父 CP 不嵌套完整子树，已完成且后续不再依赖的子工作可以不带正文；必要子事实必须覆盖恢复后会执行的查询和接纳逻辑。

以上是最小语义形状，不要求存储重复正文。接纳结果和业务新状态若是同一值，可以由 codec 一次编码并保留明确对应；不能分开异步保存后假称一致。数据格式还需要限定深度、条目数和总字节数，超限明确失败，不无限复制父子结果。

### 5.2 哪些数据固定，哪些重新绑定

| 数据                                   | 恢复要求                                             |
| -------------------------------------- | ---------------------------------------------------- |
| 原输入、当前 round、已接纳决策         | 保持原值，不重新向模型询问已接受的选择               |
| 选择结果、当前业务状态、决策步数       | 声明保存，或从明确固定结果纯计算得到                 |
| 原文范围、记忆快照、当时配置           | 按原含义固定；可用不可变版本读取时才使用引用         |
| 模型返回、文件读取正文                 | 后续仍需要则保存，或引用可验证且仍保留的权威数据     |
| 实体操作凭据                           | 保存操作身份、目标及原结果定位，另向实体确认         |
| Signal、访问端点、Provider、DB、观察者 | 重新绑定，不序列化                                   |
| 密钥                                   | 从当前服务环境取得，不进入 CP                        |
| 当前占用、目标实体可用性、资源访问范围 | 恢复时复核；复核不是把原输入换成当前数据             |
| 流式预览前缀与 UI 游标                 | 不属于首批恢复内容；正式结果可以恢复，预览不保证延续 |

UID、范围和 hash 只能帮助定位或校验，不能凭空还原已丢失正文。可变记忆仅存当前 memoryId 不能证明取回的是当时内容。首批建议直接保存有限必要正文，后续有容量需求再增加受控不可变内容存储，不先建通用证据系统。

### 5.3 真实引用与解码后的关联

当前模型再次生成的资格检查会读取前一模型子调用的输入，检查直接归属、先后、返回与接纳状态，并比较拒绝输入、异常事实和模型输出的对象引用。参见 [regeneration.ts](../services/observer/src/conversation/model/regeneration.ts)。

恢复不能把这套检查降成“JSON 相同就算同一次结果”。首批链路在 RequestModel 的成功返回位置续接：该输出在恢复活动中只解码一次，通过真实的新返回和接纳传给后续校验 A，维持本次活动里的引用一致性。原请求仍需保存，不能只保存 content。

已经发生拒绝、进入第二业务轮或需要载入旧异常对象的 CP 暂不支持。将来支持时，需要按声明版本解析异常契约，恢复可信的直接结果对应，并保持已有资格和次数检查；不为恢复便利把诊断 DTO 伪装成原异常实例，也不恢复全部对象图。

## 6 声明与绑定的建议形式

Checkpoint 作为可选能力按相同的声明与绑定模型接入。声明只定义有意义的恢复点；没有安装保存能力时，原运行路径继续成立，不为了观测额外生成 CP。

```ts
// 是建议形状，不是当前 OperationDefinition 的属性。
readonly checkpoint = {
  version: 1,
  input: modelRequestCodec,
  points: {
    'feedback-accepted': {
      state: modelFeedbackCodec,
      check: (frame, state) => checkModelFeedbackPosition(frame, state),
      resume: {
        requires: {},
        uses: [],
        execute: (_context, _invocation, _children, state) => state.output,
      },
    },
  },
};

// RequestModel O 已经接纳 start/follow 的完整返回之后。
const output = await receiveModelOutput();
await invocation.checkpoint?.save('feedback-accepted', { output });
return output;
```

`receiveModelOutput()` 仅概括当前 start/follow 与接纳逻辑，不是新公共 helper。该 point 只证明原始模型返回已接纳，仍需父层的 finishReason、JSON、Schema 等业务校验。

绑定负责把具体声明、内核事实读取、保存端口、当前资源供给和可选观测接起来。恢复点可以声明比原 execute 更小的资源范围；上例不需要模型发送资源。续接后的正常接纳和收尾若仍需资源，必须另外纳入绑定检查，不能只检查 resume.execute。

声明定位需要固定实际变体与影响语义的装配配置；同名 RequestModel 用于不同目的，或同一生成声明的构造选项不同，不能只用 name 相等判定兼容。首批由服务显式映射已知契约与装配版本，不建立动态注册平台，不把密钥纳入版本数据。

```text
Checkpoint 声明
      + 内核本层事实读取
      + 宿主保存端口
      + 可选观测
              ↓ 绑定
      本次 Invocation 的 Checkpoint 能力

CP + 兼容声明 + 当前供给
              ↓ 核验与构造
      新 Context / Invocation 活动
              ↓ 明确的恢复入口
      续接返回 → 正常本层接收与结束 → 父层接纳
```

save 在可说明的一致边界固定 frame 和 state，再等待持久提交；先核对所属活动有效、没有已归属故障、point 与当前位置相容。不得跨 await 读取一半旧、一半新的局部状态。初版只处理结构化的单一路径，不支持任意后台子调用同时修改捕获范围；存在未纳入交接的活动子工作时拒绝宣称可恢复。

保存能力启用后，要求成功的 save 失败属于运行依赖失败，不静默退化为“仍有恢复保证”。观测是否安装不影响这项承诺。捕获函数与业务 state 的 Schema 都不负责自行写记录。

## 7 保存与恢复入口

### 7.1 保存职责

内核定义窄保存端口，SQLite 实现继续留在 Observer 的 persistence 中。可以复用现有 SQLite 依赖与单进程写入方式，不在 runtime 或 protocol 中引入数据库。

存储最少需要支持三种能力，具体表名不提前固定：

- 不可变 CP 正文及格式、声明版本；不能覆盖同 ID 的另一份内容。
- 每笔工作当前可用进度的版本、最终交付状态及必要的固定交付结果，保存新 CP 时按预期版本推进，拒绝旧 CP 覆盖新进度。
- 实体固定操作及凭据，由实体自己的提交事务保存。

不可变 CP 与该工作进度指向的更新需要在一次本地事务内完成。完成、明确失败或取消要封闭原工作的恢复资格；终态是运行事实，不从 Recorder 的 finished 推断。

这里的最终交付状态不能只取 Context.status。当前 Context.complete 之后，输出收尾或严格观测仍可能失败；Invocation 对父关系确定的 succeeded/failed 才表达实际交付。终结保存需要保留这个差别，并把可供父层读取的最终结果与其交付状态协调保存。execute 内 CP 的 output 尚未经过剩余本层接收与收尾，不能直接冒充最终交付。若只有“工作已完成”而没有可信交付依据，该窗口明确不可自动继续。

若持久终态或取消意图未保存就发生崩溃，旧的 open CP 本身不足以证明仍应继续。首批只由宿主选择已知的受控中断，不扫描全部 open 自动恢复。对外承诺自动恢复之前，必须把准入、推进权、终态与取消的持久处理一并闭合。

### 7.2 恢复处理顺序

```text
宿主选择一笔允许续接的工作
  → 取得独占推进资格，确认原处理者已退出
  → 读取权威当前进度及 CP，区分待续接工作与已终结结果，排除过期位置
  → 校验格式、声明版本、直接关系、必要实体和效果依据
  → 重建兼容 Bound 结构与受限资源访问
  → 从父到子建立所需 Context / Invocation 活动
  → 静默安装历史事实，发布恢复基线
  → 从选定 point 进入实际处理
  → 子层交付、父层接纳、实体确认或落实、保存新进度
  → 正常结束或明确失败，释放占用
```

验证失败不进入业务、不请求模型、不执行新写入。恢复构造需要与普通 create 区分：当前 Invocation 构造会 attach 并发布新关系，cycle 从第一轮进入 execute；不能直接调用这两个旧入口再想办法跳过前面代码。

直接子工作分三种处理：未终结且有合法 CP，建立活动续接；已经成功交付，安装其固定返回事实，只继续父层尚未完成的接纳；明确失败、取消或交付依据不足，按对应契约处理，首批拒绝自动继续。顶层已经终结则只提供原结果读取，不重新执行。既有交付的安装属于恢复基线，不再发布一次子 returned。

Context 的安装必须通过内核检查一次完成，业务没有任意设置 ID、round、成功状态的能力。受限资源重新绑定到当前活动与当前祖先，旧端点不复活。安装已知子事实不意味着必须为全部历史子工作创建可 run 的 Invocation。

初版不实现租约、分布式接管或 fencing。现有 R 占用只能约束当前进程的结构；宿主必须保证旧进程或旧活动不再推进。不能用“新进程启动了”代替这个前提。

### 7.3 CP 的引用和保留

按工作精确查询当前进度，父 CP 指向子工作时核对归属和版本兼容，不按数据库最大时间戳拼接。必要数据缺失或关系冲突时停止恢复，不自动回退到更早且可能重做效果的 CP。

初版保留所有仍被可恢复工作引用的 CP、返回正文和效果凭据，不做自动清理。后续清理必须先明确恢复期限与引用可达性；不能只保留每层最后一条，删除父 CP 仍然依赖的内容。

## 8 实体固定操作与凭据

### 8.1 Transcript 的有限契约

首次只验证一次父层接纳里的一个助手消息追加。绑定根据真实父子关系和声明的效果位置形成操作身份，业务不随意填写 contextId 或挑选历史凭据。

```ts
interface FixedAppend {
  readonly contract: { readonly key: 'transcript.append'; readonly version: 1 };
  readonly operation: {
    readonly parentContextId: string;
    readonly childContextId: string;
    readonly position: 'answer-message';
  };
  readonly transcriptId: string;
  readonly messages: readonly Message[];
}

interface AppendReceipt {
  readonly transcriptId: string;
  readonly start: number;
  readonly count: number;
  readonly revision: number;
}
```

这只是本例的操作定位结构，不增加通用 Acceptance 实体。效果契约的标识与版本由绑定固定，并与目标和内容一起保存为操作依据；恢复必须沿用原含义。若一个接纳包含两个写操作，需要两个明确 position；循环中的重复效果还要有固定的发生位置。不能用一次父接纳的身份覆盖所有副作用。

实体侧满足以下规则：

1. 首次操作：整批校验，在同一实体持久事务中保存消息变更、固定请求依据和凭据，然后安装内存状态并发布变化。
2. 同身份、同目标、同内容：返回原凭据，不追加、不占新 revision、不再次发布 messages-appended。
3. 同身份但目标、内容或契约含义不同：明确冲突，不覆盖旧结果。
4. 无法可靠读取原操作状态：结果未知或不可用，不把“查询失败”当作“从未执行”。

同一目标和内容不能代替操作身份；两次独立工作可以合理地追加相同文本。对比固定请求需要明确编码与比较规则，不能依赖不稳定序列化或仅比较长度。

现有 [Transcript.appendFrom](../server/runtime/src/transcript/transcript.ts) 已有先持久提交、后更新内存和通知的顺序，但没有操作身份和原凭据查询。现有 [资源端点](../server/runtime/src/transcript/resource.ts) 从当前长度计算追加索引；复用操作时必须返回原凭据定位，不能再使用当前长度。

### 8.2 实体提交与父 CP 是两个提交

```text
父 CP：固定子返回、接纳前进度和效果位置
                         ↓
Transcript：消息变更 + 原操作依据 + 凭据，同事务提交
                         ↓
父层：由原凭据构造接纳后的进度
                         ↓
父 CP：接纳结果 + 本层新进度，协调保存
```

这里不宣称跨实体原子事务。实体已经提交而父 CP 未提交的窗口，由原操作身份和实体凭据衔接。父 CP 中的接纳关系与业务状态必须表达同一个边界；当前能力 helper 的 accepted 输出本来就是新 ExecutionProgress，可以作为一致捕获的来源，不必建立第二份并行进度管理器。

```ts
// 初次与恢复都使用绑定签发的同一位置；输入来自固定返回。
const receipt = messages.applyFixed({ position: 'answer-message', messages: [{ role: 'assistant', content: answer.content }] });
const nextState = finishAnswerReception({ previousState, answer, receipt });
return nextState;
// Invocation 在接纳实际完成后协调捕获 accepted 关系与 nextState。
```

示例资源端点隐藏了完整 operation 身份，但不是使用任意可变的全局“当前接纳”。绑定必须将它限定到这次直接关系与接纳窗口，沿用既有活动校验，防止保存写端点后跨调用使用。

### 8.3 不能从抛错反推效果

实体提交后，内存安装、通知或父层处理仍可能失败。原操作抛错不证明未提交；原凭据存在也不能清除调用已归属的错误或自动把父关系改为 accepted。

本次恢复讨论针对工作中断。若原工作已经明确失败，重做剩余接纳需要另外的业务授权和恢复契约，不能借旧 CP 绕过异常与错误机制。

文件、HTTP 和数据库外的副作用没有自动取得 Transcript 的保证。文件存在、相同文本或模型声称成功都不足以证明原操作已经完成；没有可确认的能力契约时保留 unknown，不自动重发。

## 9 一条完整链路的推演

以当前普通回答路径为依据，忽略文件分支。身份为示例，不是固定配置。

```text
r1 R：等待 e1
└─ e1 E：已接纳选史与决策，等待 g1
   └─ g1 生成回答 O：已固定请求，等待 m1
      └─ m1 请求模型 O
         ├─ a1 发起交互 A：已经返回
         ├─ a2 读取交互 A：按需发生并返回
         └─ cp(m1)：已接纳完整模型返回

                 中断

恢复 r1 / e1 / g1 的必要父范围和等待关系
  → m1 从 cp(m1) 返回已保存 ModelOutput
  → g1 接纳 m1 的返回
  → g1 建立新的校验 A，执行正常结果检查
  → g1 返回 GenerationOutput
  → e1 保存回答接纳前位置
  → e1 通过固定操作追加助手消息
  → e1 完成接纳并保存新进度
```

| 范围       | 必要的固定依据                                             | 续接动作                                        |
| ---------- | ---------------------------------------------------------- | ----------------------------------------------- |
| R          | E 的固定身份、输入关系与接纳位置                           | 等待或接纳原 E，不重新进入 E 入口               |
| E          | 已接纳选择、记忆快照、决策位置及预算、业务进度、目标子关系 | 接纳 g1，确认消息落实，继续本层内容             |
| 生成 O     | GenerationInput、原请求、当前 round、等待 m1 的关系        | 接纳 m1，再运行校验 A；不重新组装历史或请求模型 |
| 请求模型 O | ModelRequest、ModelOutput、所属关系                        | 直接返回固定结果，经过正常本层收尾              |
| 已完成 A   | 后续需要的交付事实；无须保留活动实例                       | 不重新执行                                      |
| Transcript | 消息、固定操作依据与原凭据                                 | 确认既有追加，或首次落实                        |

请求模型 O 的 CP 可以直接保存必要输出，也可在未来使用严格核验的 Interaction 引用。首次建议直接保存有限输出来验证恢复链；没有已保存输出的交互位置不在这个闭环的保证内，不重发模型。

图中 m1 尚未完成最终交付，所以从 CP 继续本层收尾。若实际中断时 m1 已成功交付并保存最终结果，则改为安装该返回供 g1 接纳，不再运行 m1；g1 已接纳时则继续它之后的位置。这两种分支不能统一成“找到 CP 就 run”。

父层等待 CP 必须先于子层可能产生效果的启动建立。若只能找到孤立的 m1 CP，找不到父层必要状态，就只具备局部 O 继续能力，不能宣称恢复整个 R/E 链。初版测试应显式构造并检查这一条件。

E 当前的 selected、state、feedback、checkedCandidates 和 step 是局部变量，需要在相应业务恢复点声明必要子集。当前 SelectionUsage.add、tasks.select 和流式 committed 等行为也不能被普通 execute 重入再次触发。恢复入口从已接纳的位置继续；需要重新提供服务进度时使用恢复基线，而非伪造新输入、新 task 或新消息变化。

用户消息在 E Context 创建前已经由 R 的普通 append 资源写入。此链路从已建立的 E 继续，不再次执行 R 的输入追加。输入已保存但尚无首份 R CP 的更早窗口，需要另外的受理与身份契约，不能由这个 CP 方案冒充解决。

e1 回答落实之后的记忆提取和文件保存有各自的效果边界。当前已按第 0 节补齐固定批次与文件创建日志；这个简图仍只展示回答链，不能把消息的原子提交保证推广到文件系统。

## 10 中断窗口与处理结果

| 中断或失败位置                      | 恢复依据                       | 允许的行为                                         |
| ----------------------------------- | ------------------------------ | -------------------------------------------------- |
| CP 已形成但未保存                   | 无可用新 CP                    | 不发布“已保存”；不以临时内存作为跨进程保证         |
| m1 CP 已保存，父层未接纳            | 原输出与准确父子关系           | 返回原输出并进入父层接纳，不重发模型               |
| m1 最终成功交付已保存，父层尚未接纳 | 固定最终结果与交付状态         | 安装返回事实，只继续父层接纳，不重启 m1            |
| 子 Context 已成功，但最终交付未确定 | 只有中间完成状态               | 不据此宣布子交付成功；无对应契约则拒绝继续         |
| e1 接纳前 CP 已保存，消息未追加     | 固定回答、旧进度、操作身份     | 在实体确认未落实后首次追加                         |
| 消息与凭据已提交，调用未得到回执    | 实体权威凭据                   | 取得原凭据，不再次追加                             |
| 已取得凭据，父层新进度尚未保存      | 原凭据、固定输入与声明接纳内容 | 继续完成接纳，不任意重跑整个接收函数               |
| 父 accepted CP 已保存，旧子 CP 仍在 | 父层权威当前进度               | 沿父层新位置继续，不回退到旧子位置                 |
| 后续子层可能已启动但无确认进度      | 已保存启动依据，效果状态不明   | 明确不可继续；只有安全重算契约可改变处理           |
| 当前进度已终结，仍保留旧 open CP    | 权威交付终态                   | 拒绝重新执行；允许有依据的原结果读取和父层后续接纳 |
| 版本、资源或必要正文不可用          | 检查失败事实                   | 停止恢复，不套用最新声明或当前数据                 |
| 观测失败但实体或 CP 已提交          | 原权威事实                     | 不回滚，不把观测故障变成业务重做                   |

“确认未落实”要求实体对操作查询与提交具有完整且一致的保证；任意外部系统查不到记录不能直接套用这条规则。一个接纳里有多个效果时，每个效果分别确认，部分效果完成不能作为整次接纳完成。

## 11 CP 与恢复观测

### 11.1 各处理者提供类型化出口

| 来源           | 最小事实                                                         |
| -------------- | ---------------------------------------------------------------- |
| Checkpoint     | 捕获完成、保存完成、捕获或保存失败，附工作归属、CP、point 和版本 |
| 恢复入口／绑定 | 载入、检查通过或拒绝；Invocation 未建立前也能解释失败            |
| Invocation     | 从哪个 CP 安装已有状态、从哪个入口继续，以及后续真实执行事实     |
| 父子关系       | 安装的历史关系基线，以及本次真实发生的返回和接纳变化             |
| 资源访问与实体 | 查询或复用原凭据、首次落实、冲突或不可确认                       |

事件名称留给实现定型，但发生条件必须明确：captured 不等于 saved，installed 不等于 continued，continued 不等于 completed。默认只公开标识、阶段与必要摘要，不把完整 CP 输入、正文、资源内容装进每条观测事件。

当前 [ObservationDefinition](../server/runtime/src/definition/observation.ts) 已支持泛型事实，当前 REOA observation 范围仍固定为 InvocationFact。需要扩展绑定到对应来源的窄出口，不把 Invocation 创建前的恢复失败强行伪装成子调用，不将所有新事实塞入 InvocationChange。

### 11.2 恢复基线与真实变化分开

```text
恢复安装：已知 O 返回；E 正在接纳；实体已提交某操作
     ↓
实际续接：查询原凭据 → E 完成接纳 → 保存新 CP → 新子调用
```

载入历史 returned/accepted 不调用原来的 returnedWith/accept 来重演；否则既可能产生假事件，也可能重复业务。复用实体凭据可以产生新的资源读取观测，但不增加实体 revision、不再次发布消息变化。

消费侧按本次处理来源接受恢复基线和新增量。历史记录仍保持原状，新记录安装可以引用旧工作与 CP；恢复不补写虚构的旧 finished，也不把原来源从 incomplete 改成完整。未安装 Recorder 时恢复照常成立。

### 11.3 失败策略

CP 保存是恢复机制所需的真实工作；记录 CP 保存事件是可选观测。两者错误分别归属。观测沿用默认 isolate、显式 propagate；已成立事实不回滚，显式严格观察失败也不能触发业务重做。

保存成功后观察者抛错，事实仍是“CP 已保存，观测失败”。恢复检查失败不进入业务异常处理递归尝试；在恢复入口明确报告原因。原运行已经归属的错误不会因观测关闭或 CP 存在而被清除。

## 12 服务与客户端的边界

内核恢复能力不直接解释 conversationId、submissionId、HTTP follow 或用户文案。服务投影根据恢复产生的运行事实提供交付；客户端不负责重 POST 来恢复执行。

当前 Submission 仅存在进程内。即使内核试验能够恢复 E，也不能声称刷新后可以继续 follow 旧 submissionId。要对外提供这个能力，服务还需持久关联受理身份、工作范围、接纳/终态和反馈位置，并明确跨重启取消与恢复授权。

第一阶段不改当前未知提交的处理，不伪造 completed，也不依据已有回答推断 R 成功。消息同步继续以 Transcript 为权威，正式消息不会因为恢复再次出现；预览不恢复时应保持正式内容与预览身份分开。

## 13 工程实施路径

阶段 1–3 已实现，并扩展到 Observer 内置声明的有限续接、消息/记忆固定落实和文件创建确认；阶段 4 的宿主入口与本地观测已接入，HTTP/客户端交付、自动恢复保留后续需求驱动。

| 阶段       | 实施内容                                                                                        | 完成标准                                                                 |
| ---------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 1 单层机制 | CP 声明/绑定、execute 内明确 point、受控事实安装、保存端口和基础观测；RequestModel 成功输出位置 | 重建活动后使用固定输出返回，模型发送计数不增加；普通无 CP 调用无行为变化 |
| 2 父子链路 | 精确等待关系、返回与接纳恢复、必要父状态、当前进度核对、恢复来源身份                            | R/E/O 链接正确；旧子位置不覆盖新父进度；未支持关系明确拒绝               |
| 3 实体落实 | Transcript 固定追加、Memories 固定批次、文件创建确认、父接纳前后 CP、窄资源端点                 | 在每个提交窗口中断都只追加一次；同操作异内容冲突；既有错误不被清除       |
| 4 有限交付 | 按真实需求接入 Observer 的恢复入口、服务状态与查询；补齐需要跨越的其他实体效果                  | 对用户明确哪些工作可继续；内容、运行和反馈状态一致；不扩大未实现的承诺   |

阶段 1–3 共同构成首个工程验证闭环。只完成阶段 1 不能宣布完整执行恢复；阶段 4 之前不自动恢复真实历史对话或整个服务启动时的未完成提交。

预计改动位置：

- `server/runtime/src/definition`、`binding`：可选 checkpoint 契约及资源/子能力覆盖检查。
- `server/runtime/src/invocation`、`context`：捕获协调、受控恢复构造、明确续接入口、直接关系事实安装；保留原异常与终态不变量。
- `server/runtime/src/checkpoint`：必要的 CP 数据、保存端口和机制实现；是否需要多个文件按实际职责决定，不先造空目录体系。
- `server/runtime/src/observation` 与可选 `records` 预设：生产者事实、恢复基线与记录解释分别处理。
- `server/runtime/src/transcript`：实体固定操作及凭据契约，不能由服务绕过实体 append 不变量。
- `services/observer/src/conversation`：具体点位、状态和续接内容；不能把 selected/state/step 的解释下沉内核。
- `services/observer/src/persistence`、`assembly`：SQLite 保存、实体恢复与独占恢复接线。
- `protocol`、客户端及 app：仅在阶段 4 发生真实跨端需求时增加对应投影，不把 CPF 直接作为线协议。

不引入恢复框架、消息队列产品或新运行层次。复用现有存储和验证依赖；不依赖旧工程或探索仓库。

## 14 验证矩阵

验证使用固定模型返回和可控中断，不访问真实模型。中断测试需要结束原活动，再重新建立对象；不能保留旧闭包或 Promise 继续跑而称为恢复。涉及持久提交窗口时使用临时 SQLite 与子进程，区分真正中断和普通抛错终态。

| 验证                     | 必须成立                                                        |
| ------------------------ | --------------------------------------------------------------- |
| 单 O 返回后续接          | 原请求和输出一致，发送模型次数不增加                            |
| 多层恢复                 | 直接归属、父 round、同级位置正确，已完成 A 不重跑               |
| 同 key 多次调用          | 恢复准确子工作，不按 key 或数组猜测                             |
| 父已接纳、子 CP 较旧     | 不回退父进度，不重复接纳                                        |
| 子已终结、父尚未接纳     | 使用已保存最终交付，不重跑子层，也不把 Context 成功误当交付成功 |
| 重复打开同一 CP          | 已推进或已结束时拒绝过期推进，不并发运行                        |
| 原输入与当前资源变化     | 原决策依据不漂移，当前访问约束重新检查                          |
| 无父依据或缺正文         | 明确不可恢复，不降级重新跑原请求                                |
| 消息提交前后逐点中断     | 消息只增加一次，原凭据位置不随集合长度变化                      |
| 同操作不同内容           | 冲突且原内容不变                                                |
| 实体成功、捕获或观测失败 | 保留真实效果，不误判未执行                                      |
| 业务进度与 accepted CP   | 一致读取，不出现 accepted 对应旧 state                          |
| round 与预算             | 续接不增加业务轮，不重置已经使用的次数                          |
| 无效 JSON 后的新校验失败 | 若支持该后续路径，原资格检查仍成立；不能放宽重生成契约          |
| 旧异常处理位置           | 首批明确拒绝，不重新包装为普通成功                              |
| 明确取消／失败／成功终态 | 不使用更早 open CP 自动复活                                     |
| 无 Recorder、观察者失败  | 恢复依据独立；按隔离/传播策略分别归属                           |
| 历史关系安装             | 不伪造 started/returned/accepted，不增加消息 revision           |
| 恢复来源与顺序           | 同来源不重置 sequence，不跨进程相减单调时钟                     |
| 裁剪旧子正文后继续调用   | 保持逻辑工作内下一子位置，不从剩余 children 数量重新编号        |
| 旧内容和数据库兼容       | 不迁造不存在的恢复依据，历史只读内容保持可用                    |

## 15 设计时需要定型的有限事项

心智模型与职责已经可以作为设计基线。以下属于落地时必须有结论的契约，不以“以后扩展”代替检查：

1. 原 Context 身份与新处理来源的具体构造接口，以及旧调用视图如何读取已安装的必要子事实。
2. 首批 CPF 编码、point 状态 Schema、容量限制和声明版本定位；未支持的异常与阶段必须可识别地拒绝。
3. 捕获一致边界、父子等待依据的保存时机、当前进度版本及终态保存失败的处理。
4. Transcript 操作依据比较、同事务凭据结构与恢复后的内存安装；保留期内可确认，不能静默丢弃凭据。
5. 各能力声明支持的恢复位置；文件未知窗口、尚无子 CP 的交接和旧服务提交交付边界保持明确。

这些事项的首版结论见第 0 节及对应类型与故障用例。任意函数重放、全量调用栈恢复、自动迁移声明版本、跨进程竞争接管、任意外部效果恰好一次，不属于本方案首批承诺。
