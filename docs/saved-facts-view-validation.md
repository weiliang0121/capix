## 1. 这轮回答的问题

上一轮证明：稳定接纳只需在成立、首次持久认证和冷恢复时检查，不必在每次热保存时重新检查旧值。但这不自动消除另一项成本：为了执行 point.check，每次先把所有历史关系转换成作者可读的事实对象。

本轮把两部分接在同一条实验保存链上，验证：

```text
原事实所有者中的稳定输入／返回／接纳
    ↓
关系与选择的独立认证：首次检查全部元数据，后续检查新增／变更
    ↓
point.check：作者请求哪条关系，就构造哪条完整固定事实
    ↓
既有事实库保存新增事实与当前 head，核对提交回执
```

结果支持这个分工：**事实查询不必先构造全历史；引用认证不能取决于作者是否读取；当前组合仍每次检查。** 没有把任意 point.check 改成增量函数，也没有建立第二套可变调用状态。

## 2. 实验实现与认证范围

[saved-facts.mjs](../examples/checkpoint-facts-study/saved-facts.mjs) 是实验查询适配器，读取既有 ReceptionEvidenceCall／FactCall。关系、固定正文、选择出现项和推进修订仍由原模型持有。三个既有模型文件只增加窄查询、同步检查锁和固定 child key；没有改生产包。

| 操作                        | 本轮成本与行为                                                   |
| --------------------------- | ---------------------------------------------------------------- |
| 不查询事实                  | 不构造 ChildFact，不读取历史正文                                 |
| 查询某个出现项／单值槽位    | 按准确身份点查，只构造这一条完整 ChildFact                       |
| 同一次检查再次查询同一孩子  | 复用本次已构造事实；重复出现项仍保留各自位置                     |
| count／latest               | 使用事实所有者已有的派生索引                                     |
| values／list／requireUnique | 明确枚举；按实际扫描和包装数量计量                               |
| 读取整个 many 引用数组      | 明确读取全部出现项，不能称为有界点查                             |
| accepted／handled           | 核对准确关系、结果种类及登记契约，不重跑已认证接纳的 codec/check |

返回的 ChildFact 包含当时的 input、returned、reception、key/order，而不是会随后关系推进改变的 getter。旧 pending 事实在孩子完成后仍是 pending；旧返回、接纳值不能被修改。稳定事实正文读取只是取得固定值，**计数不代表遍历了正文的每个字节**；作者之后做深比较或拼接还会另有成本。

### 关系／引用认证与查询分开

独立认证在作者 check 前完成，即使 check 为空，也会拒绝：未知槽位、错误 one/many 基数、缺少必需 one、目标成员／契约／归属不符。

独立复核还发现一个初版遗漏：未被 refs 选中的孩子，如果作者也不读取，会绕过适配器的成员登记检查。这个遗漏已经作为反例补入；关系声明认证必须覆盖所有直接关系。首次／冷载入遍历关系元数据，热路径核验新关系的成员位置／契约；后续关系状态依靠所有者保持固定身份，不再扫描旧关系正文。单纯“读到时再检查成员”不成立。

- 固定槽位布局首次使用或冷载入：认证全部现有 many 出现项。
- 后续热保存：one 槽位逐项核对；many 只核对本次仍有效的新增出现项。移除不删除原关系，重复不去重。
- 每次核对槽位元数据；成本与声明槽位数有关，不是无条件 O(1)。变化列表也要读取，按本次新增事实和关系事件计费。
- 只有成功提交并核对回执后才安装认证基线。作者检查失败不安装；绕过适配器直接保存而消耗变更列表，下次会因修订不符重新认证基线。

因此“作者不读取就零成本”只适用于事实包装与正文读取，不适用于所有认证和提交工作。关系首次／增量认证也单独计数，不混进作者全量读取。

### 查询窗口的实验约束

查询端口只在同步 check 期间有效，检查期间不允许重入保存或修改事实源。异步返回、抛错的 then getter 也关闭窗口；同形伪引用、别次检查的引用和旧进程契约对象不能成为当前查询权限。

已经取得的完整固定 ChildFact 可以在检查后保留；查询端口不能在未来读取更新后的关系。这是本轮采用的候选边界，**不能直接宣称与现行可保留的整份纯值 facts 完全兼容**。若生产需要在检查后继续查询同一个历史切面，需要持有对应版本的查询依据，不能让延迟 getter 读取当前活关系。本轮不提前决定这项公开 API。

## 3. 与真实 ToolLoop 的对照

[saved-facts-policy.mjs](../examples/checkpoint-facts-study/saved-facts-policy.mjs) 直接使用生产 ToolLoop 的 point.check、原接纳 Schema/codec 和已有实体夹具。首次将夹具事实导入实验调用，之后通过明确 append/settle 推进同一个调用，**没有在每次保存前比较全量快照来制造增量**。

45 项验证包括：

- 13 个阶段：等待模型、接纳模型、等待工具、成功接纳、预检拒绝、失败处理、下一模型以及最终回答；每个阶段也经过事实库持久化和冷载入后重新核对。
- 19 个策略反例与原 check 的判断一致，包含旧交换前缀／修订变化、refs 顺序、旧输入／回执变化、当前 cursor/active 错误、目录／预算变化、遗漏引用和未知点。
- 准确成员契约、引用身份、parentRound、创建顺序的反例单列在冷导入认证中，没有把它们冒充原业务 check 已有的职责。
- 热推进只做一次冷导入、5 次新孩子追加、6 次结果接纳；接纳成立／首次持久检查各 6 次。

最终状态再保存一次，旧事实编码和接纳持久检查都是 **0**，未变 many 选择无需重新扫描；但原 ToolLoop check 主动调用 values 和读取引用数组，仍构造 **6** 个 ChildFact、取得 **19** 份正文。这是原策略实际请求的数据，不应被包装优化掩盖。

两处原有边界明确保留：

1. ToolLoop 三个已知 point 共用 check。切换已知点不一定被这个函数拒绝，不能据此声称已经证明对应 resume 的全部资格。
2. 某些重复工具引用能通过 point.check，但随后实体确认会拒绝。选择出现项不自动变成 Set，点检查也不替代实体凭据确认。

## 4. 成本对照

同一事实模型、相同小输入／输出、每个孩子等待和接纳后各保存一次。比较四种查询方式：不读取、只读当前孩子、作者显式全量读取、在局部检查前先全量包装的对照。后者用于复现“先转换所有关系”的工作量，**不是运行生产 Frame v5，也不是耗时／吞吐对比**。

| N 个孩子 | 主要保存数 | 先全量包装／显式全读：构造数 | 只读当前：构造数 | 只读当前：正文取值次数 | 无查询：构造／正文取值 |
| -------: | ---------: | ---------------------------: | ---------------: | ---------------------: | ---------------------: |
|       32 |         64 |                        1,056 |               64 |                    128 |                   0／0 |
|      128 |        256 |                       16,512 |              256 |                    512 |                   0／0 |
|      512 |      1,024 |                      262,656 |            1,024 |                  2,048 |                   0／0 |
|    2,048 |      4,096 |                 未运行此对照 |            4,096 |                  8,192 |           未运行此对照 |

这组夹具只读当前时，等待保存读取输入 1 份，接纳保存读取输入／返回／接纳 3 份；每次只构造 1 个对象。N=8 与 N=128 的有界策略另有直接对照，热保存计数完全相同。

引用认证单列：N=32/128/512 的首次 many 认证均为 1，后续新增项认证为 31/127/511，one 核对为 64/256/1,024，总目标认证为 96/384/1,536。这个模式只把“每次重验全历史”消掉，没有消掉真实新增项或当前 one 的认证。

关系声明认证另计：同三组首次认证各 1 条，后续认证各 31/127/511 条；N=2,048 时为首次 1 条加新增 2,047 条。作者未选择的关系同样经过这项检查，没有用零包装数掩盖认证成本。

接纳固定／持久检查均各 N 次；旧接纳不重新编码或检查。额外再保存一次相同状态时：旧事实编码、接纳持久检查和事实行写入仍为 0，但局部作者检查仍构造 1 份事实、读取 3 份正文、认证 1 个 active 槽位；state 和 head 仍处理并提交。

计数来自执行路径，不由公式生成。全部扫描／目标认证／正文取值分别保留；显式全读的包装数仍是 N(N+1)，正文取值为 3N²+N，证明复杂度可以来自作者选择的检查范围。

复现命令：

```sh
node examples/checkpoint-facts-study/saved-facts-cost-study.mjs NEW_OUTPUT_DIRECTORY
```

最终产物为 `.capix/saved-facts-view-20261107/counts-final/summary.json`，保存 13 组样本、逐次计数及来源文件 SHA-256。计数测量不包括首次固定大材料、任意作者函数内部的深比较、SQLite 冷恢复或生产调用全部生命周期；不能由此宣称整个 CP 已达到有界单步成本。

## 5. 冷恢复必须核对原保存组合

[saved-facts-process.mjs](../examples/checkpoint-facts-study/saved-facts-process.mjs) 通过首进程硬退出和第二进程重新载入，验证以下顺序：

```text
读取原 head
→ 完整认证事实库与关系、解码并检查接纳
→ 重新认证原选择
→ 运行原 point／state 的 check
→ 才允许这条实验恢复流程继续并保存
```

9 项跨进程测试：accepted 和 handled 正常续接；4 类即使作者不读取也必须拒绝的槽位错误；3 类原 point/state/出现项被改变的组合错误。后三项重新计算 head 摘要，确保拒绝来自组合检查，而不是仅靠字节损坏检测。

拒绝时没有执行后续推进，也没有产生新修订。正常冷载入重新检查接纳一次，后续热保存不重新认证其正文。

这一顺序由实验恢复入口显式组织。裸 ReceptionEvidenceCall.reopen 仍只重建事实信任，不自动运行服务 point.check；未来接入生产恢复入口必须保证这条顺序，不能把“事实加载成功”当作“原组合可继续”。本轮不增加真实宿主恢复覆盖，也没有执行外部副作用，不能据此承诺资源恰好执行一次。

## 6. 保留的限制与下一步

- 本轮适配器的槽位布局固定。换布局需要重新建立认证依据；尚未证明多 point 不同布局之间切换的增量认证成本。不能仅凭 point 名称沿用另一布局的证明。
- 任意 point.check 仍执行，不自动推断其闭包或历史依赖。稳定旧事实与变化的 state 组合后，仍可能产生新的拒绝条件。
- state 每次固定和编码，日志／内存事实仍增长，冷恢复全量读取。这些没有通过禁止大 state、强制分段或要求 continue-as-new 来规避。
- ToolLoop 原策略仍全量读取，这轮只证明它可消费同一份固定事实；没有悄悄删掉其旧前缀断言。
- 生产事实字段、waiting 子 head 资格、受保护失败和资源活动继续沿用原实现。本轮不是完整 Frame 新版或生产迁移。

下一步应继续核对**同一调用在不同 point/refs 布局间切换时，哪些认证依据仍可复用、哪些必须重建**，并保持原 head 资格检查先于继续行动。这是这条保存链尚未覆盖的真实边界；不需要新增业务实体，也不应为了性能削弱现有选择和恢复语义。
