# 真实调用边界：显式续接与协调重放验证

日期：2026-11-07。隔离实验，不修改生产实现、不调整恢复资格，不决定用重放替换 CP。

## 1. 问题与比较口径

上一轮 [共同模型对照](recovery-replay-comparison.md) 证明：在相同固定事实和效果确认规则下，可以用显式位置续接，也可以重进受约束的协调函数。它尚未证明真实资源窗口、子关系、接纳权限和退出规则能否维持。

本轮把两种作者写法接到同一条真实链路：

```text
Scene
  └─ Group：固定材料 → Node 正式交付 → 接纳回调 → Transcript.applyFixed
       └─ Node：真实资源操作 → 资源清理 → 子 CP 最终交付
Scene：接纳 Group → 预览 → 业务观察 → 最终退出
```

两端都使用公开 Runner.resume 和当前 Frame v5。`explicit` 从已声明阶段继续；`replay` 在恢复处理函数中重进共同协调函数，遇到已成立步骤时读取事实，尚未接纳的子结果才进入真实接纳。**这是作者侧重放策略的验证；不是内核透明重放，也没有去掉 point/state/refs/reception。**

比较的目标不是代码行数，而是：相同持久依据是否导致相同正式效果；当次窗口或必要机制失败时，候选是否仍拒绝成功。

结果：**真实接纳、固定效果确认、清理失败和取消边界可以保留；同一业务函数的恢复观察出口尚不完整。** 重放没有解除这些职责，也没有取代现有恢复机制。本轮完成 35 项定向验证，含明确标注的观察缺口反例。

## 2. 哪些对象真实参与

| 对象 | 本轮使用                                     | 未代替的责任                             |
| ---- | -------------------------------------------- | ---------------------------------------- |
| 结构 | 真实 Scene、Group、Node 与固定成员登记       | 不重建另一套模拟调用树                   |
| 调用 | 真实 Runner 创建/恢复，保留原 contextId      | 不恢复旧 Promise、JS 栈或 Work 对象      |
| 资源 | ResourceOffer、捕获、当次端点和 onClose      | 保存值不能当作活动窗口                   |
| 实体 | TranscriptResource.append.applyFixed         | 凭据由真实父子接纳产生，不由测试手填     |
| CP   | ConversationStore 的 SQLite 实现             | 与实体提交仍是不同事务                   |
| 观察 | 普通严格观察、恢复 CP 观察、被动订阅分别验证 | 被动订阅失败不能冒充必要机制失败         |
| 中断 | 子进程直接 exit(73)，新进程 resume           | 不把已终态镜像抹掉 delivery 后伪造成中断 |

独立诊断事件用于断言执行次数和顺序，不参与恢复判断。夹具不用真实模型；没有验证网络提供者、独立 Interaction、并发竞争或生产宿主的内容资格检查。

## 3. 事实与本次权限的分界

接纳回调并不是拿到旧值后任意再执行一次：

- 子成功交付已经保存、父接纳尚未成立：恢复准确子关系，在新 Work 的授权范围内执行父接纳。
- 实体已落实但父接纳 CP 尚未保存：回调可能重算；同一 Transcript 固定操作确认原回执，不重复追加。
- 父 accepted/handled 已经保存：读取经过认证的接纳值，不再执行接纳回调。

`TranscriptResource` 在操作内取得 `activity.reception()`，形成准确 parentContextId、childContextId 与 position。相同正文不能替代这份归属。恢复的 deps/uses 重新限定本次 Work；历史引用不授予旧端点的使用权。

对应源码：[固定资源接纳](../server/transcript/src/resource.ts)、[实体确认与追加](../server/transcript/src/transcript.ts)、[关系接纳](../server/invocation/src/invocation/relation.ts)、[恢复 Work](../server/runtime/src/binding/work.ts)。

两种模式在下表得到相同的正式效果。计数为中断前与恢复后累计；成功只表示当前内核实际交付成功，不抹去第 4 节的观察出口限制。

| 硬退出或故障位置                       | 结果           | Node 正文 | 接纳回调 | 消息提交 | 验证意义                                        |
| -------------------------------------- | -------------- | --------: | -------: | -------: | ----------------------------------------------- |
| Group 已保存 waiting，Node 尚无首 CP   | 拒绝           |         0 |        0 |        0 | 保存意图不等于可以重新创建调用                  |
| Node 成功 finish 后直接退出            | 继续           |         1 |        1 |        1 | 只补父接纳，子不重跑                            |
| 实体已提交，父接纳 CP 未保存           | 继续           |         1 |        2 |        1 | 回调可重入，实体确认同一固定操作                |
| Group accepted 已保存                  | 继续           |         1 |        1 |        1 | 直接读取接纳值，不二次接纳                      |
| Scene accepted 已保存                  | 继续           |         1 |        1 |        1 | 不再恢复 Group 正文                             |
| 资源正文返回，onClose 抛错             | 失败           |         1 |        0 |        0 | 正文候选不是正式成功                            |
| 子 finish 已提交，回执抛错，活进程收尾 | 失败           |         1 |        0 |        0 | 子持久成功与父收到失败分别保留，fallback 不运行 |
| 预览后普通严格业务观察抛错             | 失败           |         1 |        1 |        1 | 已成立消息不回滚，根不成功                      |
| 预览后请求取消                         | cancelled 终态 |         1 |        1 |        1 | 已有内容保留，终态不能恢复                      |
| 恢复开始时严格 activity 观察抛错       | 失败           |         1 |        0 |        0 | 新恢复活动仍受必要机制约束                      |

另验证了二次硬退出：实体提交后第一次中断，恢复接纳并保存后第二次中断，第三进程完成。总计 Node 正文 1 次、回调 2 次、消息提交 1 次。

外部材料从 revision 1 改成 2 后恢复，Group capture 确实再次运行，但从解码后的**原输入**重建供给；结果仍使用 revision 1。材料操作不重新执行。普通端点及 waiting-resume 新签发的端点，在调用退出后再次访问均被拒绝。

本例的区别非常有限：显式恢复直接调用剩余处理；replay 重进以下协调函数：

```js
async function coordinate(port) {
  const material = await port.material();
  return port.child(material);
}
```

作者手写的恢复 port 将 material 映射到保存值，将 child 映射到恢复原关系或读取 accepted。Group 阶段中断后，replay 的协调正文累计 2 次，显式路径 1 次；实体效果不因此增加。**这个小适配证明可组合，尚未证明一般程序能自动匹配历史，也未证明作者总体成本降低。** 两端仍保存同样的业务点，Scene 的输出阶段继续使用显式恢复。

预览的成对反例：保存 `preview-pending` 后、emit 前退出，累计 delta 为 0；emit 后、保存 `previewed` 前退出，累计 delta 为 1。两端留下同一种 CP 阶段，恢复都不能由它判断哪一种情况发生。本实验均保守拒绝；保存 `previewed` 后恢复则不重发旧 delta，继续最终交付。这个标记至多说明生产端发出过，不证明浏览器收到或接纳，更不恢复预览历史。

## 4. 已发现的恢复观察接缝

独立探针在保存未终结根后直接退出，再以同一 contextId 在新进程执行同一个业务函数。业务函数先调用 `work.observation`，再读取资源；必要观察失败即使被业务 catch，也应该仍由调用承担。

| 路径                                  | 业务事件 strict / passive 收到次数 | 资源方法执行次数 | 根交付    |
| ------------------------------------- | ---------------------------------: | ---------------: | --------- |
| 普通 run，strict business 抛错        |                              1 / 1 |                0 | failed    |
| resume，执行同一个业务注释            |                              0 / 0 |                1 | succeeded |
| resume，strict resource returned 抛错 |                              0 / 0 |                1 | failed    |

第二行是**反例**。`work.observation()` 在恢复中正常返回，但事件没有到达普通观察、CP 严格观察或 Runner 被动出口；测试通过代表复现当前行为，不代表认可该契约。

根因是恢复时 Invocation 使用 `CheckpointObservation`；它转交 activity/resource/transcript/memory，没有 business 分支，继承的 business 发布器面对空会话。普通观察安装不会在恢复中重新绑定，这是为避免伪造历史事件而保留的边界。

这不是本次重放造成的新回归。[运行出口](runtime-ports.md) 与 [Checkpoint](checkpoints.md) 已明确此前没有增加恢复业务注释出口。本次将这项限制变成了真实的新进程反例：**不能宣称同一业务函数在恢复时已经拥有全部相同的必要观察能力。** 显式恢复同样受影响。

恢复中的新事件与历史事实回放需要分别定义。补充新业务事件的恢复出口，不等于重新执行历史观察；也不能用发布一个不同的资源事件来宣称原业务事件已经交付。本轮只记录缺口，不修订生产契约。

源码：[恢复观察桥](../server/invocation/src/checkpoint/observation.ts)、[CP 事实联合](../server/invocation/src/checkpoint/contract.ts)。反例：[observation.test.mjs](../examples/recovery-runtime-study/observation.test.mjs)。

## 5. 如何解读“恢复调用”

固定事实能够保留输入、交付、接纳和准确效果依据；活调用负责当前资源窗口、当前取消、当前清理与出口。这两类信息不能互相代替。

尤其需要区分子 CP 提交成功后的两条路径：

1. 活进程收到错误回执：当次交付失败，父层不能将其当作可接收业务失败降级为成功。
2. 随后进程消失、父失败尚未形成持久终态：恢复可能读到父 waiting 与子成功 delivery，按原规则继续。这不是把第一次活动改判成功，而是新活动依据持久事实推进。若父终态已经保存，则不得复活。

这项差异已有 [真实回执切点测试](../examples/checkpoint-facts-study/receipt-recovery.test.mjs)，本轮纳入回归。不能把所有“回执失败”概括成永久禁止恢复，也不能把 Store 成功概括成活调用一定交付成功。

重放不会自动消除这些边界；它只是提供重建部分协调局部变量的另一种方式。普通函数里的非受控效果、竞争顺序和未声明代码变更，仍受上一轮反例限制。

## 6. 对下一步的判断

不需要把“调用是活的”推导为调用无法恢复，也不能因为重进普通函数可行，就删掉调用的持久事实。现在更准确的区分是：

| 内容                   | 本轮依据                                          |
| ---------------------- | ------------------------------------------------- |
| 已成立的数据与关系     | 原输入、子交付、父接纳、实体固定回执              |
| 新活动要重新取得的条件 | 本次 Work、资源端点、取消信号、严格观察与输出连接 |
| 协调位置的重建方式     | 显式 resume 或本例中明确选装的协调函数重入        |

前两项都需要独立成立；第三项是其上的执行选择。本轮没有证明必须二选一，也没有必要预先建立两套公共 API。

下一步应先把**恢复活动承接哪些本次能力**列成契约：哪些读历史事实、哪些新建窗口、哪些只描述新事件、哪些必要失败仍阻止交付。`work.observation` 是已经找到的具体接缝，宜先明确是否及如何在恢复活动中提供；这不要求重播旧观察或建立全局事件系统。

对于预览，则分别决定新活动输出和历史展示接回的承诺，不让调用 CP 承担浏览器交付确认。完成这些接缝约定后，才适合评价可重放协调是否值得作为作者预设；不能用它跳过缺失依据、降低必要故障保护，或强制所有调用遵守重放限制。

验证结果：

- 新实验 **35/35**：32 项真实结构与故障测试，加 3 项观察对照；其中恢复业务事件丢失是明确标记的反例。

- 持久产物 **32 组主场景 + 3 组观察对照**，包含两模式、硬退出、故障、材料变化和二次中断。不是性能基准，诊断自身还会写 SQLite。

产物：[summary.json](../.capix/recovery-runtime-study-20261107-final/summary.json)、[35 项测试](../.capix/recovery-runtime-study-20261107-final/tests.tap)、[89 项回归](../.capix/recovery-runtime-comparison-regression.tap)、[99 项回归](../.capix/recovery-runtime-regression.tap)、[构建日志](../.capix/recovery-runtime-build.log)。summary 记录八份实验源码的摘要、Git HEAD 与既有已跟踪工作树 diff 的摘要；目录中保留实际数据库。

限制：

- 验证的是当前工作树，包含此前尚未提交的 CP 值／SQLite 复用候选。本轮没有改动或单独验收这些生产改动，未运行全仓 `pnpm check`。
- 没有完整的生产宿主恢复资格预检。尤其 accepted CP 直接消费认证接纳事实，本夹具没有再向实体确认其凭据是否被外部删除或损坏；不能据此宣称与真实对话宿主资格等效。
- 仅串行、固定的一个子 Node；没有重做全部并发、独立 Interaction 或长期事件推进的验证。
- 仍使用 Frame v5 全量关系保存；没有测试事实行增量表示，没有宣称解决长任务 CP 计算范围问题。
- 所有异常与切点由隔离夹具注入，测试只使用临时／专用数据库，未读取用户对话库、凭证或调用真实模型。
