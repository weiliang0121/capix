# 调用续接：显式恢复与受约束重放对照

> 历史设计／验证记录：下文版本、测量和“下一步”保留当轮语境，不是当前兼容承诺。现行接口见 [Checkpoint](checkpoints.md)、[增量引用选择](checkpoint-selection.md)；旧格式与数据库策略见[开发期兼容](development-compatibility.md)。文档脉络见[导航](README.md)。

日期：2026-11-07。状态：隔离实验与概念判断，未迁移生产，未决定以重放替换现有 CP。

## 1. 本轮回答什么

调用涉及实体、局部变量、结构、资源和外部交互，能否安全续接？能否用重新执行协调代码减少作者的恢复声明？

本轮把问题收紧为：**在相同固定事实和外部效果确认规则之上，比较保存推进位置与重建协调局部变量。** 两者都不恢复旧 Promise、资源窗口或 JS 栈。

结论是：受限场景存在可行解；重放可以减少作者对位置和局部变量的重复表达，但没有取消调用事实、固定效果确认及版本约束。还不能据此判断整个内核应改为重放。

“只记录事实、不记录调用”需要修正：本实验两端都记录了调用意图、准确身份、返回和父接纳。它们就是调用事实；不保存活 Invocation 对象，并不等于不保存调用依据。

## 2. 如何保证对照有效

可执行代码：[场景](../examples/recovery-comparison/scenario.mjs)、[共同模型](../examples/recovery-comparison/model.mjs)。

```text
固定入口
  → 材料读取成立
  → 模型子调用派发意图
  → 外部执行 / 外部回执
  → 子返回成立
  → 父接纳意图
  → 接纳映射 / 实体效果 / 固定回执
  → accepted 或 handled 成立
  → 根终态
```

两端共用：

- 同样的入口身份、固定输入和 policyVersion。
- 同样的三个受控操作；每项有 ordinal、kind、name、member、owner、准确输入及独立 UUID。
- 同样的意图先于效果、结果晚于效果的提交边界。
- 意图与 head 中的命令数量锚点同库原子提交；缺失历史后缀不能被误认成尚未执行的新步骤。
- 同样的 `returned` 与 `accepted/handled` 区分；模型失败不因父处理而变成成功。
- 同样的外部效果回执核验；已记录意图但缺准确回执时拒绝，既不重发也不猜测未执行。
- 同样的冷读取检查，以及相同的失败、取消、成功终态禁止推进。

协调事实与模拟外部世界分别使用 SQLite WAL/FULL。进程在指定位置执行 `process.exit(73)`，绕过 finally；恢复由新的进程读取同一组数据库。效果计数只作观察，不参与恢复判断。模拟 World 的效果与回执故意分开，保留“已执行但无回执”的真实不确定窗口。

这是**两种新候选协议模型**的公平对照，不是“生产 Frame v5 与生产重放实现”的对照。共同模型只有受限 JSON、单写者和串行链；其中命令记录并不冒充真实 Invocation 的完整交付、资源权限或错误来源。

## 3. 作者写法的差异

下面是与可执行模型对应的简写，不是拟定公开 API。

重放写法保存普通局部变量：

```js
function run(work) {
  const material = work.read();
  const delivery = work.model(material);
  const accepted = work.accept(delivery);
  return work.finish(accepted.value);
}
```

恢复时重新进入这个函数。已完成的受控操作按准确身份和输入匹配后返回原结果；已经接纳的操作不重跑接纳回调。尚未完成的操作只在既有确认规则允许时继续。

显式写法另外保存推进位置和局部事实引用：

```js
if (point === 'read') {
  read();
  savePosition('model', { material: readFact });
}
if (point === 'model') {
  model(load(material));
  savePosition('accept', { delivery: childFact });
}
if (point === 'accept') {
  accept(load(delivery));
  savePosition('finish', { accepted: receptionFact });
}
return finish(load(accepted));
```

这种写法直接从保存位置开始，不重走已经越过的协调语句。这里为了可比性，两端使用同一事实日志；不说明现有作者必须改成上述 switch/if 写法。

| 维度         | 显式位置续接                         | 受约束协调重放                            |
| ------------ | ------------------------------------ | ----------------------------------------- |
| 局部变量     | 作者保存需要的值或事实引用           | 通过重进函数、注入历史结果重建            |
| 已完成操作   | 按引用读取                           | 再遇到同一命令时匹配并注入                |
| 已成立接纳   | 跳过原回调                           | 也必须跳过原回调                          |
| 未完成部分   | resume 明确规定继续范围              | 重放越过历史末端后继续                    |
| 作者主要负担 | 位置、state、refs 和 resume 的一致性 | 哪些代码可重演、操作如何匹配、版本兼容    |
| 冷成本       | 事实校验 + 定位 + 继续               | 事实校验 + 历史协调代码重执行/匹配 + 继续 |

不能从第一段代码短就推出总体契约更简单。它把一部分复杂度从作者的恢复分支移到了执行规则。

## 4. 硬退出矩阵

下表两种模式得到相同的预期结果；“可继续”是本实验协议的覆盖，不是扩张生产宿主恢复资格。

| 进程消失的位置             | 结果     | 依据                                               |
| -------------------------- | -------- | -------------------------------------------------- |
| 原输入保存后，尚未读取     | 继续     | 尚未观察材料，可进行第一次读取                     |
| 读取结果保存后             | 继续     | 复用原读取，不重读变化后的实体                     |
| 模型意图保存后、尚无回执   | 拒绝     | 缺回执不能证明未发送；本夹具即便实际还没发也不猜测 |
| 模型效果发生、尚无回执     | 拒绝     | 模型效果计数为 1，但不能用测试计数作恢复依据       |
| 模型回执保存、子返回未保存 | 继续     | 准确确认同一模型请求，不重发                       |
| 子成功返回保存、父未接纳   | 继续     | 只补尚未成立的父接纳                               |
| 接纳意图保存、实体回执缺失 | 拒绝     | 不将“没找到”解释成允许重新写入                     |
| 实体效果发生、回执未保存   | 拒绝     | 保留不确定性，实体效果仍是 1 次                    |
| 实体回执已存、父接纳未存   | 继续     | 重算纯映射，核对同一固定效果                       |
| 父接纳已存、位置未推进     | 继续     | 跳过映射和实体写入，复用接纳结果                   |
| 根终态已提交               | 只读终态 | 不重进作者函数、不重复效果                         |

另有以下覆盖：

- 恢复途中再次硬退出，然后第三进程继续；模型与实体效果仍各一次。
- failed 子返回已保存但尚未 handled：两端拒绝，以免候选重放悄悄扩张现有失败恢复权限。
- handled 已保存：返回原替代值，孩子的 returned 仍为 failed，回调不重跑。
- failed/cancelled 根已有终态：即使外部回执可读，也不复活。
- 缺原 head、策略版本变化、命令输入/名称/归属变化、准确回执丢失均拒绝。
- 受约束重放若提前返回，却未消费完历史命令后缀，则拒绝，不把旧步骤静默删掉。

固定读取与固定输入也要分开：入口已保存但读取尚未发生时，之后读取到新材料是允许的；读取已成立后则必须保留原观察结果。**固定调用输入不等于提前固定所有未来可能访问的实体。**

## 5. 揭示出来的限制

### 5.1 命令匹配不能证明全部业务逻辑不变

已有子命令被重新匹配时，名称或输入改变会被拒绝。但在子返回之后、尚未发生父接纳前，把映射闭包偷偷改掉且不升 policyVersion，两种方式都可能产生新的接纳内容。

此时没有旧接纳值可比较。只有在实体效果已经发生、有准确回执时，新映射与原效果不一致才会被拒绝。

所以版本化和固定依据不是 CP 独有的负担；重放也不能自动识别所有未声明的语义变更。对已经被显式位置跳过的旧语句进行未升版本修改，则可能出现“显式续接不执行旧语句、重放执行后拒绝”的不同结果；它与损坏历史事实不是同一问题。

### 5.2 非受控代码重复执行

实验在协调函数开头加入一个不通过受控操作的外部计数，模型回执后中断：显式续接从后续位置开始，计数保持 1；重放重新进入函数，计数成为 2。

这不是推荐使用隐式效果，而是证明“操作去重”没有覆盖整个函数。如果中断在显式位置尚未前进的段内，显式恢复也会重新执行该段，计数同样成为 2。两者都必须明确允许重算与效果确认的边界。

### 5.3 结果集合不等于选择顺序

普通 Promise 反例：原执行 B 先完成，`Promise.race([A, B])` 选择 B；重放时给 A/B 都注入已完成 Promise，可能选择 A。

两份结果内容都没变，也没有重复调用，决策却变了。需要记录实际选择，或使用具有明确重演规则的组合操作。对照的 `Promise.all([A, B])` 按输入顺序返回，两种完成顺序得到相同数组。**不能据此把框架并发全部改成串行，也不能把所有并发都当作透明可重放。**

### 5.4 缓存资源结果后重新 run 不是调用恢复

真实公开 Runner 探针运行两次相同 Scene，资源底层效果只发生 1 次，但观察到：资源接收 2 次、子接纳 2 次、资源清理 2 次、预览输出 2 次，并具有不同 entryId。

另一个真实资源探针返回已缓存成功值，但当次 onClose 失败，正式交付仍失败，成功接收回调不执行。

这说明注入结果的边界必须明确定义。不能在资源正文 return 时就记录“正式成功”，也不能绕过当前活动窗口与清理。

## 6. 审查中修正的公平性问题

首版测试把命令损坏放在 child-returned 切点，显式位置尚未推进，因此两端都再次匹配该命令并拒绝。交叉审查把同一损坏移到 accepted 后，发现显式路径跳过旧步骤，简化冷验证漏掉了该历史命令的输入。

因此本轮补充共同的固定场景语义核验与较晚切点反例。**冷验证必须独立成立，不能把重放恰好再次执行命令匹配，当成两边已有同等认证。** 本实验只认证声明好的三步链；它不推断任意业务代码的历史约束，更不是完整 Frame 认证的替代品。

还补充了历史完整性反例：如果日志末尾被删除，不能把缩短后的末尾当作第一次执行的新位置。head 的命令数量与新意图同事务更新，冷读取发现缺少后缀即拒绝；避免为同一旧效果重新生成 UUID。摘要与数量锚点用于本实验的损坏/缺失检测，不防止有写权限者同时伪造全部数据库。

## 7. 计算与持久成本怎样解读

本轮只统计命令和效果，不评价速度或服务器容量：只有三个操作，而且诊断计数自身产生额外 SQL 写入。

| 指标                                    | 显式位置续接 | 受约束重放 |
| --------------------------------------- | -----------: | ---------: |
| 无中断运行：新命令数                    |            3 |          3 |
| 无中断运行：模型/实体效果               |        1 / 1 |      1 / 1 |
| 无中断运行：正文行写入次数              |           14 |         11 |
| accepted 后恢复：共同冷核验命令数       |            3 |          3 |
| accepted 后恢复：再次匹配旧命令数       |            1 |          3 |
| accepted 后恢复：新增映射/模型/实体效果 |    0 / 0 / 0 |  0 / 0 / 0 |

`workflowCommits` 是代码中计数器的名称，实际计数口径为 `#write` 的正文行写入：意图和数量锚点的两次行写入属于同一事务。它不等于物理写入或数据库总事务数，也不含诊断计数的额外写入。

- 两种方式都保存三项意图及三项结果；重放没有让这些事实消失。
- 显式模型额外调用三次 `advance(point, locals)`。这是夹具把位置单独保存的选择，可以与操作结果同事务保存，也可以从既有事实派生；不能当作重放固有的写入优势。
- 冷验证两端都读取历史。重放之后还会匹配旧命令、重执行非受控协调代码；计数与冷校验分开。
- 热路径按行写入不等于整体算法增量化。这个小 Journal 的顺序检查仍会列出命令，不能拿它证明长任务单步 O(1)。
- 频繁中断时，重走越来越长的协调前缀可能再次累计大量计算；它并不自动解决此前 CP 的计算范围问题。显式定位可以少执行旧协调代码，但仍需要独立解决历史认证和材料读取成本。

稳定交付、事实所有权、固定表示和局部验证仍对两条路径都有价值。本轮不撤回此前实验，也不强制 continue-as-new、切短调用或增加新的业务实体。

## 8. 与现有内核接缝的关系

| 现有边界    | 本轮已证明的内容                      | 尚未证明的内容                                        |
| ----------- | ------------------------------------- | ----------------------------------------------------- |
| 结构和输入  | 模型中准确身份、版本和输入可匹配      | 真实绑定布局、恢复 uses、跨进程结构兼容               |
| 资源        | 真实探针证明返回后清理仍影响交付      | capture/refine 的固定材料重建、按当前窗口注入历史交付 |
| 子调用      | 模型分开 returned 与 accepted/handled | 真实父子关系安装、接纳作用域、完整故障归属            |
| Interaction | 模拟外部回执可确认原操作，缺失拒绝    | 自动适配实际持久 Interaction 和独立发送生命周期       |
| 输出、观测  | 重进 Scene 会重复预览，不能冒充原调用 | 历史投影、新恢复活动、严格观察失败的具体接线          |
| 控制        | 持久终态不推进                        | 异步取消、在途后代退出、并发选择和控制传播            |

源码依据：[资源 capture](../server/runtime/src/resource/installation.ts)、[资源操作完整交付](../server/resources/src/activity.ts)、[子调用 run/accept 组合](../server/runtime/src/binding/children/binding.ts)、[关系安装与接纳](../server/invocation/src/invocation/relation.ts)、[调用最终交付](../server/invocation/src/invocation/invocation.ts)、[Interaction](../server/interaction/src/interaction.ts)。

本实验以硬退出表示提交后进程消失；没有完整模拟活进程收到错误回执后继续运行。既有 uncertain/受保护故障规则不能因本实验而放宽。模拟纯数据失败也不能取代真实 Error 身份、catch 语义和 receptionAllowed。

完整结果已在本实验日志时直接使用该事实，不再重新要求外部回执可读；生产宿主还有原 Interaction、内容与固定效果资格检查。两者不能混称等效恢复覆盖。

## 9. 下一步应决策什么

后续真实 Group、资源窗口、Transcript 固定接纳与恢复观察的验证已完成，见 [真实调用边界验证](recovery-runtime-validation.md)。以下保留本轮提出的推进依据。

当前支持保留重放候选，尚不足以全局选择它。最有判别力的下一步，是只把一条真实 Group 接到候选重放端口：

```text
固定材料 → 子 Node 正式交付 → 父接纳落实实体 → 预览 → 必要观察 → 退出
```

检查四个接缝：资源清理失败、子终态 CP 提交后回执失败、实体已落实但父接纳未保存、输出后取消。验收关注真实接纳权限、未知效果拒绝、终态不复活、旧输出不冒充新事件。

之后才讨论：是否把“可重放协调”作为选装执行契约、作者需要接受哪些限制，以及它与显式点是否有明确的组合边界。不能为了证明重放可行而削弱普通 run 的能力，也不预先决定引入两套公共 API。

恢复旧调用与基于新事实开始下一次业务推进仍分开。全天候外部事实到达如何取得推进权，不由这条三步重放链自动回答。
